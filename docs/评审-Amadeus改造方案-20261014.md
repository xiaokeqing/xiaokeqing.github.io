# Amadeus 改造方案评审意见（2026-10-14）

评审对象：`docs/提示词-给外部AI-Amadeus改造评审.md` 中的改造方案（§四 A–F）

## 总体结论

**可行，且调研质量异常高**——所有关键机制（状态机 37/87、场景机 6/19、口型 RMS×3.75/10ms、
眨眼 39–42 帧、硬切无相机、情绪入口 prob=0）都有源码行号或实测背书，配套数据
（statemachine.json / scenarios.json / 15 份源码切片 / 1150 行 HOW-IT-WORKS）已核实齐全。
渲染层 A、运行时 B、口型 C 的分层没有方向性错误。

但有 **4 处可以更优**，其中资产口径一处可直接把预算砍半。

---

## 一、更优方案（按收益排序）

### 1. 资产口径：96MB 可砍到 48MB，甚至 ~20MB（最大收益）

文档 §四-E 的估算（60~80MB → 上限 96MB）偏保守，有两条更好的路：

| 路线 | 总量估算 | 说明 |
|---|---|---|
| ① 全量 medium 图集（**勘误后**） | **55~60MB（上限 60）** | ⚠️ 勘误（2026-10-14 复核）：`web/medium` 实测 35 件 / 34.6MB 但**只含 28 个剪辑**，状态机 37 个图内剪辑**缺 9 个（含 root 的 `idle`）**——照原结论收口角色连待机都播不出。正确口径：补齐 37 剪辑 ≈44MB（中位 1.18MB×37）+ 常用 6~10 剪辑另发 hi 档（高 400~500，防 2x DPR 发虚）→ 总量 55~60MB。详见 `实施计划-页面搬运与Amadeus重规划-20261014.md` §2.6 |
| ② 预合成视频（更激进） | **≈15–30MB** | 见下 |
| ③ 精选子集 | 15–25MB | 有路线①后不再需要 |

**路线② 预合成视频——值得认真考虑的架构替代**：
- 关键洞察：角色只在 **CRT 屏幕内**活动，而 CRT 内背景（空房间底图）是静态的。
  → 离线把"角色帧序列 + 空房间底图"**逐帧合成**，导出**无 alpha 的普通视频**
  （H.264 保底 + VP9 可选）。7552 帧 ≈ 250 秒 @30fps，体积估算 15–30MB。
- **状态机完全不变**：剪辑 = 视频文件，播完掷骰子选下一个；
  `once_then_hold` = `pause()` + 停末帧；硬切 = 双 `<video>` 预载轮换。
- 口型不受影响：说话剪辑的嘴本来就烘焙在帧里；静音时照样叠闭嘴补丁
  （补丁可从"整帧图"缩小为**嘴部裁切小 PNG + CSS 椭圆 mask**，进一步省体积）。
- 收益：体积再砍一半以上；解码全走浏览器原生，自研帧循环代码量减半；
  与"零第三方依赖"红线不冲突（`<video>`/WebCodecs 都是原生 API）。
- 代价：失去逐帧时钟精度（上游本来就没有骨骼/变形，只有换帧，损失≈0）；
  视频首帧需 `preload` 预热，否则硬切瞬间黑帧。
- 建议：**v1 用路线①（图集，已转换完、风险最低），v2 评估路线②**。

### 2. 口型：三条兜底够用，但"最稳"的一档还没写进去

稳定性排序（从高到低）：

1. **服务端随合成返回包络**（文档未列，推荐新增）：`/api/public/tts` 代理在云端合成后、
   落盘缓存前，顺手按同款 10ms 窗 RMS×3.75 算好包络，`audio + envelope.json` 一起返回。
   确定性最强、客户端零算力、无播放时钟漂移。
2. **预生成固定台词 + 预计算包络**（文档已列，正确排第一优先级）。
3. **客户端离线预分析**：拿到音频后先用 `OfflineAudioContext` 完整解码算一遍包络**再播放**。
   比 AudioWorklet 实时分析简单且确定，不依赖播放时钟。
4. 浏览器 `speechSynthesis`：建议**降为最后兜底**——机械音色会直接击穿人设，
   与其伪驱动口型，不如纯字幕 + 帧里自带的嘴（文档的 c 档）。

### 3. 最大的遗漏：浏览器自动播放策略

方案通篇没提 **autoplay policy**：进站语音问候在**用户首次交互前必然被浏览器静音拦截**
（Chrome/Safari/iOS 皆然）。必须显式设计：

- 未交互态 = 字幕 + 动画正常播、声音静默（或显式"点我开声"提示）；
- 首次 pointerdown/keydown 后解锁 AudioContext，再补放/续播语音；
- 这不是边缘情况，是**每个新访客的必经路径**，验收矩阵 P5 应加一项"无手势进站"。

### 4. 模块划分小修

A/B/C 分层认可，两处微调：
- **资产加载独立成 loader 模块**：懒载顺序、降级（reduced-motion/省流量/加载失败）、
  内存回收（只留当前+下一段）都归它，不要散在状态机里。
- 状态机与场景机共用一个"**加权有向图游走**"原语（掷骰子 + once_then_hold + dwell），
  两份 JSON 只是配置。

## 二、最可能翻车的三处（替代与代价）

| # | 翻车点 | 替代方案 | 代价 |
|---|---|---|---|
| 1 | 96MB 总量：Pages 部署/克隆重，且与"画质"矛盾（320–360px 图集在大屏 CRT 区域会发虚） | 全量 medium 48MB（已实测）；或预合成视频 15–30MB | 视频化需一次性离线合成管线 |
| 2 | 进站语音被 autoplay 拦截，"会说话"的核心卖点在首访时静默失效 | 交互门控 + 预生成问候音频 + 字幕先行 | 首访体验降级为"先看后听"，需设计引导 |
| 3 | 闭嘴补丁对齐：整帧闭嘴图 + 椭圆遮罩在 clip-path 缩放坐标系 + devicePixelRatio 下容易漂移 | 补丁裁小到嘴部区域；锚点用 CRT 内归一化坐标；dPR 取整对齐 | 需重新导出补丁素材与锚点数据 |

## 三、其它遗漏（上游机制层面）

- **键盘音效**：视觉运行时包里有键盘音，"她在电脑前"场景的环境音，成本极低、氛围收益高。
- **首句音频缓存**的思路 → 对应你的"预生成进站问候音频"，方向一致，确认做。
- **录屏 NCC 配准方法**：你之前验证"拉远=场景硬切"用的掩屏多尺度 NCC，可直接复用为
  P3 验收的自动化比对手段，不用人肉并排看。
- `sad`/`smile` 不在图里只能手动播——建议直接映射到 8 情绪触发点，别闲置。

## 四、最小可行路径（3 步）

1. **CRT 场景层**：书桌底图 cover + 14 点 clip-path + 空房间 + 6 场景硬切。
   验收：0–15s 每秒印样与参考录屏并排一致。
2. **角色层**：medium 图集 + 状态机（37/87）+ 开场 84 帧（含 39–42 眨眼四连帧证明）。
   验收：30 秒游走节点序列 + 39 剪辑逐一可播截图矩阵；首屏 ≤1.5MB 实测。
3. **对话层**：输入条 → `/api/public/ask` → 字幕 + speaking 动画 + 离线预分析口型；
   自动播放门控。
   验收：无手势进站 / 有手势对话 / reduced-motion / 窄屏 四项端到端过门禁。

注：按今天上午的进度，第 1、2 步的演示版（demo-主页.html）已经存在，实际落地可直接从
"演示 → 工程化（loader/降级/门禁）"开始，不必从零起。

## 附三：语音说话的服务器压力解法（"声音三层架构"）

前提澄清：**小服务器任何时候都不跑 TTS 模型**。GPT-SoVITS 只在你自己的电脑上离线跑，
服务器要么发静态文件、要么转发字节流，两者都是小服务器最擅长的活。

| 层 | 内容 | 合成位置 | 服务器负载 | 成本 |
|---|---|---|---|---|
| L1 固定台词 | 问候/切页解说/状态播报/兜底句（几十句） | 你的电脑离线跑 GPT-SoVITS，一次合成永久使用。**素材无缺口**：官方资源页"Kurisu 语音包"自带 GPT-SoVITS v3 权重 + 参考音频（2026-10-14 站主截图确认；"需自备参考音频"的说法只适用于源码仓库） | **零**（Opus 静态文件放 GitHub Pages，连你的服务器都不经过） | 零 |
| L2 动态回答 | /api/public/ask 的自由文本 | Fish Audio 云端，/api/public/tts 代理只转发字节流 | ≈转发一张图（可忽略）；有 sha256 缓存 + 限流闸兜底 | 按 API 次数，短回复（≤6 句）+ 缓存命中 → 极少 |
| L3 无 Key 过渡 | 动态回答的临时形态 | 不合成 | 零 | 零：字幕 + 说话动画（帧自带嘴），固定台词仍有声 |

配套措施：
- 音频格式 Opus（一句几秒 ≈ 30~80KB）；L1 的口型包络在离线合成时一并算出存 JSON。
- L1 与 L2 音色引擎不同（GPT-SoVITS vs Fish Audio）会有细微差别；若在意，Key 到位后
  可用 Fish Audio 重录一遍 L1，静态文件直接替换，代码零改动。
- **架构红线（2026-10-14 站主确认背景后补）：srv1（2C/2G）与 srv2（4C/4G）均不得跑任何
  TTS/LLM 合成进程**——内存不够（torch+权重 2~4GB）、CPU 打满会让 Suricata 丢包。
  L1 离线合成的合法执行位只有三处：① Fish Audio 云端 API ② 临时租按量 GPU 实例
  （T4 ≈¥1.5~3/小时，批量半小时内，总成本几元，用完即释放）③ 站主本机 3060 Laptop。
- 语音输入（麦克风）**全期不做**（站主 2026-10-14 拍板）：不申请麦克风权限、
  不引入 Web Speech API，交互只有底部文字输入条。

结论：语音上线的真实依赖只有"Fish Audio Key 什么时候到位"，服务器性能不是瓶颈。
