### ② 情绪怎么和"说的话 / 做的动作"对应？"生气就口气重"靠什么实现

**原理 = 四样东西必须同时被切到同一个情绪上**：

```
a) 情绪参考音频（**口气重的真正来源** ✓）
   素材包给 6 类参考：angry / sad / shy / blush / surprised / disappointed
   用法（已验证通道 ✓）：infer(semantic_reference=(参考音频, 日文文本, "日文"))
   ⇒ 同一个模型，换参考音频 → 语气/力度/停顿全变 ⇒ **这就是"生气口气重"** ✓
   ⚠️ 前提：上游情绪路由门槛是 Windows + CUDA + 内置 V3 + **TTS_OUTPUT_LANGUAGE=日文**
      —— 我们切成日语后才满足 ✓（这也是之前吃不到情绪的原因 ✗）
   ⚠️ 包里**没有 happy / normal 参考** ⇒ "开心"用 blush/shy 近似（已在台词库标注 ✓）

b) 情绪化台词（生气的句子 ✓）—— 台词库按 trigger 分组，组内再按 emotion 标注 ✓

c) 对应动作剪辑（`angry_speaking` / `angry_trans` / `smile_speaking` … ✓ 状态机里都有 ✓）
   —— 注意：`angry_speaking`、`sad_trans`、`shy_trans`、`surprise_trans`、`speaking_trans`、
     `speaking_short`、`closed_eye_trans`、`trans_smile`、`thinking_trans` 这 **9 个是"只能靠宿主触发"的入口** ✓
     （状态机里它们的入边概率 = 0 ⇒ 天生就是给"情绪驱动"用的 ✓✓ 架构早就留好了口子 ✓）

d) 可选后处理：语速 / 停顿 / 音量（现在没做 ✗ —— 因为后处理会破坏包络对齐，建议只做"整句语速"这一个旋钮 ✓）

**缺的那一环 = "谁来决定用哪个情绪"** ✗
现在只有"页面/事件 → 固定台词"✗，没有"当前局势 → 情绪" ✓
→ **T14（LLM 决策行为）** 就是补它：把当前告警摘要喂给 LLM，输出严格 JSON：

```jsonc
// POST /api/public/decide   （新增，只读输入、不执行任何操作）
{ "emotion": "angry",              // 6 类之一
  "clip":    "angry_speaking",     // 必须在 statemachine.json 的剪辑白名单内 ✗ 防幻觉
  "line_id": "event_bruteforce",   // 只能引用预渲染台词库的 id（这样一定出得了声 ✓）
  "line_zh": "有人在拿常见密码试我们的 SSH —— 我已经把证据收好了。",
  "urgency": 0.8,                  // 0~1，驱动表情强度/是否打断当前动作
  "reason":  "12 次暴力破解尝试，来源集中"   // 审计用，可展示在 HUD 里 ✓
}
```
**三条硬约束**（防幻觉 / 防卡死 / 防花钱）：
```
① clip 与 line_id 必须通过白名单校验，不合法就**丢弃并回退**到现有"概率+固定事件"逻辑 ✓
② LLM 超时/报错 → 立刻回退 ✓（页面绝不卡住 ✗）
③ 决策结果按"告警指纹"缓存 5 分钟 ✓（同场景不重复请求 ✓）
```

**事件 → 情绪 → 动作 的映射建议**（`[建议]`，可由 LLM 判断，也可先用规则起步 ✓）：

| 事件 | 情绪 | 动作剪辑 | 台词组 | 备注 |
|---|---|---|---|---|
| 暴力破解 / 扫描激增 | angry | angry_speaking → angry_trans | event | 语气重、句子短 ✓ |
| 蜜罐抓到新凭证 | surprised | surprise_trans → surprise_speaking | event | 语速略快 ✓ |
| 一切正常 / 长时间无事 | calm | idle 家族 | status / idle_banter | 闲聊、傲娇 ✓ |
| 深夜 / 回访 | shy(近似温柔) | idle_side_soft_wind | greeting | 语气放软 ✓ |
| 接口取不到数据 | disappointed | sad_trans | fallback | 不能编数字 ✗ |
| 用户问它答不出 | disappointed | thinking_trans | fallback | 明确说"没找到依据" ✓ |

### ③ 助手 × 安全项目：两个智能体的区别、联系、怎么合作

**本质区别：一个是"人格层"，一个是"技能层"**

| 维度 | 桐莉栖（助手侧 / 人格层） | SecAgent（安全侧 / 技能层） |
|---|---|---|
| 目标 | 让人愿意看、看得懂、愿意回来 ✓ | 发现、研判、取证、处置 ✗ 不负责好懂 ✓ |
| 有无性格 | 有（语气、口癖、情绪 ✓） | 没有（结构化输出 ✓） |
| 权限 | **只读** ✓（现状 `publicDemo=true` + `toolExecutionAllowed=false` ✓） | 大（写库、封 IP、动容器 ✓） |
| 输入 | 自然语言（网页/语音 ✓） | 日志、流量、告警、威胁情报 ✓ |
| 输出 | 台词 + 字幕 + 动作 + 情绪 ✓ | 结论、证据、处置建议、审计记录 ✓ |
| 出错代价 | 出戏 ✗ | 误封 / 漏报 ✗✗（严重 ✓） |

**它们现在就已经在合作了**（只是很浅 ✓）：
```
她读 `/api/public/*`（alerts / latest / overview / honeypot / geo / webstats / stories）→ 把安全的结论"翻译成人话" ✓
⇒ 这就是"**人格层只读技能层的结论**"这一条边界的实现 ✓（刻意的 ✓ 不是偷懒 ✓）
```

**我建议的三层协作模型**（`[建议]`，逐层可独立上线 ✓）：

```
第一层｜只读展示（现在 ✓ 已完成）
   她 → GET /api/public/*（白名单、限速、配额池 public-demo 30 次 ✓）
   价值：数据真实、权限零风险 ✓

第二层｜决策层（T14，1~2 天 ✓）
   她 ← POST /api/public/decide（输入=告警摘要，输出=情绪/动作/台词 ✓ 见 ② 的 JSON）
   价值：让她"看情况反应" ✓ —— 这是"像活人"的关键一步 ✓
   边界：输入只读、输出只影响**表现层**（不影响安全系统 ✗）

第三层｜提议层（远期，可选 ✓）
   POST /api/public/propose：她可以生成"建议动作"（例如"建议临时封禁 45.155.x.x"）
   但：**只能提议、不能执行** ✗ —— 提议进入安全侧的既有审批/剧本流程，由人/规则批准后才由 SecAgent 执行 ✓
   全程留审计（谁提议、谁批准、执行了什么 ✓）
   价值：从"会念报告的助手"升级为"能参与运营的同事" ✓（但要先把审批链做扎实 ✓）
```

**一条铁律（别破 ✗）**：
```
**她的输出永远不进执行链** ✗ —— 人格层可以被提示词注入/被忽悠，技能层不行 ✓
所以：只读 + 建议 + 人工/规则审批，三段分离 ✓
（现在的 `toolExecutionAllowed=false` 就是这条铁律的实现 ✓ 值钱的就是这个边界 ✓）
```

**顺带一个很实用的收益**：这套边界刚好能写成简历/答辩亮点 ✓
"**把 LLM 人格层与安全执行层做了权限隔离，人格层只读+只提议，执行必须过审批**" ✓✓

### ④ 更多动画：造腿 / 全身 / 换装 / 换发型 —— 能做，但代价差别很大

**先说素材现实**：现有角色包是围绕**中景/半身**设计的（基准画幅 764×1028），
动作家族是"待机/侧面/靠窗/听歌/说话/思考/情绪转场"✓，**没有为"整身行走/腿部动作"准备的剪辑** `[待核对]` ✓
⇒ 所以：**腿 / 全身 / 换装 / 换发型都不是"接线"能解决的，必须新产素材** ✗

**四条路，按性价比排**：

| 路线 | 做什么 | 代价 | 风险 | 建议 |
|---|---|---|---|---|
| **1. 先接线已有的** | 38 动作 + 情绪 + 口型 + 视频化全上 | 0 新素材 ✓ 1 天 | 低 | ★ **先做这个** —— 观感立刻从"4 段"变"38 段 + 会看脸色" ✓ |
| **2. SpriteForge 产新动作** | 用官方产线 (`reference→stills→i2v→QA→graph→export`) 生成新表情/动作 | 需要**云 GPU**（推荐 Wan 3.0 CLI；本地 6GB 多半不够 ✗）+ 按次计费 | 中：**角色一致性**要人工筛 ✗ | 值得试：先做 2~3 个动作 pilot ✓ |
| **3. 换装（半身）** | 只换上半身服装，不动腿与镜头 | 素材重做量 ≈ 一次全身动作集 ✗ | 中高：一致性 + 与现有动作衔接 ✗ | 折中可行 ✓（先把"只换半身"当目标 ✓） |
| **4. 造腿 / 全身 / 换发型** | 需要**全套动作重做**（每个动作都要有腿、都要一致 ✗） | 成本最高（几十个剪辑 ✗） | 高：一个不一致就"出戏" ✗ | **最后再考虑** ✗（除非有画师或产线打通 ✓） |

**两个务实的替代（不用新素材也能"看起来更丰富"）** ✓：
```
① **场景/机位变化**：房间已有多个候选背景（空实验室/电脑前/白板前/靠窗…）✓
   她 + 场景组合一下，观感变化比"多一条腿"更明显 ✓（且零新素材 ✓）
② **表情/情绪条 + 小道具**：包里有 8 套情绪头像素材 ✓（已被表情条用上 ✓），再加"小道具/字幕条/CRT 效果"变化 ✓
```

## 六、补充：造腿 / 全身 / 换装 / 换发型 —— 要的是**能力**（产线），不是让谁现在去产 ✗

> 站长澄清：目标是**拥有这种能力**（以后想加动作/换装/换发型都能自己产），不是现在就产出某个素材 ✓

### 6.1 "能力"定义（满足这四条才叫有能力）
```
① 能生成：给定角色参考图 + 动作/服装/发型描述 → 产出可用素材（动作序列或全身帧）
② 能对齐：产出必须自动落到**现有规格**（画幅 764×1028 基准 / 逐帧时长 8·17·21ms / 透明 alpha / 锚点一致 ✗）
   —— 不对齐就没法进状态机与落位公式，等于白产 ✗
③ 能筛一致性：自动打分筛掉"不像她"的（用现成指标：与定妆集的相似度、关键点/锚点对齐、alpha 边缘 NCC ✓）
④ 能入库：一条命令把新剪辑注册进 statemachine.json（节点 + 概率边 + 情绪/台词绑定）并打包 ✓
```

### 6.2 能力建设路线（三段，每段可独立验收）
```
段一｜打通"能生成"（0.5~1 天评估 + 1 天 pilot）
  · 生成服务：SpriteForge（官方产线 ✓，推荐 Wan 3.0 CLI）或本地 ComfyUI（作者计划支持 ✓）
  · 硬件现实：本地 6GB 显存多半不够 ✗ ⇒ 用**按小时租的云 GPU**（先算成本再决定 ✓）
  · pilot：只做 **2 个新动作**（例如"喝咖啡""站起来"）验证全流程，不做全身 ✗

段二｜打通"能对齐 + 能筛"（1~2 天，**这才是能力的核心** ✗）
  · 写两个脚本（可复用 ✓）：
      a) `tools/asset-align.py`：任意生成结果 → 裁切/缩放/补透明边 → 对齐到 764×1028 与既有锚点，
         逐帧时长按目标剪辑规格写入，输出可直接进图集/视频管线 ✓
      b) `tools/asset-consistency.py`：与"角色定妆集"（多角度参考图）做相似度 + 边缘 NCC + 关键点距离，
         低于阈值直接判不合格 ✓（阈值先用现有素材互测标定出来，别拍脑袋 ✗）
  · 建立**角色定妆集**：从现有 38 个剪辑里抽 12~20 帧代表性定妆图（正/侧/情绪/服装）作为一致性基准 ✓

段三｜打通"能入库"（0.5 天）
  · 扩展 `_dev/build_statemachine_manifest.py`：支持"新剪辑登记表"（名称/帧数/时长/情绪/可触发方式）
     → 自动生成节点与边（含 host_triggered 入口 ✓）→ 重新生成 statemachine.json + manifest ✓
  · 写 SOP 一页：**"新增一个动作 / 一套服装 / 一个发型"的完整步骤**（从描述到上线 ≤ 半天 ✓）
```

### 6.3 能力分级（诚实版：哪些能立刻有，哪些要额外投入）

| 能力 | 需要什么 | 可行性 | 备注 |
|---|---|---|---|
| **新表情 / 新动作（半身）** | SpriteForge + 云 GPU + 段二脚本 | ✅ 可达 | 现有画幅内，一致性最好控 ✓ |
| **半身换装** | 同上 + 少量人工筛 | ✅ 可达（较慢） | 每套服装 = 一整套动作重产 ✗ |
| **全身 / 腿** | 更多定妆参考 + 更长序列生成 + 大量一致性筛 | 🟡 困难但可试 | 6GB 本地基本不可能 ✗；云 GPU 成本按次累加 |
| **换发型** | 同全身，且发丝边缘 alpha 极难稳 | 🟡 最难 | 建议最后做 ✗ |
| **整段行走/跑动** | 视频生成长序列 + 镜头语言重做 | ❌ 不建议 | 与现有 CRT 机位冲突 ✗，收益低 ✗ |

### 6.4 成本与约束（先算账再动手）
```
· 云 GPU 按小时租（生成类任务）：先跑 1 小时 pilot 实测"每个动作多少分钟、多少钱"，再定规模 ✓
· 一致性失败率会直接乘成本（生成 3 个过 1 个 = 3 倍价钱 ✗）⇒ 所以段二脚本必须先于规模化 ✓
· 授权：素材包声明为**非商业技术学习/研究/演示** ✓ ⇒ 由它派生的新素材同受约束 ✗；商用需另议 ✓
· 存储：新素材进 `static/kurisu/` 会顶 80MiB 门禁 ✗ ⇒ 走"接线后删旧档"的 T9 顺序 ✓
```
