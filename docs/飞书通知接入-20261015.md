## 1. 机制说明（三层，各自职责清楚）

```
┌─ 调用方 ─────────────┐   ┌─ 通知出口 ─────────────┐   ┌─ 中继（唯一持有飞书密钥的地方）──┐   ┌─ 飞书 ─┐
│ 宿主脚本（心跳/容量/  │   │ /opt/secagent/scripts  │   │ secagent-notify-relay.service    │   │ 群机器人│
│ 看门狗）/ 人工        │──▶│ notify.sh              │──▶│ notify-relay.py                  │──▶│ webhook │
│                       │   │ 纯 bash + curl         │   │ 监听 172.20.0.1:8899  POST /notify│   │         │
├───────────────────────┤   │ 不依赖应用存活 ✓        │   │ 读 /opt/secagent/.env 的          │   └─────────┘
│ 应用（容器内）        │──▶│（脚本侧独立出口）       │   │ FEISHU_WEBHOOK_URL 转发           │
│ NotifyController /    │   └───────────────────────┘   │ 按 [高危]/[HIGH]/[严重]/[CRITICAL] │
│ NotificationService   │───────────同一份 .env────────▶│ /[紧急] 判定高危 → 邮件（当前关闭）│
└───────────────────────┘                               └──────────────────────────────────┘
```

| 组件 | 事实（实测/现读） |
|---|---|
| `notify.sh` | 16052 B，`/opt/secagent/scripts/notify.sh`；纯 bash + curl；**全文 0 处提到 `feishu`** ⇒ 它只往中继发 ✓ |
| `secagent-notify-relay.service` | **active**；`ExecStart=/usr/bin/python3 /opt/secagent/scripts/notify-relay.py`；`NOTIFY_RELAY_HOST=172.20.0.1`、`NOTIFY_RELAY_PORT=8899`（只绑 docker 网桥网关，**不对外**） |
| 指令入口 | `POST /notify`（也兼容 `/`）；body `{"text":"…"}` 或飞书形状 |
| 出口判定 | `send_feishu()` **只有在飞书 API 返回 `code==0`（且 `StatusCode==0`）时**才返回 `sent`，否则 `failed` + 对端响应片段（≤160 字符）|
| 密钥位置 | **只有** `/opt/secagent/.env`（`mode 600 root`）里的 `FEISHU_WEBHOOK_URL`；中继只把它读进内存发请求，**从不打印值** ✓ |
| 应用侧管理面 | `/api/notify/**` 不在白名单 ⇒ 必须带 `X-API-Token`；只暴露 `/watchdog-rollback`（POST，看门狗回滚专用）、`/state`、`/ping` —— **没有"发任意消息"的入口**，所以人工通知走 `notify.sh` 是正解 ✓ |

> `NOTIFY_WEBHOOK_URL`（脚本看的那个键）在 srv1 上**不是飞书地址**，而是**中继自己的内网地址**（长度 29 字符，形如 `http://172.20.0.1:8899/notify`）。
> 这是 2026-10-13 那次的修复：`.env` 值里带 `{` 会让 docker compose 读 env_file 失败，所以把"JSON 形状/双通道/分级路由/冷却"全部搬到中继里 ✓。

## 2. ⚠ 审计归属纠偏（**手工发送不写 `notify-audit.jsonl`**）

站主原以为"发一条 → `notify-audit.jsonl` 里就该有新条目"。**实测不是**，三个文件各有写手：

| 文件 | 谁写 | 记什么 | 手工 `notify.sh` 发送会写吗 |
|---|---|---|---|
| `/opt/secagent/logs/notify.log` | **notify.sh** | 每次调用的结论（已发送 / 被压制 / 未配置 / 失败 + 原因） | ✅ **会**（本次两条都在） |
| `/var/log/secagent-notify.log` + `journalctl -u secagent-notify-relay` | **中继** | `seq=N high=? feishu=sent\|failed mail=?` | ✅ **会**（真实飞书回执） |
| `/opt/secagent/data/notify-audit.jsonl` | **应用**（`NotificationAudit.java`） | 应用侧事件（`HIGH_ALERT` 等）的 `outcome=SENT/MERGED/SUPPRESSED/FAILED` | ❌ **不会** |

**实测铁证（发送前后对比）**：

```
BEFORE 23:35:49  audit_lines=9156  audit_mtime=2026-10-15 23:35:06  log_lines=46
SEND   23:35:50  notify_exit=0     stdout=已发送（HTTP 200）
AFTER  23:35:50  audit_lines=9156  audit_mtime=2026-10-15 23:35:06 ← 行数与 mtime 都没变 ✗
                 log_lines=47     ← notify.log 多了一行 ✓
```

`notify-audit.jsonl` 末条仍是真实高危告警（脱敏）：

```json
{"time":"2026-10-15 23:35:06","eventType":"HIGH_ALERT","severity":"HIGH","actor":"system",
 "dedupKey":"alert:1792078459.269114433","targetIpMasked":"168.144.28.x",
 "title":"[高危] 蜜罐: 攻击者\"登录成功\" 用户=david 口令=[口令已隐藏] 来源=168.144.28.x",
 "outcome":"MERGED","reason":"并入已发出的聚合窗口（累计 2327 次，不再重复推送）","attempts":0}
```

⇒ **结论**：要证明"我这条测试发出去没有"，看 **`notify.log` + 中继日志**；
`notify-audit.jsonl` 是**应用事件**的账本（事件类型 `HIGH_ALERT`、`dedupKey=alert:…`），手艺通知不会进它 ✓。
（本文件也**不**建议为了"让审计里有记录"去调应用的 `/watchdog-rollback` —— 那会往站主手机发一条**假的高危回滚告警** ✗。）

## 3. 正确调用契约（读自 `notify.sh --help` ＋ 第 72–101 行参数解析）

```
notify.sh <级别> <标题> [正文] [选项]
```

| 位置 | 必填 | 说明 |
|---|---|---|
| `<级别>` | **必填** | `CRITICAL` \| `HIGH` \| `MEDIUM` \| `LOW` \| `INFO`（**大小写不敏感**） |
| `<标题>` | **必填** | 短标题（手机推送里第一行） |
| `<正文>` | 选填 | 省略时自动填 `（无正文）`；**只能有一个位置参数**，多了直接退出 2 |

| 选项 | 默认 | 说明 |
|---|---|---|
| `--force` | 关 | **越过冷却、夜间静默、最低级别**（手工推送/演练用）← 本文件的一行命令靠它 |
| `--key K` | `md5(级别+标题)` | 冷却键；同键在冷却窗口内不重复发 |
| `--cooldown N` | 600 | 本次调用的冷却秒数（覆盖配置） |
| `--dry-run` | 关 | 只打印将发送的载荷，**不发送**（验证用，零副作用） |
| `--config F` | 自动探测 | 指定配置文件（`NOTIFY_ENV_FILE` → `/opt/secagent/.env` → `/etc/secagent/notify.env` → `/opt/secagent/notify.env`） |
| `--help` / `-h` | — | 打印用法（由脚本头部注释生成） |

**退出码（本脚本的核心设计："没发出去"必须能被区分）**：

| 码 | 含义 | 是不是"发出去了" |
|---|---|---|
| 0 | 已发送（或 `--dry-run` 成功） | ✅ 是 |
| 2 | 用法/配置错误（多余参数、未知模板变量、渲染后非法 JSON） | ❌ 否（fail-closed） |
| 3 | `NOTIFY_WEBHOOK_URL` 未配置 | ❌ 否 |
| 4 | 冷却中跳过 | ❌ 否 |
| 5 | 发送失败（curl 非 2xx / 超时 / 连不上） | ❌ 否 |
| 6 | 级别低于最低级别，**或被夜间静默压到阈值以下** | ❌ 否 |

> ⚠ **"没发出去"时不打 stdout**，只写日志 —— 所以命令行看起来"无输出"很可能是被压制了（站主原现象即此）✓。

### 6.3 「真的到达飞书」的判据（为什么 `feishu=sent` 可信）

`notify-relay.py` 的 `send_feishu()`：

```python
with urllib.request.urlopen(req, timeout=12) as resp:   # POST 到 FEISHU_WEBHOOK_URL
    raw = resp.read().decode("utf-8", "replace")
j = json.loads(raw) if … else {}
if j.get("code") in (0, None) and j.get("StatusCode", 0) == 0:
    return "sent", ""                                   # ← 只有飞书 API 回 code=0 才算 sent
return "failed", raw[:160]
```

⇒ `feishu=sent` 是**飞书服务端受理回执**，不是"我们试着发了" ✓；失败会写 `feishu=failed` 并带对端响应片段。

## 7. 失败排查表

| 现象 | 退出码 | 原因 | 处置 |
|---|---|---|---|
| stdout 空、日志写「按阈值压制」 | **6** | 夜间静默 high-only（22:00–07:00 压 INFO/LOW/MEDIUM）或低于最低级别 | 加 `--force`，或改用 `HIGH` |
| 日志「冷却中（键=… 还剩 Ns）」 | 4 | 同键默认 600s 内重复 | 换 `--key`，或加 `--force` |

## 10. 残余与边界（写清楚，别只写好的一面）

- **srv2 未做端到端验证**：`/opt/secagent/scripts/notify.sh` 在 srv2 存在（16052 B），但 srv2 上 **没有 notify-relay 服务**（`inactive`），
  也没有 `NOTIFY_SERVER_MIN_SEVERITY` / `NOTIFY_NIGHT_QUIET` 键 ⇒ srv2 的出口口径与 srv1 **不同**，本次未验证、**不声称可用** ✗。
