## 3. A / B / C 三类判定（每条带理由 + 数据源）

判定维度：① 是否泄露内部信息 ② 是否可被滥用 ③ 是否有叙事价值 ④ 隐私与合规 ⑤ 维护成本

### A 类 · 适合现在展示（无需后端改动）

| # | 能力 | 数据源 | 叙事价值 | 合规 | 维护 | 判定理由 |
|---|---|---|---|---|---|---|
| A1 | **处置成果 · 封禁榜** | `/audit`→`summary`+`blocks[]` | 高（"不只看，还会动手"） | 需脱敏 IP（B 规则） | 无 | 全部字段都是"我们做的动作"，不是攻击者隐私；且 `readOnly:true` 明确 |
| A2 | **攻击故事线**（候选池 + 单源时间线） | `/stories` + `/story?src=` | **最高**（一次攻击全过程） | 需脱敏 `srcIp` 与 `summary` 里的 IP | 无 | `stages/gaps/coverage` 天生带"没接入 vs 没发生"的区分 ✓ 诚实 |
| A3 | **知识库检索** | `/kb?q=` | 高（对访客有实用价值、利于传播） | 白名单内 ✓ 零 IP | 无（结果自带 `available/rule`） | 后端已做白名单 + 来源类型 + 内部黑名单三道口子 ✓ |

| A6 | 检测能力自评（覆盖了哪些手法） | `/alerts`→`stats.byType` + `/overview`→`bySource` | 中 | ✓ | 无 | 类型标签由服务端给，前端不编 ATT&CK 映射 ✓ |

## 8. 顺带任务：GitHub Discussion #27 摘要（作者在说什么 / 对我们有没有用）

**抓取情况**：本机 `web_fetch` 返回的是 GitHub 外壳（正文被截断）✗ ⇒ 改从 **srv1** 用 `curl` 抓全文再解析，**抓到了** ✓
标题：`Browser Provider scope: Playwright interaction vs lightweight Web research · Code-Amadeus · Discussion #27`
链接：<https://github.com/Code-Amadeus/Amadeus/discussions/27> （注意：原 URL `github.com/Code-Amadeus/...` 会 302 到 `github.com/orgs/Code-Amadeus/discussions/27`）

**Milchstrasse（2026-08-31，用户）在说什么**：
系统测了内置 Browser Provider，目标是让 Main Chat 直接做轻量 Web research（查天气、搜 GPT-SoVITS 最新信息并给多来源）。结论是 Playwright / Chromium / `browser.open(url)` 本身正常，但连用会遇到**偏 research / agent 层**的问题：
① 无 URL 的 Web research 被降级成 `open` ⇒ `missing_open_target`；② 已有 live browser session 会让新 query 被当成"当前页面的延续"；
③ 第一个 search candidate 导航失败 ⇒ 整个任务直接结束；④ consent / translation / Wikipedia 这类页面被误判成"有效 research evidence"；
⑤ 旧的页面/任务上下文被带进一个新的独立 research request。
他本地已对 request normalization / structured query / candidate fallback / evidence relevance 做了实验性修复 + 回归测试，并说愿意整理成 Issues / focused PRs。

**Lucas1479（Maintainer）回复要点**：
① 设计 Browser Provider 时**没打算**把它做成 research-heavy Agent；做 Kurisu 角色与执行解耦时发现外部 Agent 的问题——浏览器与 DOM 上下文都在 Agent 那边，Main Chat 只能拿到一段摘要，难解释页面细节、难做精细多轮交互。
② 所以要 `Active Browser Interaction Branch`：DOM/页面文本/interaction refs/操作过程放**短期 branch**，Host 拿 URL、截图、执行结果这些**可验证证据**；Main Chat 保留角色与对话上下文，又不把 DOM 和工具日志塞进长期对话。
③ 用户报的 case 正好打中边界：Host routing / request normalization / Main Chat prompt 都可能把"无明确 URL、意图模糊"的 Web 请求错误路由到 Browser，也可能把旧页面上下文带进新请求。
④ 更麻烦的是**意图会在交互过程中漂移**（从"站内搜一下"变成"找多来源并综合比较"）⇒ 应识别"任务已从 page interaction 变成 research"并**重新路由**。
⑤ 倾向路线：**Browser 收敛成更底层、边界更窄的页面执行能力**（只在明确 URL、当前页观察、站内搜索、click/fill/back、截图这类轻量场景调用）；靠 Host 侧 request normalization、branch retarget、Main Chat prompt 避免旧 session 干扰新请求。
⑥ **开放式搜索、多来源比较、最新信息这类 research 交给有调查与规划能力的第三方 Agent**（更慢，但更适合查询规划、候选重试、来源判断、综合整理）。
⑦ 轻量 Browser task 怎么定义、这套路由能否稳定，还需要不同表达方式/语言/session 状态/任务切换的对照实验；欢迎继续提方案，也欢迎把 trace、本地修改、回归测试、实验数据整理成单独 Issues 或 focused PRs。

**对我们有没有用**：
```
· 直接可用：**没有** —— 我们博客侧不走 Browser Provider（AI 问答是服务端 RAG + 只读数据端点，浏览器只发 fetch，
  不驱动 DOM、不做联网 research）✗ ⇒ 这条讨论里的 bug 与修复不落在我们的链路里。
· 方法论可用（值得抄的三条）：
  ① "意图漂移要重新路由" —— 对应我们"公开面只解释概念与防御 vs 内部面读事件数据"的分层：
     用户问着问着滑向"我们被谁打了"，必须识别并重新路由到拒答，而不是继续在公开知识库里硬答 ✓
     （我们的 PublicOutputGuard / state=input-insufficient 已经是这个思路 ✓）
  ② "短期 branch + 只把可验证证据交回主线" —— 对应我们"处置动作的留痕（auditId/actions）才是证据，
     模型的自述不算证据" ✓ 与 §4.1 展示 `auditId` 的设计同源。
  ③ "边界要用对照实验定义" —— 对应我们 R3/U6 这类"文案承诺了接口、实现却是本地演示"的问题：
     边界模糊处必须实测，不靠描述 ✓
· 一条旁证：maintainer 提到"做 Kurisu 角色与执行解耦"——与我们用 Amadeus/Kurisu 素材 + 自己后端解耦的做法同源，
  说明"角色层不承担执行"是被上游认可的架构 ✓（对应我们 `docs/amadeus-research/HOW-IT-WORKS.md`）
```
