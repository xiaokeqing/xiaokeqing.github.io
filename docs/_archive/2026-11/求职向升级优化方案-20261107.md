> 定位：在既有 `升级蓝图-20261107.md` §10 的基础上，**从"求职面试官第一眼"这个视角**，重新诊断 + 重新排优先级的一份可落地方案。

## 0. 结论先行（30 秒版）

这个项目**工程底子已经非常硬**：双机采集、只读 API、护栏 + 真实防火墙落盘、721 个单测、90 项发布断言、降噪/脱敏/限流/审计都做齐了。技术上不输大部分一线安全团队的内部工具。

但**求职场景下，面试官/HR 不会读你的代码，只看 3 样东西**：

1. 打开 `xiaokeqing.cn` 的前 10 秒，**排版专不专业、数据一不一样看懂**；
2. 点进几个页面，**"每个数字能不能下钻到原始日志"这个承诺是否一眼可见**；
3. README 上那几行**量化数字准不准**（面试官会随手点链接验证）。

当前最大风险不是"功能不够"，而是：

| # | 短板 | 证据（我实际读到的） | 求职后果 |
|---|---|---|---|
| 1 | **视觉语言碎片化** | `xk.css` 有 `--txt/--acc` 设计令牌，但 `/more/` 硬编码 `#eef3f6/#7fd3e3`、`/daily/` 硬编码 `rgba(255,255,255,.x)/#cfe9f5`、`/ip/` 又是一套 `#eaf6ff`——三套色板三套圆角共存 | 页面间像"三个不同人做的"，第一印象打折 |
| 2 | **数据页零可视化** | 全站只有数字 + 表格，无地理热力/时序热力/分级环/攻击链时间线（蓝图 V1–V5 全没做） | "安全观测站"却没有一张图，冲击力不足 |
| 3 | **数字卡不统一** | `.mr-card / .dy-grid>div / .ipp-card / .dy-num` 四套卡各自为政，值/口径/下钻箭头没有统一组件 | 下钻承诺看不到，"凭什么信"打折扣 |
| 4 | **后端结构性债** | `PublicApiController.java` 2907 行 god object；`AlertBoardController` 与公开接口告警逻辑重复；`dto` 包只有 3 个类，契约靠手写 `OpenApiSpec.java` | 面试问"你怎么组织后端"时答不出清爽架构 |
| 5 | **README 数字漂移** | README 写"16 端点 / 42 断言"，实际已是 **20 端点 / 90 断言** | 面试官交叉验证发现对不上 = 直接扣分 |

**结论**：功能已经很满，现在要补的是**"一眼专业"** 和 **"可被验证"**，而不是再堆功能。

## 1. 三大重点逐条诊断与方案

### 1.1 网页排版布局（重点一）

#### 现状问题（具体到文件）

1. **设计令牌没有成为唯一事实源**。`assets/css/xk.css` 第 2–15 行已经定义了 `--txt/--mut/--acc/--ok/--warn/--bad/--mono/--sans/--r`，但各数据页没引用，而是自带一份 `<style>` 硬编码：
   - `/more/` → `#eef3f6`、`#7fd3e3`、`#9fb0ba`、圆角 `14px`；
   - `/daily/` → `rgba(255,255,255,.8)`、`#cfe9f5`、`#bfe3d0`、圆角 `7/9px`；
   - `/ip/` → `#eaf6ff`、`#cfe9f5`、`#E8837B`、圆角 `7/8/9px`。
   同一种"正文色"被写成三种不同值。改一次主题 = 翻 15 个文件。

2. **容器宽度三种口径**。`.main` 用固定 `padding:22px 344px 64px 88px` + `max-width:1520px`；`/more/` 用 `max-width:1180px` 居中；`/daily/`、`/ip/` 走 `.screen` 全宽。三个数据页内容区横向对不齐，1024px 下尤其明显。

3. **数据页被二次元面板挤占**。右侧 284px holo 面板 + 左侧 dock 在 `/alerts/`、`/daily/`、`/ip/` 这些**数据页**上常驻，吃掉大量横向空间。数据页需要的是"一眼读完"，不是角色互动。

4. **卡片四套、无统一结构**。`.mr-card`（more）、`.dy-grid>div`（daily）、`.ipp-card`（ip）、`.dy-num`（daily hero）各自定义标题/数值/描述的位置与字号，字段含义（值、标签、口径、下钻）不统一。

#### 方案（按 ROI 排序）

| 优先级 | 动作 | 落到哪里 | 效果 |
|---|---|---|---|
| ★★★ | **补 `tokens.css` 并让全站唯一引用** | 新建 `assets/css/tokens.css`，把 `xk.css` 的 `:root` 令牌抽出来，追加：间距 8pt 阶（4/8/12/16/24/32/48/64）、字号四阶、容器三档（760/1180/1400）、圆角四档（6/8/12/16） | 一次定义，全站改主题只动一处 |
| ★★★ | **数据页收拢到统一容器** | `.main` 从固定 padding 改为 `--dock-w` + `--rail-w` 两个变量驱动的流体布局；数据页（alerts/daily/ip/passwords/noise）统一 `max-width:1180px` | 三档屏下内容区对齐，无横向溢出 |
| ★★☆ | **数据页隐藏/折叠 holo 面板** | 给 `body[data-xk-ssr="daily|monitor|ip|..."]` 加规则，默认收起右侧 holo，只留小气泡 | 数据页横向空间 +40%，更像专业 SOC |
| ★★☆ | **统一卡片组件** | 抽 `partials/xk-demo/card.html`（值/标签/口径/下钻箭头四要素），各页改用它 | 数字可下钻的"承诺"在每个卡上可见 |
| ★☆☆ | **三态组件** | `partials/xk-demo/state.html`：loading 骨架 / empty / error（原因+重试），替换各页手写的"读取中…/未取到" | 加载态一致、错误态可重试 |

> 验收锚点（沿用蓝图 10.6）：`grep -rn "padding-left: 120px" assets/` 为空；`grep -rn "rgba(255,255,255" layouts/` 只剩 `tokens.css` 一处；1440/1024/390 三档 `_layout.py` 输出 `overflow=[]`。

### 1.2 后端数据的更好显示（重点二）

#### 现状问题

1. **零图表**。全站数据展示 = 数字 + 表格，蓝图 V1–V5 的图表方案全未落地。安全观测站的核心卖点（攻击从哪来、什么手法、多猛）目前只能靠读数字脑补。
2. **数字卡不统一**（见 1.1）。
3. **表格缺增强**：桌面端无 sticky 表头；`min-width:760px/520px` 靠横向滚；无排序/筛选/分页。
4. **"实时攻击流"是文字 ticker**，不是可视化流。
5. **手写 `innerHTML` + `esc()` 拼接**，字段漏转义即 XSS，且 149KB 的 `xk-bind.js` 承载了本可组件化的事。

#### 方案（硬约束：不引 ECharts/Chart.js，首页 1MB 预算顶不住）

| 优先级 | 动作 | 技术路线 | 视觉冲击 |
|---|---|---|---|
| ★★★ | **24h 时序热力（V2）** | 24 格纯 CSS grid，悬停给该小时 top 规则；无数据小时显示 `—` 不显示 0 | 低，但补齐"时序"叙事 |
| ★★★ | **分级环 + 噪音漏斗（V3）** | 纯 CSS `conic-gradient` 画分级占比环；漏斗用几个渐变矩形 | 中，一眼看严重度分布 |
| ★★☆ | **攻击地理热力（V1）** | 40KB 简化世界轮廓 + Canvas 双层脉冲点，国家质心表内置；`prefers-reduced-motion` 退静态 | 高，最像"安全大屏"的一张图 |
| ★★☆ | **攻击链时间线（V5）** | 单 IP：首次出现→尝试→结果→被封，垂直时间线 + 原始日志片段 | 高，直接兑现"可下钻"承诺 |
| ★★☆ | **统一数字卡（V6）** | 值/标签/一句口径/下钻箭头四要素，全站复用 | 中，统一感 |
| ★☆☆ | **表格增强** | `thead th{position:sticky;top:0}`、首列 sticky；数值列可排序（前端本地）；超大表虚拟滚动 | 中，可读性 |

> 关键点：**先把 V2+V3 这种"纯 CSS、0 依赖、半天能出"的做了**，立刻让 `/alerts/` 和 `/daily/` 从"表格"变"大屏"。V1/V5 留到第二批，因为要画图和连数据。

### 1.3 后端功能优化（重点三）

#### 现状问题（具体到文件）

1. **God controller**：`PublicApiController.java` 2907 行（160KB），一个类扛 20 个公开端点 + 全部业务编排。
2. **逻辑重复**：`AlertBoardController /api/alerts/*` 与 `PublicApiController /api/public/alerts` 两套告警聚合并存，改一处漏一处。
3. **契约靠手写**：`dto` 包只有 `AIOpsRequest / DocumentChunk / FileUploadRes` 3 个类；`data` 多为 `Map<String,Object>`；`OpenApiSpec.java`（481 行）手写维护，与真实端点存在漂移风险。
4. **响应无统一分页/错误码枚举**：`{code,message,data}` 有外壳但无分页信封、无 `ErrorCode` 枚举。
5. **能力缺口**（蓝图 B2–B8）：无 SSE 实时流、无 MTTD/MTTR、无事件归并 Case、无 IP 情报富化、无取证包导出、无公开 API 分级 token。
6. **无可观测性**：只有 `/api/health`，无 Micrometer/Prometheus 指标。

#### 方案

| 优先级 | 动作 | 具体做法 | 求职价值 |
|---|---|---|---|
| ★★★ | **拆分 god controller** | `PublicApiController` 按域拆成 `AlertPublicController / GeoPublicController / IpPublicController / DailyPublicController / StoryPublicController / TtsPublicController`，编排逻辑下沉到已有 Service | 面试问"架构"时能讲出"按域拆分 + Service 编排" |
| ★★★ | **合并重复告警逻辑** | `AlertBoardController` 与公开告警共用同一个 `PublicAlertSource` / 聚合器，只留两种视图（登录全量 / 匿名脱敏） | 消除"改一处漏一处"的隐患 |
| ★★☆ | **DTO + 分页信封 + 错误码枚举** | 把高频端点（alerts/geo/honeypot/ip/daily）的 `data` 固化成 DTO；统一 `Page<T>` 信封；`ApiError` 枚举 | 契约清晰，顺带解决 OpenApiSpec 漂移 |
| ★★☆ | **OpenAPI 自动生成** | 引入 `springdoc-openapi-starter-webmvc-ui`，从注解生成 `/v3/api-docs` + Swagger UI（只读子集暴露，写操作不暴露） | 面试官打开一个 Swagger UI 比看手写清单体面得多 |
| ★★☆ | **MTTD/MTTR（B5）** | 事件三时间戳（发现/处置/恢复）+ 日报趋势中位数 | 安全岗最想听的量化指标，直接写进简历 |
| ★★☆ | **SSE 实时流（B4）** | `GET /api/public/stream`，心跳 15s，按 IP 限流，前端 `EventSource` 断线自恢复 | 补齐"实时"叙事 |
| ★☆☆ | **事件归并 Case（B3）** | 同 IP+手法 30min 合并，时间线可下钻 | 从"散点"到"故事"，面试讲得动人 |
| ★☆☆ | **IP 情报富化（B2）** | AbuseIPDB/VirusTotal 可选 key + 24h 缓存，`by-ip` 增 `reputation` | 有外部情报 = 加分项 |
| ★☆☆ | **取证包导出（B8）** | case → zip（CSV + pcap 片段 + 时间线 PDF） | 安全分析完整闭环 |
| ★☆☆ | **公开 API 分级（B7）** | token 作用域 + 端点级 QPS + 429 计数进面板 | 展现 API 治理意识 |
| ★★☆ | **可观测性** | 引入 `micrometer-registry-prometheus` + `spring-boot-starter-actuator`（只读 /actuator 走内网或独立端口），记录告警吞吐/处置耗时/限流计数 | 运维成熟度一眼可见 |

## 2. 求职呈现优化（额外但最关键）

README 已经写得很好（"面试官 30 秒内能自己验证"），但有几处能再往上提：

1. **修数字漂移**：README 里"16 端点 / 42 断言"→ 更新为"20 端点 / 90 断言"，并加一句"数字由 `assert-build.sh` 自动断言，非手填"。
2. **补一条"黄金演示路径"**（放在 README 顶部，面试官照着点）：
   ```
   打开 xiaokeqing.cn
     → 首页三数字（累计拦截 / 封禁 IP / 蜜罐连接）
     → /alerts/ 作战室（实时攻击流 + 威胁等级 + TOP 来源）
     → 点任一来源 IP → /ip/ 该 IP 档案（命中规则/攻击端点/最近出现）
     → /daily/ 安全日报（24h 告警 + 来源国 Top5 + 语音摘要）
     → /more/ "凭什么信这些数字"（降噪指数 / 弱口令结构 / 攻击样本）
   ```
   每一步都是一个"数字 → 原始日志"的下钻闭环。
3. **加一张"量化成果卡"**（README 顶部 5 行）：
   - 24h 分析告警 **78,130** 条、源 IP 75,127 个；
   - 后端单测 **721** 例 / 0 失败；
   - 发布断言 **90** 项，全过才允许上线；
   - 隔离靶场 **7** 台、可核实小项目 **5** 个；
   - 站上**纯静态 + 只读 API**，无后门。
4. **架构图统一**：README 与 `升级蓝图` 用同一张 ASCII/mermaid 拓扑，避免两处图对不上。
5. **（可选）90 秒演示视频**：录一段 gif/webm 放 README 顶部（首页 CRT → 作战室 → IP 下钻），比任何文字都管用。

## 5. 附录：与蓝图 §10 的差异

- 蓝图把 L1 排在第一批，本方案把 **V2+V3 提到和 L1 同批**（纯 CSS、半天、视觉收益大）。
- 蓝图没提 **README 数字漂移**（16→20 端点、42→90 断言）——这是本方案新增的**最高优先级求职项**。
- 蓝图没提 **数据页折叠 holo 面板** 和 **容器宽度三口径统一**——本方案补充为布局重点。
- 蓝图没提 **springdoc OpenAPI 自动生成** 和 **Micrometer 可观测**——本方案补充为后端结构项。
- 蓝图 B2/B3/B8 是"功能新增"，本方案把它们**降权到批次 3**，因为求职优先级低于"结构清晰 + 可视化 + 数字可验证"。
