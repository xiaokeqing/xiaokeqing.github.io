## 2. ① 证书到期三级告警（srv2，新增 systemd timer，复用现有通知出口）

### 2.1 做法

```
脚本：/opt/secagent/scripts/srv2-cert-expiry-alert.sh（7395 B，755，root:root）—— **只读**证书，只发通知
通知：复用现有 /opt/secagent/scripts/notify.sh（srv2 → 飞书），未新增任何通道 ✓
单元：secagent-cert-expiry.service（oneshot）+ secagent-cert-expiry.timer
      OnCalendar=*-*-* 09:40:00，RandomizedDelaySec=120，Persistent=true
      —— 排在 certbot.timer（约 09:08 + 随机延迟）之后，续期成功的当天就能看到「回落为 OK」
读的两个证书（都只读，不写）：
  主：/etc/letsencrypt/live/xk-site/fullchain.pem     ← LE 源文件
  对：/etc/ssl/secagent/site-fullchain.pem            ← nginx 实际对外用的那份（交叉核对是否同步）
```

**三级阈值与动作**（任务要求 21/7/1）：

| 剩余天数 | 等级 | notify 级别 | 含义 / 建议动作 |
|---|---|---|---|
| > 21 | OK | （不发）/ 回落发 INFO | 正常 |
| ≤ 21 | MEDIUM | MEDIUM | 该准备了：确认 certbot.timer 与 SAN 与 DNS 一致 |
| ≤ 7 | HIGH | HIGH | 要人介入：手动 `certbot renew --cert-name xk-site --dry-run` 看校验 |
| ≤ 1 | CRITICAL | CRITICAL | 当天必过期，立即处理 |
| < 0 / 证书读不到 / 无法解析 | CRITICAL | CRITICAL | 同上（分支已单独测过） |

**降噪**：状态文件 `/var/lib/secagent/cert-expiry.state` 记录「等级 + 日期 + 天数」；
等级**变化**时发，等级**不变**每天最多发 1 条（`--cooldown 86400`）；等级从高**回落**时发 1 条 INFO「已恢复/已续期」。
`--dry-run` 与 `--test N` 都**不写**状态文件（避免演练污染真实状态，已实测前后一致）。

**用法 / 退出码**

```
sudo bash /opt/secagent/scripts/srv2-cert-expiry-alert.sh            # 正常巡检
sudo bash … --status          # 只看状态不发通知（上表数字即来自它）
sudo bash … --dry-run         # 只打印将发的载荷
sudo bash … --test 6          # 演练：假装只剩 6 天，走完整告警链路（标题带【演练】）
退出码：0=正常 1=有告警发出 2=用法/依赖错误；unit 里 SuccessExitStatus=0 1（告警发出也算巡检成功，避免 journal 全是 failed）
```

## 3. ② 站点可用性外部探测（srv1 侧 curl 公网，每 5 分钟）

### 3.1 探测点为什么放 srv1（而不是本机、也不是 srv2）

| 候选探测点 | 结论 | 依据（本轮实测） |
|---|---|---|
| 站主本机（Windows） | ✗ 不可用 | 直连被未备案阻断：`HTTP/1.1 302 OK` + `Location: https://dnspod.qcloud.com/static/webblock.html?d=xiaokeqing.cn`；443 `curl: (35) Recv failure: Connection was reset`（2026-10-15 20:31 实测） |
| srv2（自己探自己） | ✗ 不采用 | 站点进程/隧道挂了，srv2 自己也一起失效，探不出「整机/隧道不可用」 |
| **srv1（另一家云的另一台机器）** | ✅ 采用 | 按真实用户路径走公网域名：DNS→Cloudflare 边缘→隧道 `secagent-static`→srv2 `127.0.0.1:18080`→`/opt/secagent/site`；实测 apex/www 均 200 ✓ |

> ⚠️ 顺带发现（**本轮实测，与旧记录的差异**）：从 **srv1** 直连 srv2 的 80/443 **当前没有被阻断**
> （`curl -H 'Host: xiaokeqing.cn' http://{公网IP-腾讯云}/` → nginx `301`；`--resolve` 到 443 → `200`、33,213 B；对照测试用未备案的假 Host 也是 `301`）。
> 即：阻断只在**站主网络→腾讯云**这条路径上复现，服务器↔服务器之间不复现。所以探测**必须打域名（走 CF）**，
> 若改成打 IP 直连就会「永远 200」，探不出真实访客看到的问题 ✗ —— 这是本探测设计的关键点。

### 3.2 判据（每 5 分钟，两个 URL 各最多 3 次尝试）

```
URL：https://xiaokeqing.cn/  与  https://www.xiaokeqing.cn/
① HTTP 200
② 响应体 ≥ 10000 B（当前实测 33,213 B ✓，留足余量）
③ <title> 含「xiaokeqing」
④ 关键内容特征至少命中 1 个：charCanvas / crt-clip（主页 CRT 场景真渲染出来的标志）
⑤ 总耗时 ≤ 15s（走 CF，本轮实测 1.75~6.55s，故上限给 15s）
判定：单 URL 连续 3 次全失败（约 10s 内）→ 立即发 HIGH 告警；恢复 → 发 INFO
降噪：同一 URL 的 down 告警冷却 1800s（不会 5 分钟刷一次）；状态文件 /var/lib/secagent/site-probe/<url>.state
夜间：srv1 的 notify 配置 NOTIFY_NIGHT_QUIET=22:00-07:00 + MODE=high-only ⇒ 夜间只有 HIGH 及以上能发（本探测是 HIGH ✓ 能发）
```
