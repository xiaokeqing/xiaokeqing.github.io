# 互联网噪音指数（NIS）设计 - 2026-10-18

> **一句话**：NIS 用「剔掉自家心跳与内网后的外源告警量 + 去重源 IP 数 + 蜜罐建连数 + 被敲的诱捕端口数」四个通道，各自做对数饱和归一化后加权成 0–100 分，描述**本平台观测到的**互联网背景噪音强度。
> 只读取现有数据（Suricata `eve.json`、Cowrie 日志、蜜罐端口），不改任何线上配置。计算脚本：`scripts/noise-index.py`。

---

## 1. 要回答的问题（以及不回答什么）

**要回答**：今天/这 24 小时，互联网上那些无人值守的扫描与暴力破解，打到我们身上的"底噪"是平常水平、偏高还是异常？

**不回答**（写清楚，避免被误用）：

- 不是"全网攻击强度"——只反映**打进来的流量**，我们封了谁就看不见谁。
- 不是"攻击严重度"——不含目标资产重要性，不给单个事件定级（公开面严重度仍按既有口径强制 `INFO`）。
- 不跨平台比较——每家的端口、蜜罐配置、封禁策略不同，分数不可横向对比。
- 不参与自动处置——当前纯只读、只展示，不作为封禁/告警触发条件。

**关键事实：`alert` 里 278,405 条（94.9%）是同一个心跳。**

### 2.4 必须剔除的三类

1. **心跳**：`HB_SIGNATURE` + `src 10.0.0.10` + `dst 169.254.0.4:80`（脚本里先判心跳再判内网，否则永远量不出那 94.9%）。

3. **平台自身出口 IP**：同上，按 CIDR 整段剔除，不要只列一个 IP。

## 3. 指标定义

### 3.1 四个通道

| 通道 | 变量 | 定义（24h 窗口） | 取值 |
|---|---|---|---|
| **A** 清洁告警量 | `x_A` | 剔除心跳与内网后的 `alert` 条数 | 条/24h |
| **U** 去重源 IP | `x_U` | 上述告警中 `src_ip` 去重后的个数 | 个/24h |
| **H** 蜜罐建连 | `x_H` | Cowrie `session.connect` 去重数 | 会话/24h |
| **P** 诱捕端口面 | `x_P` | 有命中的诱捕端口个数（上限 = 当前开放数 9） | 个 |

四个通道是**互补**的：A 说"敲了多少下"，U 说"多少人敲"（抗单源刷量），H 说"真进来了多少次"，P 说"门被摸了几扇"（反映扫全端口的机器）。

### 3.2 归一化：对数饱和，不是 min-max

```
s_i = min(1, ln(1 + x_i / x_ref_i) / ln(1 + K)),      K = 10
```

三个理由：

- **抗长尾**：扫描流量跨几个数量级，线性归一会让一个刷屏日把分打到 100 后再也不动；`ln` 让 10 倍变化才明显移动刻度。
- **可解释**：`x_i = x_ref_i` 时 `s = ln2 / ln11 ≈ 0.289`，即**典型日 NIS ≈ 29**；`x_i = 10·x_ref` 时 `s ≈ 1`。
- **不写死上限**：`x_ref` 可随基线更换，分数不会因为"参考值选错"永久贴边。

`K = 10`（而不是 100）的理由：平台单日数据量本来就集中在一个数量级内，`K=100` 会把所有典型日压到 <15 分，失去区分度；`K=10` 让 1×/3×/10× 参考值分别落在 ≈29/≈50/≈100 三个不同档位。

### 3.3 权重

```
NIS = 100 × Σ_i w_i · s_i,        w_A=0.40, w_U=0.25, w_H=0.20, w_P=0.15
```

| 通道 | 权重 | 为什么是这个数 |
|---|---|---|
| A | **0.40** | 最直接、最连续、与我们的配置无关（Suricata 规则一触发就计数）；是"底噪强度"的主载体。 |
| U | **0.25** | 抗刷量：单源 `179.63.84.194` 一天对 1433 打了 2,752 次，A 通道会被它一个人顶爆，而 U 只算 1；同时它是"面有多宽"的分母。 |
| H | **0.20** | 行为最硬（真建连、真尝试登录），但受蜜罐开关与端口配置影响大，故低于 A。 |
| P | **0.15** | 与 U 高度相关（扫全端口的机器通常也是多 IP 群），共线，只能给最低权重；且取值 0–9 离散、饱和快。 |

辅助诊断量（**不入分**）：`multi_port_srcs`（1 分钟内敲 ≥3 端口的源数）、`top_src_share`（单源最大告警占比，>50% 打 `degraded`）、`heartbeat.share`（心跳占比，>0 即需查）。

### 3.4 等级

| NIS | 等级 | 含义 |
|---|---|---|
| 0–20 | 静 | 比典型日低一半以上，先怀疑数据断了 |
| 20–40 | 正常 | 典型日（`x_ref` 附近即 ≈29） |
| 40–60 | 偏高 | 约 2–5 倍典型量，注意观察 |
| 60–80 | 高 | 接近或超过 10 倍，多半是集中扫描/爆破事件 |
| 80–100 | 极异常 | 多通道同时饱和，配合人工核查 |

> 分档先按 p50≈29 手工标定；跑满 30 天后用实测 p50/p90/p99 替换，并把 `REF_DEFAULT` 改为滚动 p50。

## 5. 口径边界（硬约束，违反则指标失效）

1. **心跳必须剔除或单列**：它是 94.9% 的 alert。不剔，NIS 实际测的是"Wazuh 心跳频率"。脚本已单列 `heartbeat.share`，并在占比异常时报 `degraded`；Wazuh 侧（7,283/18,228 ≈ 40%）涉及同一 signature，做 Wazuh 派生指标时同样要剔。
2. **内网与保留地址一律剔除**（含本平台自身出口 CIDR）。`excludedSelf=44,004` 说明这不是洁癖，是必须。
3. **"本平台观测到"是定语，不能省**：封禁/黑洞会让被拦的 IP 不再出现 ⇒ NIS 下降可能只代表"我们封得更狠了"，这是**观测反馈回路**，不是互联网变安静。任何对外表述都要带这个限定。
4. **窗口固定 24h、UTC、左闭右开**：跨时区/跨日对齐会让 A 差几倍；`<20h` 的窗口不出分（标 `degraded`），不做比例外推当正式值。
5. **去重口径写死**：U = 去重 `src_ip`；H = 去重 `session`；P = 命中端口集合大小。同一 IP 多端口多次命中，U 只算 1、P 只算它的端口集合。
6. **单源刷量保护**：A 可能被一个扫描器顶爆（实测 `179.63.84.194` 单源 2,752 次 1433 就是实例）。脚本输出 `top_src_share`，>50% 时 `degraded` 并人工复核，必要时把 A 换成"去重后告警数"或对单源做上限截断（截断会改变口径，须在报告里注明）。
7. **P 的分母必须与端口配置同步**：`DECOY_PORTS` 只有 9 个端口；增删端口要同步改常量并重设 `P_ref`，否则历史分数不可比（P 是"面"，端口变多天然变大）。
8. **数据完整性先于分数**：eve 轮转分片漏读（`eve.json.1` 这类）会让窗口缺行；而公开接口里的 `sampled=800` 是**API 的窗口采样数**、与原始日志无关，别混用。脚本输出 `lines/parsed/bad`，`parsed == 0` 直接退出码 1，不编分数。
9. **时区统一 UTC**：`eve.json` 的 `+0800` 写法由脚本归一化；报告里的时间戳一律带 `+00:00`。
10. **不做因果推断、不做定级、不触发自动处置**：它描述底噪强度，不是攻击判定；公开面严重度口径不变（仍强制 `INFO`）。
11. **参考值会过期**：`REF_DEFAULT` 只是冷启动常量；30 天后必须用实测 p50 覆盖，否则整体分数会随时间漂移（趋势仍可用，绝对值不可比）。
12. **不新增公开端点**：`noise` 不在 `scripts/assert-build.sh:106` 的 `ALLOWED` 里 ⇒ 不要写进公开 API 文档，也不要暴露给前端；当前仅运维侧只读运行。

## 6. 怎么跑

```bash
# 0) 自检（本机没数据也能跑，只验证路径）
python3 scripts/noise-index.py --dry-run

# 1) 昨天晚上到今天（UTC 24h 窗口）
python3 scripts/noise-index.py \
  --eve /opt/suricata/logs/eve.json \
  --cowrie '/opt/cowrie/logs/cowrie.json*' \
  --since 2026-10-17T00:00:00Z --until 2026-10-18T00:00:00Z --explain

# 2) 机读（喂监控/写日志）
python3 scripts/noise-index.py --window-hours 24 --json

# 3) 换参考值（例如用 30 天 p50）
python3 scripts/noise-index.py --ref '{"A":2400,"U":700,"H":13000,"P":6}'
```

不带 python 的一分钟快检（只读，看心跳到底占多少）：

```bash
# 心跳条数 / alert 总数 —— 一行看清 94.9% 是不是还在
echo "hb=$(grep -c 'ET INFO Python-urllib/ Suspicious User Agent' /opt/suricata/logs/eve.json) \
all=$(grep -c '"event_type":"alert"' /opt/suricata/logs/eve.json)"

# 谁在敲、敲哪扇门（去重源 IP + 端口分布）
grep '"event_type":"alert"' /opt/suricata/logs/eve.json \
  | grep -v 'ET INFO Python-urllib' \
  | awk -F'"' '{for(i=1;i<NF;i++){if($i=="src_ip") s=$(i+2); if($i=="dest_port") p=$(i+2)} print s, p}' \
  | sort | uniq -c | sort -rn | head -20
```

（注意：571 MB 文件上 `grep` 全扫约几十秒，别在高频 cron 里跑；正式计算用脚本流式读。）

### 基线标定步骤

1. **冷启动**：先用 §4 的常量跑 7 天，确认分数落在 20–40。
2. **采基线**：连续 30 天，每天存一份 `--json` 输出（只写本地日志，不写线上）。
3. **定参考值**：取 30 天各通道的 **p50** 作为 `x_ref`，写回 `REF_DEFAULT` 并提交（改常量是改代码，不是改线上数据）。
4. **定分档**：用同一批数据的 p50/p90/p99 替换 §3.4 的 20/40/60/80。
5. **盯回归**：`heartbeat.share` 突降 ⇒ agent 挂了；`parsed` 突降 ⇒ 轮转/权限问题；`degraded` 非空 ⇒ 当天分数不可用。

## 7. 已知缺陷与未验证

**缺陷（接受，写进报告）**

- U（去重源 IP）量大时占用内存：脚本用 `set` 存全部源 IP；10 万级无压力，百万级需改 HyperLogLog（未实现）。
- A 通道未做单源截断，只做 `degraded` 提示（截断会改变口径，留待基线期后再定）。
- P 通道信息量偏低（0–9 离散），权重已压到 0.15，但仍可能与 U 共线；30 天数据出来后再看是否合并。
- 轮转：`cowrie.json*` 有分片，脚本会跳过 `.gz`（不引解压依赖）⇒ 跨轮转边界时 H 可能少算。

**未验证（照实写）**

1. **U 的实测值**：本轮没拿到全局去重源 IP 数（只有 `withSourceIp=89,039` 与分国家 `uniqueIps`），§4 的 500 是示意。
2. **心跳剔除规则在真实 eve.json 上的命中率**：假设 5 分钟一条、24h ≈ 288 条/天；而 `alert` 里 278,405 条对应多少天，README 未写清 ⇒ 无法反推"每天实际心跳条数"，也没在真实文件上跑过脚本。
3. **脚本只在构造的 14 行 fixture 上验证过**（心跳剔除、内网剔除、BOM 容忍、session 去重、空数据退出码 1），**没有在 1,471,376 行的真实 `eve.json` 上跑过**——性能与行数统计未验证。
4. **`eve.json` 是否含 `http` 块**：`/ca_report.cgi` 只作为人工识别线索，脚本判心跳用 signature + 五元组，不依赖 URL 字段（避免不同 eve 版本字段缺失导致漏剔）。
5. **等级分档**：20/40/60/80 是按"典型日 ≈29"手工定的，是设计值不是实测分位数。
6. **Wazuh 侧噪音**（18,228 条里 40% 心跳）**未纳入 NIS**：本设计只用 Suricata + Cowrie + 端口，Wazuh 派生指标留作后续，避免通道间重复计数。
7. **`/opt/...` 路径与文件权限**：按文档记录书写，本轮未在生产机上验证可读性（脚本用 `--dry-run` 自检）。
