### 1.2 它怎么加载模型（`psb.mjs` 逐行读到 ✓）

```
folder = `./红莉栖E-mote模型/${name}/`         ← 目录名是硬编码中文
① fetch  <名>.psb.m.json        → 模型树/时间轴/选择器/眼控/眨眼/锚点
② fetch  <名>.psb.m.resx.json   → 资源索引（PsbVersion 必须 = 4）
③ resx.ExtraFlattenArrays       → Float32 → Uint8Array（extra 平坦数组）
   resx.ExtraResources          → fetch  *.psb/extra/@N.bin
④ resx.Resources (PNG 图集)     → createImageBitmap(premultiplyAlpha:"none") → canvas
                                 → getImageData → RGBA Uint8Array
   ★注释原文：「浏览器负责 PNG 解码；不要把现有 PNG 当成原始 BC7 数据上传。」
⑤ prepareModel(model)           → 见 §1.3
⑥ encodePsb(model, resources, extras) → 手写 PSB v4（名表前缀树 + Adler-32）
⑦ new EmotePlayer(canvas).loadData(bytes)
```

### 1.3 为什么需要"内存重编码"（兼容层，也是它的天花板）

`[源码]` `prepareModel()` 把数据从 **E-mote 3.03** 降级/翻译成 **FreeMote WebGL 3.9** 能吃的形式：

- **播放入口**：原版顶层合成入口（`タイムライン構造`）在 3.9 上渲染成**黑色剪影** ⇒ 改用模型自身的
  `object.all_parts.motion.全体構造` ⇒ **顶层合成与图层特效不保证与原版游戏一致** ✗
- **选择器**：3.9 不认 `lower/upper` 区间 ⇒ 表情值被换算成**选项序号**
- **口型**：数据用 `face_mouth` 选部件 + `face_talk` 控开合 ⇒ 丢掉旧的合并 `mouthControl`
- **部件显隐/透明**：`cw` 打包色权 + `mask & 0x80000000` ⇒ 中性 RGB 才能换算成 3.9 的 `opa`；
  **非中性 RGB 直接抛 `error.cwColor`，不做近似** ✗
- **A/B 姿态**：`ab` 源是两套互斥手臂（`arm_type` 0/1），必须**每帧显式驱动** 0..100 的可见性，否则两条袖子一起画
- **眼睛**：总眼控值镜像进 `varL`/`varR`；鼠标视线走**独立差分通道**（否则被表情时间轴覆盖回 0）

⇒ 这就是"能做"与"做得像"的分界线：**它自己承认是兼容预览，不承诺原版特效一致** `[外部声明]`。

### 1.7 与我们现有渲染层的技术落差（定量的）

| 维度 | 现状（六页 + kurisu-player.js）`[已实测]` | E-mote 路线 |
|---|---|---|
| 渲染方式 | canvas 逐帧画**PNG 图集/视频帧**（`ctx.drawImage`），2,239 行 `static/js/kurisu-player.js` | 一套 WASM/WebGL 引擎 + 内存重编 PSB |
| 尺寸基线 | 画幅 **764×1028**，medium 134×180 / hi 2× | `screenSize` **800×1080** + `charaBounds` 自适应 | 
| 动画驱动 | `statemachine.json` 38 节点/92 边 + 宿主触发 9 入口 | E-mote **时间轴槽**（`表情_*` / `slot0~3`）+ 变量表 |
| 口型 | 嘴部补丁层（48 补丁 + 逐帧锚点，A/B NCC ≥0.9928） | **正弦波演示**，无同步 ✗ |
| 引擎/文件 | 纯前端 JS，无外部二进制 | FreeMoteDriver.js 1.26 MB + emoteplayer.js 40 KB（+可能 .wasm） |
| 首屏预算 | 6 页 ≤ 1,689,600 B（门禁硬拦） | 引擎 1.3 MB 单独就顶满一页预算 ✗（必须懒加载） |
| 素材体积 | `static/kurisu` = 82,400,264 B，assert ⑨ 上限 **80 MiB** | 全套 123.29 MiB，单件最大 42.13 MiB ⇒ **必然顶爆** ✗ |
| 移动端 | 有降级判据（`r.height<260` / `pointer:coarse`） | 官方口径"未针对手机优化"✗ |

⇒ `[推断]` **它是"第二套渲染层"，只能并存，不能"接线进去"**。六页现在同时挂着
`kurisu-player.js`（六页）与 `xk-demo/shell-script.html` 内的 demo 播放器（`charCanvas`），
再塞第三套（WebGL）就要处理画布/可见性/降级/dpr 的互斥，成本见 §3。

## 3. 改造成本：三条路线（工时/风险/与现有六页的关系）

**共同前提（三条路线都要付，先记一次）**：

```
P1 vendor 运行时到 `static/emote/runtime/`（两条 CDN script 换本地）+ 带 LICENSE/署名   ≈ 0.5 人日
P2 素材不进仓库（放 _emote-assets/，untracked）+ 打包脚本带入 public/  ≈ 半天（含 zip 解包与校验）
P3 新目录**必须**从 assert ⑨（static/kurisu ≤80 MiB）的统计范围里排除，否则**每次都 FAIL** ✗
   ⇒ 需要改 `scripts/assert-build.sh`（契约改动，得规划侧点头 ✓）
P4 门禁口径：首屏 ≤1,689,600 B ⇒ 引擎 1.3 MB **必须懒加载**（点击后再下），否则新页必超 ✗
P5 流量口径：单访客 25~42 MiB，月红线 150 GB ⇒ 要么接受 ≈5,000 人次/月上限，要么加访问控制
```

### 选项 A｜独立一页（**不动六页、不动 38 节点状态机**）★ 技术上最省

```
做什么：新增一条独立入口（建议 `/emote/`，或 **不进公开站**、只在本机 8000 端口演示）
· 复用 demo 的 psb.mjs / app.mjs / i18n.mjs / index.html（去掉 ?v=7、改相对路径、目录名照旧）
· 站点侧只加：static/emote/runtime/**、static/emote/app/**、static/emote/assets/**（← 打包期生成，untracked）
· 六页的 HTML/JS/状态机/视频**一个字节都不改** ✓
· 门禁：新增页**不进** `_dev/gate-firstscreen.mjs` 的 PAGES 清单（否则预算必爆）；或给该页单列一条"懒加载后"口径
工作量：P1~P5 + 端到端跑通 + 三个模型抽查（半身/全身/换表情/换装）  ≈ **2.5~3.5 人日**
        若**只要"本机能不能跑"的可行性验证**（不接站、不做打包）≈ **0.5~1 人日**
风险：技术低 ✓ ｜ 授权**高**（公开即违规 ✗）｜ 观感：与现有 CRT 场景**风格割裂**（另一套引擎/另一套光照/无 CRT 包裹）
```

### 选项 B｜与六页共存（只做"全身/换装"专区）

```
做什么：保留现有帧播放器为主轨（首屏/日常动作/对话/口型都不变 ✓），
        点"全身 / 换装"时切到 E-mote 轨（一块独立 canvas，仅在专区内可见）
      · 新增：专区路由或面板、两套渲染的共存契约（可见性/reduced-motion/dpr/暂停/销毁）
      · 需要适配：800×1080 + charaBounds 取景 → 现有 CRT 窗口的落位与互淡逻辑
      · 需要同步：切换时把当前情绪/姿态映射到 E-mote 槽（`表情_*` + `arm_type`）
工作量：A 的全部 + 4 项适配与联调 + 视觉一致性打磨  ≈ **4~6 人日**
风险：中（两套引擎同页共存是新的复杂面；`xk-kurisu-stage.html` 已经是双画布，
      再加第三套需要明确"谁在什么时候接管" ✗）
收益：**"换装"是真的**（两套服装 + 三种姿态）✓；"全身"是真的 ✓
代价：**不能新增服装** ✗ —— 再要第三套服装 = 重新找/产素材（回到 T18 的问题）
```

### 选项 C｜全面替换渲染层（**不建议** ✗）

```
做什么：废掉 764×1028 图集/视频 + 38 节点状态机 + 嘴部补丁，改用 E-mote 时间轴槽 + 变量表

 ① 38 节点/92 边状态机与 `frame_size`/`medium|hi.pages[]` 强绑定 ⇒ 全部重做
 ② 口型**退化**：E-mote 路线官方就是正弦波，现有补丁层 NCC ≥0.9928 是实测过的 ✓
 ③ 顶层合成特效不保证一致（黑剪影妥协）⇒ 观感回不去 ✗
 ④ 首屏/移动端/流量三条门禁全线重定（1.3 MB 引擎 + 25~42 MiB 素材）
 ⑤ 已投入的资产（medium/hi/full、40 组透明 WebM、嘴部 48 补丁、视频门禁）沉没
工作量：≈ **15~25 人日**（含全站视觉回归），且**授权问题依旧无解** ✗
结论：**不做** ✗
```
