## 0. 结论摘要（先看这段）

1. **状态机本身能跑，而且没坏**：显式 `smStart()` 后图加载成功（**38 节点 / 92 边**），24 秒走了 **7 步**（`idle → trans_standby → shy_trans → shy_speaking1`），**`errors: []`**，画布 `558×418` 存在。
2. **但产品里现在"打开也跑不起来"**，卡在三处（全部可修，且都是"代码/配置缺"，不是素材缺）：
   - **① 产品里根本没有 `data-xk-kurisu=stage` 挂载点**：50 个产物页面里的挂载点全是 **`rail`**（头像/侧栏轨），而 `smOn` 要求 `mode === 'stage'`（`kurisu-player.js:401-403`）⇒ 即便给挂载点加 `data-xk-kurisu-sm="on"` 也不会跑 SM。
   - **② `manifest.clips` 只有 4 个**：`['idle','opening','speaking','thinking']` ⇒ 公开 `play('<clip>')` **无法驱动 9 条宿主入口与 38 个节点**，实测**每一个都抛** `清单里没有剪辑 xxx`（证据见 §2.3）。
   - **③ `manifest.stateMachine.auto` 只当"关闭"用，不能开启**：`kurisu-player.js:2925` 是 `smOff = (auto === false)`；开启只认挂载点属性。且**没有 URL/配置级一键开关**（只有改生成物 `manifest.json`）⇒ 生产环境缺"能一键关掉"的把手。
3. 素材层面：**7 个房间背景在产物里各被引用 1~2 次但没有任何运行时切换逻辑；`light_high/light_low` 引用 0 次（完全没用）**；38 条 medium 图集（50.5MB）与 6 条 hi（20.6MB）"数据在但几乎没在演"。⇒ 本次施工说明把它们纳入**场景与光照层**（§5）。
4. 站内**没有**"喝咖啡/趴电脑前/站起来"这三条；它们属产线 pilot（§9 给建议）。

## 2. 状态机可运行性（问题 A 的答案）

### 2.1 一次真实游走（原始数据，`_shots/probe-sm-walk.json`）
```
smOn=true  mode=stage  hasCanvasEl=true  graph=true
nodes=38  edges=92  hostEntries=9 条  maxWalkBytes(图内)=6291456
smStart=ok
seqLen=7   edgesWalked=7   visitedCount=4   errors=[]   canvas=558x418
seqOrder = idle, idle, idle, trans_standby, shy_trans, shy_speaking1, shy_speaking1
走过的边（前 7）= idle->idle, idle->idle, idle->trans_standby,
                   trans_standby->shy_trans, shy_trans->shy_speaking1,
                   shy_speaking1->shy_speaking1, shy_speaking1->shy_speaking2
```
**判断**：**状态机可用** —— 图能载、能按边游走、无错误日志、能停住（`currentClip=sm:shy_speaking1`）。
**注意**：24 秒只走 7 步（≈3.4s/步，而 `SM_MIN_HOLD_MS=900`/`SM_MAX_HOLD_MS=2600`）⇒ 差额是**图集懒载**（每步要拉 medium 图集页；`maxWalkBytes` 6MB 闸门就是为这个设的）。**这直接影响"接线后多久能看到第一个动作"** ⇒ 见 §5/§8 的预热建议。

### 2.2 ★硬事实一：产品里没有 `stage` 挂载点
- 产物 `/demo/` 页内实测：`document.querySelectorAll('[data-xk-kurisu]')` ⇒ **count=1, attrs=['rail'], 带 sm=on 的 = 0**。
- 全产物扫描：50 个页面含挂载点，**全部是 `rail`**；那些"匹配到 stage"的命中经核都是 **JS 字符串**（源码里搜 `data-xk-kurisu=.stage` 与 `data-xk-kurisu-sm` 在 `layouts/**`+生成器里 **0 命中**）。
- 而 `smOn` 的硬条件是 `(opts.mode || this.mode) === 'stage'`（`:401-403`）⇒ **rail 挂载点永远不满足**。
**⇒ 结论："打开状态机"这件事今天不只是"加个属性"，而是"产品里没有它的宿主"**（stage = 全身舞台；现网用 rail = 头像轨 + 视频模式 CRT）。这是**代码/结构缺**，不是素材缺。

### 2.3 ★硬事实二：公开 `play()` 只能播 4 个 clip（实测逐个报错）
`manifest.clips = ['idle','opening','speaking','thinking']`（`clipsMedium`/`hiClips` 是**统计与档位**，不是可按名播放的清单）。
实测（`_shots/probe-sm-walk.json` → `control[]`）：

| 调用 | 结果 |
|---|---|
| `play('idle')` / `play('thinking')` | ✅ 返回几何描述（`{clip,frames,columns,fw,fh,interval,tier,fit,once}`） |
| **9 条宿主入口**（`angry_trans`/`closed_eye_trans`/`sad_trans`/`shy_trans`/`speaking_short`/`speaking_trans`/`surprise_trans`/`thinking_trans`/`trans_smile`） | ❌ **全部** `Error: 清单里没有剪辑 xxx` |
| `play('sad')` / `play('smile')`（`clips_not_in_graph`） | ❌ 同上 |
| 生活片段 `idle2`/`idle_mic_wind`/`idle_side_butterfly`/`idle_side_wind`/`idle_str_wind`/`idle_closed_eye`/`trans_standby` | ❌ 同上 |
| `setEmotion('angry')` | ⚠️ 返回 `null`（**stage 模式下是空操作**；它按注释是"头像模式；8 情绪"） |
| `speak('greet_back')` | ✅ `{ok:true, source:'bank-synth', url:'/kurisu/voice/greet_back.m4a', envelopeValues:453}` |
| `smDiag()` | ✅ 返回 `{seed:805579800, durationMs:24000, hostTriggerEveryMs:3000, …}` |
| `instances()` | 1（我自己的实例；用 `create()` 不会进产品的 `mounts`，与产品行为无关） |
| `intro()` | ⚠️ `{played:false, reason:'no-intro-canvas'}`（开场序列需要 CRT intro 画布，只在主页出现） |

**⇒ 结论**：38 个节点的图集**在磁盘上、在 `statemachine.json` 里有几何**，但**不在 `manifest.clips` 里** ⇒ 任何"事件 → `play('shy_trans')`"的接线**今天都会抛错**。
**两条修法**（择一，建议 ①）：
- ① **让生成器把图里节点的 clip 也写进 `manifest.clips`**（`_dev/build_statemachine_manifest.py` 已经逐节点补了几何，补 `clips` 条目是顺手的）⇒ 公开 `play()` 即可驱动全部 38 个；
- ② 给播放器加一个**按图节点播放**的入口（如 `playNode(clip)`），内部走 `graphByClip` + 图集几何，不动 `manifest.clips`。

### 2.4 ★硬事实三：开关只有"关"的一半，且缺一键开关
```
kurisu-player.js:2925  var smOff = !!(p.manifest && p.manifest.stateMachine && p.manifest.stateMachine.auto === false);
kurisu-player.js:2926  if (p.smOn && !smOff && !p.staticOnly && !p.destroyed) { return p.smStart({ durationMs: 0 }); }
```
- **开启**：只认挂载点 `data-xk-kurisu-sm="on"`（或 `create({stateMachine:true})`）。
- **关闭**：只认 `manifest.stateMachine.auto === false` —— 而 `manifest.json` 是**生成物**（`build_statemachine_manifest.py` 写出）。
- **没有** URL / `localStorage` / `__xkConfig` 开关（同文件的眨眼/注视/静音口型**都有** `?xk-blink=` 这类开关 —— SM 漏了）。
**⇒ 修法**：给 SM 补 `?xk-sm=off`（或 `__xkConfig.sm=false`）作为生产级一键关闭，**默认仍关**；并保留 manifest 的 `auto:false` 作为"永久关"。

### 2.5 口型取证出口：改名 + 一个"采样为 0"的机制发现（给 T5）
- 正确名字是 **`window.__xkVoiceTick`**（`{t, mouth, clip, hopMs, speaking, at}`）；`window.__xkVoice` **被语音子系统占用**（`shell-script.html:827`），别再混用。
- 实测：不带开关时 `typeof window.__xkVoiceTick === 'undefined'` ⇒ **默认关、零开销** ✓。
- ⚠️ **本探针实测 `tick: 'ABSENT'`（即使我先设了 `window.__xkVoiceOn = true` 且 `speak()` 返回 `ok:true`）**。最可能的原因（读码 + 部分复现，**未完全证实**）：
  `forensicVoiceOn()` 把结果**记忆化**（`:2000-2006` `if (forensicVoice === null) { forensicVoice = !!(global.__xkVoiceOn || ?xk-voice-diag=1) }`），
  而**页面自身的语音子系统在我注入开关之前就可能已经调过一次** ⇒ 被记忆成 `false`，此后一直是 false（我事后打开也没用）。
  **给 T5 的建议（不改播放器）**：用 **URL** `?xk-voice-diag=1` 打开（而不是事后设 `window.__xkVoiceOn`），保证**首次 tick 之前**就是 true；这大概率能解释"0 样本"。

## 3. 触发契约（三类 + 优先级 + 抢占）

### 3.1 三类动作（**必须分开管，规则完全不同**）
| 类 | 真实 clip 名（站内已有） | 触发 | 优先级/冷却 | 承载信息 |
|---|---|---|---|---|
| **反应类** | `thinking`（正播）、`thinking_trans`、`speaking_trans`/`speaking_short`、`angry_trans`/`shy_trans`/`surprise_trans`/`sad_trans`、`trans_smile` | **站点事件**（取数中/取不到/429/新告警/提问/回答） | 高，按事件冷却 | **是**（把技术状态可视化） |
| **转场类** | 9 条 `hostTriggeredEntries` | 状态切换时衔接 | 中，短（≤900ms） | 否（防跳变） |
| **氛围类（生活片段）** | `idle2`、`idle_mic_wind`、`idle_side_butterfly`、`idle_side_wind`、`idle_side_soft_wind`、`idle_str_wind`、`idle_closed_eye`、`trans_standby`（未来：喝咖啡/站起来） | **时间/空闲驱动**（不是事件） | **最低**，长冷却 | 否（给"生命感"） |

### 3.2 优先级总表（**不许叠加，同层内按冷却+历史挑一个**）
```
口型（播语音时，抢占一切）
  > 用户交互反应（提问/回答/点情绪）
  > 站点事件反应（取数中/取不到/429/新告警）
  > 转场（衔接用，不单独存在）
  > 氛围（生活片段）
  > 纯 idle（兜底）
```
**抢占规则**：高优先级到来时，**当前动作允许被打断**，但必须用**转场类**衔接（不硬切）；被打断的低优先级动作**不进历史去重表**（下次还可以演）。

## 4. 动作调度器（**必须收敛到单点**，否则会互相打架）

现在站内有多处直接调 `speak*/setEmotion/play`（`idcard.html:245/264/616/645/658/723/778/803`）⇒ **必须新增一个单点调度器**，其它地方只向它提交"意图"。

```
Scheduler.request(kind, name, {prio, minHoldMs, cooldownMs, source}) -> Promise<{accepted, reason}>
Scheduler.tick(nowMs)   // 由播放器已有的同一个 rAF 驱动，不新开循环
Scheduler.cancel(reason) // 抢占：内部走转场
Scheduler.state() -> {current:{kind,name,startedAt}, history:[{name,at}], cooldownUntil:{...}, dropped:[...]}
```
规则（写死）：
1. **单点**：任何非调度器代码不得直接 `play()`（除了口型层）；
2. **不叠加**：同一时刻只有一个"动作层"在演，排队/丢弃都要记 `dropped`（可取证）；
3. **历史去重**：同 `name` 在 `cooldownMs` 内不许重复；氛围类额外"10 分钟内不同名复播"；
4. **抢占必须过转场**（转场类永久豁免冷却，但最短 300ms）；
5. **可见性/偏好**：`document.hidden` 或 `prefers-reduced-motion` ⇒ **只保留口型与转场，其余全部不演**；
6. **带宽闸**：沿用 `maxWalkBytes`（6MB）；氛围/反应动作**必须先查 `manifest.clips` 是否可播**（修完 §2.3 前一律跳过并记 `dropped:'clip-missing'`）。

## 5. 场景与光照层（新的一层：优先级**低于动作、高于纯 idle**）

### 5.1 现状（证据）
| 资产 | 体量 | 产物引用 | 结论 |
|---|---|---|---|
| `kurisu/scene/bg/room_{coffee,computer,sleep,crt,thinking,whiteboard,empty}.webp` | 7 × ~82KB ≈ 576KB | 各 **1~2 次**（都在 `xk-app.js`/生成物的清单里） | **睡着**：没有任何"按状态/时段切房间"的运行时代码 |
| `kurisu/scene/bg/light_{high,low}.webp` | 2 × ~40KB | **0 次** | **完全没用到** |

### 5.2 房间规则（由**同一个调度器**驱动）
| 触发 | 房间 | 依据（已有数据） |
|---|---|---|
| 监测中心 / 有告警在处理 | `room_computer` | 当前页面 + `XK_FEED` 有告警 |
| 空闲闲聊、无告警 | `room_coffee` | 长时间无告警 + 无交互 |
| 深夜（本地时段）或 idle ≥90s | `room_sleep` | 本地时间 / idle 计时 |
| 正在研判（取数中/思考） | `room_thinking` | `thinking` 态 |
| 讲口径/原理（关于页、口径段落） | `room_whiteboard` | 页面/锚点 |
| 空态（无数据、无笔记） | `room_empty` | 空列表态 |
| 默认/进站 | `room_crt` | 现状 |

### 5.3 光照
`light_high` / `light_low` 按**本地时段**选一张，**叠在房间层之上、角色之下**（`z-index` 介于两者之间），`opacity ≈ 0.25~0.45`（需真机调），**不参与口型层**；`prefers-reduced-motion` 时不更换（只保留静态一张）。

### 5.4 切换方式与冷却（硬要求）
- **必须交叉淡入淡出**（两张图 `opacity` 互切，≥400ms），**不许硬切**；
- **房间切换时角色不能跳**：切换只影响背景层，**不动角色画布**；
- **冷却**：房间最快 **60s** 才换一次；同一房间 5 分钟内不重复切回；
- **可一键关**：`?xk-scene=off`（建议与 §2.4 的 `?xk-sm=off` 同一套开关口径）。

## 7. 素材预算账（新增任何素材前必算）

```
现状：static/kurisu + static/images/crt = 145.03 MiB ／ 门禁上限 160 MiB ⇒ 余量 ≈ 14.97 MiB
分档：voice 57.90 | medium 48.15（38 条图集）| hi 19.62（6 条）| video 9.10 | full 7.11
已被砍（manifest.stateMachine.notShipped）：
  · 37 条剪辑的 *.boot.webp / *.poster.webp 共 8.2MB（顶穿 80MB 闸门，首帧改用图集第 1 帧）
  · speaking_long 的 hi 档 6.12MB（加上会到 83.7MB > 80MB ⇒ 只发 medium）
门禁：scripts/assert-build.sh 第 ⑨ 条（分片与总量）+ 第 ⑩ 条（首屏预算，资产自报口径 1536KB）
```
**结论**：房间（576KB）+ 光照（80KB）= **约 0.64 MiB**，**在当前余量内且几乎无感**；但**任何新动作（如 pilot 的"喝咖啡"）若带 hi 档图集，1 个动作 ≈ 1.3~2.6MB（medium）+ 可选 hi**，仍可容纳 **约 5~10 个新动作**，之后必须重编码或提闸门。**做 pilot 之前先按本节算账**。

## 9. "要不要做喝咖啡 / 站起来"这一节

- **站内现在没有这两条**：38 条剪辑里带生活感的只有 `idle2`、`idle_mic_wind`、`idle_side_butterfly`、`idle_side_wind`、`idle_side_soft_wind`、`idle_str_wind`、`idle_closed_eye`、`trans_standby`（见 §6）。
- **它们是产线 pilot（新产素材）**：`docs/素材产线能力-T18-20261015.md:473,477`（`pilot = 2 个新动作（例：喝咖啡 / 站起来），每个动作 = 1 条转场 + 1 条循环`，结论"量级是一杯咖啡，不需要立项审批"）；`docs/角色能力深化与双智能体协作方案-20261015.md:253`（"pilot：只做 2 个新动作…不做全身"）。
- **建议**：**先用现有 8 条生活素材把调度器与氛围规则跑通并真机验收**（S4+S5+S8），**再决定是否产新动作**。理由：① 新动作要占预算（§7，每个约 1.3~2.6MB medium，可能带 hi）；② 没有调度器时，多两条素材只会让"乱动"更明显；③ pilot 的收益（"生活感"）与现有 8 条重叠度高。
