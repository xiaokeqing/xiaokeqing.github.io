## 6. 风险评估

### 6.1 成本影响（`max_tokens` 2000 会让单次费用上升多少）

**单价（官方页，`[待核对]`）**：阿里云百炼 `qwen-plus`，华北2（北京）、输入 ≤128k：

| 计费项 | 官方单价 | 出处 |
|---|---|---|
| 输入 | **0.115 USD / 百万 tokens** | [qwen-plus 模型信息 · 模型价格](https://www.alibabacloud.com/help/zh/model-studio/qwen-plus) |
| 输出（非思考） | **0.287 USD / 百万 tokens** | 同上 |
| 输出（思考） | **1.147 USD / 百万 tokens** | 同上 |

```
[待核对] ① 页面给的是美元/百万 token 口径（国际站）；线上走的是华北2 国内结算，
            人民币价目表需在百炼控制台核对（本文不猜人民币单价，只做量级换算）。
[待核对] ② 是否走"思考模式"未知：代码里没有任何 enable_thinking/dashscope 思考开关
            （全仓库 grep 只有 RagService 的注释提到 thinking 模型名），
            而公开问答用的是 qwen-plus（Qwen3 系列，支持思考/非思考融合）
            ⇒ 若实际按思考模式计费，输出单价是 4 倍。
[待核对] ③ 1 USD 折算按 7.2 元，仅用于量级换算。
[待核对] ④ 中文 token↔字符比（1 token ≈ 1.3~1.5 汉字），用于把 token 换算成"多少字"。
```

**结论（按公式，不拍脑袋）**

1. `max_tokens` 是**上限**，不是用量 ⇒ **原本没被截断的回答，费用一点不变**；
   只有"以前被截断、现在能写完"的那部分回答才会变贵。
2. 单次最坏增量 = (2000−800) × 输出单价：
   - 非思考：1200 / 10⁶ × 0.287 USD = **0.00034 USD ≈ 0.0025 元/次** `[待核对]`
   - 思考：1200 / 10⁶ × 1.147 USD = **0.00138 USD ≈ 0.0099 元/次** `[待核对]`
3. 公开池极端上界（60 次调用/日 **全部**顶格到 2000）：
   - 非思考：**≈ 0.15 元/日 ≈ 4.5 元/月**
   - 思考：**≈ 0.59 元/日 ≈ 17.8 元/月**
   > 注意 `public-daily-limit` 计的是**模型调用次数**（`ModelQuotaGate.checkAndAcquire()` 在模型出口记账，
   > `DashScopeLlmProvider.java:154-156`），而一次提问有 **PLANNER + ANALYST** 两次调用
   > （`MultiAgentCoordinatorImpl.java:337-354` 与 `690-713`），失败还会再重试一次
   > （同文件 698 行 `for attempt = 1..2`）⇒ 60 次 ≈ 20~60 次真实问答。上面的 60 已经按"调用次数"计，不必再乘。
4. **可能净降**：现在失败的回答会白烧最多 **2 × 800** 输出 token（两次尝试都真实计费、都过一次配额闸门），
   却一个字都没交付。改后同一问题若**第 1 次尝试就成功**，输出可能只有 1000~1400 token ⇒
   这类问题的单次成本**反而下降**，同时把"假故障"消掉。
5. 输入侧：`max-question-chars` 600→1200 只影响**输入** token，量级 ≈ 0.0005 元/次以下 `[待核对]`，可忽略。
6. **不确定项**：A 组让回答真的变长 ⇒ 撞 20s 的概率上升（见 6.2），
   而"超时"的那次调用**已经产生的输出 token 仍会计费** ⇒ 若超时比例明显上升，成本会非线性变差。
   **判据**：升级后一周内看 `data/model-quota-public.json` 的 `used` 增长速度与日志里
   `模型调用超时（20000 ms）` 的条数（两者任一明显上升就要重新评估）。

1. **yml 在 jar 里** ⇒ P1–P4 要生效**必须重建镜像**（沿用正文 §3.1 路径 A 的发布链）。
2. **成为 Spring 配置键之后才可热覆盖**：一旦 J1–J4 落地，`app.llm.persona.temperature` / `top-p` 就能像正文 §1.2 B2/B3 那样，
   通过 `docker-compose.yml` 的 `SPRING_APPLICATION_JSON`（**优先级高于 jar 内 yml**）覆盖 —— 但**改 env 仍需重建容器**，只是不必重发镜像。
3. **⚠ 顺序坑**：在 J1–J4 落地**之前**往 `.env` / compose 里加 `APP_LLM_PERSONA_*` 是**无效动作** ✗
   （没有 Java 读它 —— 与正文 §1.4 记的 `rag.model` 是同一类坑）。本节把顺序写死：**先合 Java → 重建镜像 → 再用 env 调值**。
4. 线上现状（只读核对）：compose 的 `SPRING_APPLICATION_JSON` 里**没有任何 `app.llm.*`**，`.env` 也没有采样类键
   ⇒ 现在的生效值全部来自 jar 内 yml，**站主不需要为这批额外改线上文件**（除非要热调值）。

### 12.6 成本影响（写明：**≈0**）✓

- `temperature` / `top_p` **都不是预算**：它们只改采样分布，**不改 `max_tokens`、不改调用次数、不改超时、不改额度池**。
  一次提问仍是"最多 2 次模型调用"（PLANNER + ANALYST），**这个次数本批不变**。
