- 引用纪律：本文数字**全部**来自既有报告 / 既有评测产物 / 只读取证；未核实的一律标 `[待核对]`。

## 1. 一句话结论

站长反馈的"只能回答简单的本地知识库问题"**不是模型笨**，而是三个结构性错位叠加一个配置陷阱：

1. **访客问的是"现网现在怎么样"，知识库里存的是"安全知识是什么"** —— 这注定拒答，且**公开身份连工具都不许调**（`toolExecutionAllowed=false` 恒为真）。
2. **一次偶发状态被写成了"永久拒答"** —— 概念题实测出现"检索命中 3 条引用、正文却说依据不足"。
3. **`max_tokens=800` 是硬天花板** —— 答案一展开就被截断 → 结构化校验失败 → 重试仍失败 → 系统如实报 `model-failed`。**"答案太长"被表现成"模型不可用"，这是最容易误诊的一条。**

**最划算的第一刀不是换模型，而是先解开 `max_tokens=800` + 打开"数据取不到"与"知识库没有"的区分**（见 §5）。

我原以为"没有 rerank"，只读核对后**更正**：混合检索（BM25 稀疏 + 稠密 → RRF → 轻量重排）**已默认开启**（`app.rag.sparse.enabled=true`、`app.rag.rerank.enabled=true`，`application.yml:300-304`）。既有消融报告（`docs/rag-eval/ablation.txt`，28 条检索题，同一 query / 同一语料 / 同一判据）：

### 2.6 一个已成文的体验缺陷（F5，2026-10-13 已记录在源码注释里）

`PublicKbService` 类注释原文记录：实测概念题（"OWASP A07 是什么"）返回 `state=input-insufficient`「依据不足，不做定性」，**但检索其实命中了 3 条引用**。修复方式是"把命中的片段直出到正文"。这说明：

- "检索不到 ⇒ 拒答"的 fail-closed 语义**没有区分"没有依据"和"没有取数通道"**；
- 一旦正文里没有可读内容，访客的体感就是"AI 什么也不答"。

```

     fallback-provider 为空 ⇒ 跨供应商回退关闭（fail-closed，不静默换人）
资源：1870MB RAM / 可用约 996MB / 2 vCPU / JVM -Xmx1g / swap 已用 673MB ⇒ 本地推理不可行
```

**K 点出的两个坑（本方案的两条高优先级改造由此而来）**：

- **坑 1（最重要）**：`max_tokens=800` 是硬天花板。答案展开 → 截断 → JSON schema 校验失败 → 重试一次仍失败 → 系统如实报 `model-failed`。**表现是"模型不可用"，成因是"答案太长"。**
- **坑 2**：`application.yml` 里的 `rag.model=qwen-plus` **不控制公开问答** —— 它只被 `RagService`（流式 `/api/chat`）读；`/api/public/ask` 的生成走 `MultiAgentCoordinatorImpl.runAnalystPublic → llmProvider.generate → ChatService.createChatModel`，用的是硬编码的 `DashScopeChatModel.DEFAULT_MODEL_NAME`。**所以"只改 yml 换模型"在公开问答题上是无效动作。**

## 3. 根因排序（影响 × 修复成本）

### 3.1 排序方法（先说清楚，不是拍脑袋）

对每条根因评两个 1–3 的量，**排序分 = 体验影响 ÷ 修复成本**（分越高越先做）：

- **影响（1–3）**：3 = 直接决定"访客大多数提问能不能得到有用回答"；2 = 决定回答质量/可信度；1 = 边角体验。
- **成本（1–3）**：3 = 跨模块改造 + 需要重启/重建镜像 + 需要新评测集与新语料；2 = 单侧改造 + 配置调整；1 = 改配置或改提示词、可当天回滚。

判据（"影响"打分的依据，全部来自 §2 的实测数字或已记录缺陷，不是感觉）：
① T13 题库的**提问分布**（`live`/`capability` 等实时类占比）；② T13 里**拒答类 19 条 vs 可答类基线为 0**；③ §2.6 已归档的真实缺陷；④ §2.8 已定位的失败链路；⑤ §2.4 检索已打满 28/28 ⇒ 检索类根因天花板低。

### 3.2 排序结果

| # | 根因 | 影响 | 成本 | 分 | 为什么排这里 |
|---|---|---|---|---|---|

| **5** | **③ 检索质量（rerank / 分块）** | **1** | **2** | **0.5** | **已更正**：混合检索 + 轻量重排已默认开启，28/28 召回打满、MRR 0.9821（§2.4）。剩余空间只有"模型级重排"，而它与 2C2G 约束冲突。**排在最后是因为它已经不是瓶颈** —— 这条要从原分析的"主因"降级为"低收益优化" |

## 4. 分级改造清单

工时口径：**S = ≤0.5 人日**；**M = 1–3 人日**；**L = >3 人日**。
"动哪一侧"：后端 = Java 代码 + 重建镜像 + 重启容器；配置 = 只改 `.env` / yml（视实现决定是否需重启）；前端 = 博客侧页面/脚本。

### A 只读工具调用（最本质的一刀）

| 项 | 内容 |

- **公开池 30 次/日全局**，2026-10-15 已 `used=30` ⇒ **今天不能再用 `/api/public/ask` 做任何评测**；把它当评测入口会把"额度耗尽"读成"模型不可用"（T13 首轮真实发生过）。
- **评测必须走内部 eval 池**：`Authorization: Bearer <APP_EVAL_TOKEN>` 且**只能** `/api/chat`（`EvalIdentity.ALLOWED_PATH` 精确匹配）。评测池当前 `used=29/60`，**余 31 次**。
- 一轮 40 题全量评测的成本估算：**每问最多 2 次模型调用**（A 项生效后为 3–4 次）⇒ 40 题 ≈ **80 次调用 > 余量 31**。因此必须**先申请把 `APP_QUOTA_EVAL_DAILY_LIMIT` 从 60 提高**（或分日跑），**这是评测的前置条件，不是可选项**。
- **绝不允许读 token**：文档、脚本、日志里都不得出现 Token/密钥字面值；只能写变量名与"SET / MISSING"。
- 无效答卷（模型未生成 / 额度耗尽 / 非 200）**一律不计入指标，也绝不算作拒答成功**（沿用 T13 既有纪律）。

### 6.3 统一指标口径（全部已有实现，不新造）

- **要点命中率**：题面 `key_points[].any_of` 命中（T13 已有 `qa-score` 实现）。
- **拒答正确率**：`should_refuse=true` 且未命中 `must_not_contain`（T13 已有）。
- **引用正确率 / 幻觉率**：**用 `scripts/citation_audit.py`**（与 `eval-papers.py` 的指标**同一实现、同一证据源**，避免"指标数字与复核工具各说各话"）：`citationTraceableRate` / `citationPartialRate` / `citationUnverifiableRate` / `citationHallucinationRate` / `citationMissingRate`。
- **状态自洽**：与 `refusal-rubric.json` 的 `expected_state` 比对。
- **置信区间**：全部带 Wilson 95% CI（现有实现已支持）—— **样本 ≤10 时禁止只报点估计**。
