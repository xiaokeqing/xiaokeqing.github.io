| `/api/public/stories`、`/story?src=` | 单源候选池与点击后懒加载的事件时间线 | 15s |

**脱敏铁律**：公开面**默认展示观测到的真实来源 IP**（`app.public.mask-ips` 缺省 `false`，2026-10-14 站主拍板），但**内网 / 保留 / 链路地址一律显示「内网/未知」**（`PublicIpPolicy.java:30–39`），`/ask` 上访客地址 `masked` 恒为 true；蜜罐凭据只保留结构与频次；自由文本统一过滤（含同类泄漏回归测试）；访客 IP 与内网地址零泄漏；取不到 / 确实没有 / 未接入 三种措辞分开，**绝不补样例值**。

**缓存口径（当晚实测）**：`/api/public/<name>.js` 是内容相同的可缓存别名（响应带 `stale-while-revalidate=90`），CF 侧实测出现过 `EXPIRED` / `MISS`，说明它确实进了缓存；而 `home`、`alerts` 等 JSON 端点仍是 `cf-cache-status: DYNAMIC`，每次都要回源 srv1 再跨境回到浏览器 —— 这就是 §9 第 4 条那 3–4 秒的来源。

## 4. 处置与封禁链路

1. 规则判定（Wazuh 告警 / 阈值）给出建议处置；
2. 高危动作需人工审批（模型只解释不拍板）；
3. 落地真实防火墙规则（可解封，`unblockMode=REAL`）；
4. 全过程写审计留痕，前端只读展示，误处置有拦截机制。

## 5. 公开面防护

- 统一数据出口闸门（唯一出口：`/api/public/*`，全部只读）；
- 访客限流 6 次/分钟/IP，超限 429 + `Retry-After`；
- 站主令牌（`X-User-Token`）走同一套登录校验后放行，不降低安全边界；
- 提示词注入护栏（`PromptInjectionGuard`），不可信内容统一包裹；
- 问答契约：**只解释、不取证**；检索不到依据直接拒答。

### 19.6 发布链「tar 包里没有 index.html」的假失败（根治）

- 现象：发布偶发 `[X] tar 包里没有 index.html`，重试有时就过；成员 2,531 个文件时更容易撞。
- 真因：`scripts/srv2-site-receive.sh:139` 原 `printf '%s\n' "$MEMBERS" | grep -qE '(^|/)index\.html$' || die …` —— `grep -q` 一匹配就退出 ⇒ `printf` 继续写吃 **SIGPIPE(141)** ⇒ `set -o pipefail` 把 141 当整条管道失败。
- 修法：改纯字符串匹配 `case $'\n'"$MEMBERS"$'\n' in *$'\n'index.html$'\n'*|*$'\n'*/index.html$'\n'*) …`，不再有管道。

第一版上线后线上页面是**竖排碎片**：PDF 表格被逐格拆成 `<ul><li><p>对比</p></li><li><p>交换机</p></li><li><p>路由器</p></li></ul>`，课程里「交换机 vs 路由器」「默认子网掩码/CIDR」「DORA 四步」「递归 vs 迭代」「常见 Web 中间件」「虚拟主机」这些核心内容全部失去可读性。

| 步骤 | 结论 |

### 21.3 断句：碎片何时该合并

`MARKER`/标题/代码之外的正文行，只有三种情况才续接到上一段：上一行以 `state['wrap_next']`（越过右边界）结尾、上一行末尾没有句末标点（`END_PUNCT = [。！？：；…”」）)】]$`）、或本行以收尾标点开头。另修两处顺序 bug：非缩进 marker 行先 `flush()` 再起段（否则续行接不上，表现为 pki 的 `件）` 单独成段）；缩进 marker 行也要先 `flush()`（否则待定段落被排到 bullet 之后）。裸编号（`4  、`）例外，不走 marker，避免位权列表被拆段。

### 24.7 /ai/ 的 11.6 MB 为什么没压下去（一次失败的实测，记下来免得下次再撞）

`/ai/` 的大头是 E-mote 模型：`kurisu_c.psb.m.json` 3512KB + `tex#000/001/002` 共 2952KB 的 PNG 纹理 + `resx` 761KB + `FreeMoteDriver.js` 1226KB。

做法（已回滚）：把三张纹理缩到 1024 宽存成 `.webp`、改 `kurisu_c.psb.m.resx.json` 里 `Resources` 的三条路径、

### 27.3 后端：为什么要加一个 `/api/public/daily/index.json`

第一版归档是前端"按日期逐个探"`/api/public/daily/daily-<日期>.json`，实测 30 个并发请求全 `net::ERR_FAILED`。两个原因叠加：

- 公网端点限流 **20 次/分钟**（`PublicApiController` 的 `PublicRateLimiter`）；

### 27.4 部署这一课：`-SkipBuild` 只是验证通道，生产指针在 ACR

`deploy-remote-build.ps1 -SkipBuild -AllowDirty` 用本机编好的 jar 在 srv1 侧构建镜像并重建容器，我据此验证了 `/api/public/daily/index.json` 在 13:10:26 返回 `count=4`、四天日期倒序、`masked=false`。但 **13:10:31 容器被重建，镜像换成 ACR 里那版旧镜像，端点随即 404**。

根因：srv1 上有一整套 systemd 守护 —— `secagent-containerguard.timer`（25 秒）、`secagent-healthwatch.timer`（约 2 分钟）、**`secagent-redeploy.timer`（每 5 分钟读 ACR `stable` 的 digest，与当前运行不同就 pull + 重建 + 硬校验 + 健康核对）**、`secagent-site-probe.timer`、`secagent-srv2deadman.timer`、`secagent-daily-check.timer`。所以：

- **真正的发布姿势**：本机构建 jar → 服务器构建镜像 → 镜像 tag 成 ACR `stable` → `docker push` → `systemctl start secagent-redeploy.service`（或等 5 分钟的 timer）。`-SkipBuild` 那条路 5 分钟内必被回滚，只能当快速验证。
- 推上去的镜像还会被 `srv1-redeploy.sh` 第 5/9 步的 fail-closed 闸门拦住：镜像缺少 `org.opencontainers.image.revision` 就 `[X] 来源不明，拒绝部署`。`secagent:local` 当时只有 `{"org.opencontainers.image.version":"22.04"}`（继承自基础镜像）。
- 修法（已提交 `3a8b15a`）：`scripts/build-on-server.sh` 第 2/4 步的 `docker build` 补两个 label —— `--label org.opencontainers.image.revision=$TARGET_FULL`（完整 commit）与 `--label artifact-md5=$JAR_MD5`（上传 jar 的 MD5）。闸门还会校验 revision 的形状与（若发布指针公告了 commit）两者是否一致；`artifact-md5` 缺失只会降级为 warn。

修复后实测：镜像 `sha256:060e4739…` 带齐两个 label → push 到 ACR 得到 digest `sha256:4dc09123…` → `systemctl start secagent-redeploy.service` 报"当前运行 digest 与发布指针相同 —— 无需变更" → 容器镜像已是新 digest、`/api/health` 200、`/api/public/daily/index.json` **200 / 3164 字节 / count=4**。

### 36.2 为什么修不好（关键坑）
1. `secagent-static` 是 **`config_src=local`**（本地配置托管）。这种隧道用 `--token` 跑时，cloudflared 会说 `No ingress rules were defined in provided config … will return 503 for all incoming HTTP requests`，API 侧那个「远端配置」根本不生效。
2. 所以正确组合是：**token 只当身份，ingress 用本地 yml**：
   `cloudflared --no-autoupdate --config /etc/cloudflared/ingress.yml tunnel run --token-file /etc/cloudflared/token-static`

3. 隧道 token 由 API 取：`GET /accounts/{aid}/cfd_tunnel/{tid}/token`（aid=`30df99f621c51dfb031a953ae55ed67d`）。写进 `/etc/cloudflared/token-static`（0600）后与 API token 无关，**API token 可以随时 revoke 掉**。
4. 上一版 `LoadCredential=` + `--credentials-file /run/credentials/...` 那种写法在反复重启后凭据文件读不到，会 crash-loop（2 分钟 60+ 次注册）——换成 token-file 后 4 条连接稳定。
5. srv2 nginx 的 systemd 修复（同一晚）：原 unit 是 `Type=forking` + `PIDFile=/run/nginx.pid`，但 nginx 写不了这个文件（`Can't open PID file … Operation not permitted`）⇒ 每次 `systemctl start/reload` 超时并且**把正在跑的 master 一起带走**（真宕过一次）。修法：drop-in `/etc/systemd/system/nginx.service.d/runtime.conf` 改成 `Type=simple` + `ExecStart=/usr/sbin/nginx -g 'daemon off;'` + `PIDFile=`（清空），`RuntimeDirectory=nginx`。修完 `systemctl restart nginx` 实测安全（站点/API/靶场全 200），并已 `enable` 开机自启。**以后改 nginx 配置用 `systemctl restart nginx`，不要再用 `nginx -s reload`。**

### 38.1 为什么做
站主口径原话：「功能优化和功能升级指的是后端安全方面的功能」。
升级前的后端只有一条链：**Wazuh 告警规则命中 → 生成一条事件**。Suricata 侧只读 `event_type=alert`，于是**被测端口、被探测的 SNI、TLS 指纹 JA3 全部看不见** —— 「有人在扫我」能看见，「扫了哪些端口、按什么指纹来探」看不见。封禁侧同样单薄：只支持 IPv4、只靠 Wazuh 的 active-response 下发，没有 TTL 分级、没有 dry-run、没有回滚。

### 38.2 Suricata 全事件摄取（agent A 交付，commit `c38e39c` 的一部分）
新增包 `src/main/java/org/example/integration/suricata/`：
- 事件模型：`EveEvent`、`FlowEvent`、`HttpEvent`、`DnsEvent`、`TlsEvent`、`AlertEvent`。
- 聚合与缓冲：`PortCount`、`SniCount`、`Ja3Count`、`BoundedRingBuffer`。
- 读取侧：`EveEventParser`（把 eve 的 JSON 行解析成上面那套模型）、`SuricataEventStore`。

`SuricataService` 从「一次性读尾部」改成 `@Scheduled` 按字节偏移增量读取（`RandomAccessFile`），并检测轮转 / 截断（文件变小或换 inode 就从头来）；每类事件缓冲成一个 **50000 条的有界环**（`BoundedRingBuffer`），内存封顶、不随 `eve.json` 涨。

新增 `SecConnController`，三个只读端点（`/api/sec/**` 默认需要登录，响应统一 `{code,message,data}`）：

|---|---|

### 38.3 跨机同步（srv2 的 Suricata → srv1 的应用）
拓扑：Suricata 跑在 srv2 的容器里，`eve.json` 由宿主挂载在 `/opt/suricata/logs`（约 **286 MB**，增长约 **1 MB/分钟**）；应用跑在 srv1，读的是 srv1 本地的 `/var/log/suricata/eve.json`。中间靠一条单向同步：
- srv1 侧脚本 `/usr/local/sbin/secagent-eve-sync.sh`，调度在 `/etc/cron.d/secagent-eve-sync`（每分钟，root，走 `/root/.ssh/xk2srv2`）。

四个坑，全是真踩过的：
1. **拿本地大小当远端偏移**：`last_ts` 停在 `2026-11-05T23:59:36`，新数据永远追不上 —— 等于把旧数据「追到最新之后」。修法：state 文件 `/var/log/suricata/.eve.remote_offset` 只记**远端** size。
2. **链路只有约 2 Mbps**：8 MB 要传 6 分钟，积压越滚越大。修法：`tail | gzip -1 | ssh | gunzip`，同一段降到 **20 秒**。
3. **cron 每分钟重入**：两次并发写同一个 `.tmp`，偶尔落半截文件。修法：脚本里 `flock -n 9`，拿不到锁直接退出。
4. **`tail -c` 的种子首行是半截 JSON**：解析器直接报错。修法：首行切到第一个换行之后（Python 里按 `\n` 找第一个切点再喂）。

容器要能看到文件：`docker-compose.yml` 的 app 服务加 `- /var/log/suricata:/var/log/suricata:ro`（commit `32c6d8f`）；没挂的时候如实报 MOCK，不假装有数据。

### 38.4 启动回填（commit `758d13d`）
缓冲是纯内存，重启就空。回填参数 `integration.suricata.backfill-lines`（默认 `20000`，`0` 关闭）：`@PostConstruct` 阶段从 `eve.json` 尾部倒读，按 **64 KB** 块找第 N+1 个换行，只把这一窗口读进内存后**正序**喂解析器；回填结束把 `ingestOffset = raf.length()`，保证后续增量从文件尾接上、不重复。
选 `@PostConstruct` 而不是 `ApplicationRunner` 的三个理由：
1. 与 `available` / `store` 的初始化同序，不会出现「store 还没准备好就回填」。
2. 在端口开始接收请求**之前**完成 —— 避免「重启后端点先返回空」的那个窗口。
3. 与首次增量调度无竞态（调度器起来时 offset 已经是文件尾）。

### 39.2 高清件怎么造（IVF 路线，13 分钟/6 个动作）

不重新解 7688 个 KTX2，而是走原始包里的 `video/<clip>/{color,alpha}.ivf`（VP9 + 独立 alpha 视频）：

```
ffmpeg 解 color.ivf / alpha.ivf → numpy 预乘 → Pillow LANCZOS 缩到 535×720
  → 反预乘 → 8 列 × ≤5 行（每页 ≤40 帧）拼图 → WebP q80 method=6
```

- 保真度用 KTX2 交叉验证：颜色平均 |Δ| **1.79/255**、alpha **0.70/255**（肉眼不可分）。
- 体积（`idle` 实测）：540 三页合计 **3.94 MB**（32.8 KB/帧），同帧数 360 三页 **1.64 MB** ⇒ **2.40×**。
- 单页解码内存 4280×3600 RGBA = **61.6 MB**，所以每页上限 40 帧——这也是**必须做页级懒解码**的原因（120 帧全常驻要 185 MB，`thinking_speaking2` 300 帧要 462 MB）。

### 39.3 播放器改造（页级懒解码）

之前 `ensureMediumClip` 把一个 clip 的**所有页**一次 decode 并常驻（`smEvict` 只释放别的 clip）。
本轮改成按当前帧号取页、只保留**当前页 ±1**，离得远的页立即释放；同时把 `smUseHi` 的门槛从 `canvas.width >= 480` 抬到 `>= 700`（小画布下不值得为 540 下几 MB）。

### 39.5 这一轮踩到的三个坑

1. **首页那份内联副本**：`layouts/index.html` 里有 `xk-scene.js` 的同构内联代码（108 KB），`hiAtlas()` 仍是"只认单页" `if(ps.length !== 1) return null`，所以改完 `assets/js/xk-scene.js` 后首页毫无变化。诊断绕了两圈：先怀疑 Hugo `resources/_gen` 缓存（删缓存、`--ignoreCache` 都无效），又用 `window.__xkMarkerTest` 标记测试证明构建确实读源文件，最后才定位到内联副本。**凡是改 `xk-scene.js`，必须同时改 `layouts/index.html`。**

### 41.8 同日收尾：数据面快照化与部署链修复

这一节记 2026-11-07 深夜的收尾：**公开只读数据从「实时接口」改成「同源静态快照」**，以及把当天部署链踩到的三个坑固化成判据。

#### ① 为什么快照化：CF 隧道对大响应已经不可用

- `demo.xiaokeqing.cn` 走 Cloudflare 隧道；**响应体超过 ~3 KB 时吞吐掉到 ~600 B/s**。小响应还能忍，一上 10 KB 就崩。
- 实测两笔：`home.js` **36 KB**，60 s 只下到 **3 KB** 就停住；`alerts.js` **16 KB**，直接 `connection reset`。
- 后果是 `/alerts/`、首页数据卡、`/ip/` 长时间转圈 —— 骨架屏、重试、超时提示都遮不住，因为**慢的不是前端，是这条链路本身**。
- 结论：公开只读数据不该每次实时穿隧道。它们本就是低频变化的聚合结果，构建期抓一次就够。

#### ② 做法：12 个公开只读端点 → 构建期快照

| 步骤 | 做什么 |
|---|---|
| 抓取 | `scripts/snapshot-api.ps1`：ssh 到 srv1/srv2，**从 loopback 打** `127.0.0.1` 上的 API（不穿 CF 隧道，毫秒级），打成 `tar.gz` 再 scp 回本机 |
| 落盘 | 解到 `static/api/public/`，**路径与线上端点同形**（线上 `/api/public/home.js` ⇒ 仓库 `static/api/public/home.js`），Vercel 同源直出；`_snapshot.json` 记 `generatedAt` 与逐文件字节数 |
| 切换 | `layouts/partials/xk-demo/head-meta.html` 末尾一段内联脚本：把 `meta[name="wb-api"]` 的 `content` **清空** ⇒ 页面所有 `fetch` 变成同源相对路径，直接命中静态 JSON |
| 回退 | URL 加 **`?live=1`** 就跳过清空、继续用原 API 基址（排障用，不写进任何页面） |

覆盖的 12 个端点：`alerts / alerts5 / home / geo / metrics / stories / password / webstats / deploy / eval / kb / daily/index.json`（快照文件随仓库入库，Vercel 构建即带上）。

快照会随数据增长：22:42 那次刷新后 `alerts.js` 17,944 B、`home.js` 40,019 B，仍在 1 s 级。

#### ④ 部署链三个 bug 与修法

1. **health 轮询时机**：`deploy-remote-build.ps1` 的 fail-closed 核对在 `docker compose up -d --force-recreate` 之后**立刻**读 `/api/health` ⇒ 容器还在 starting，读到的是**旧**容器的 commit，于是误判失败并「已按 fail-closed 中止」。修法：先等容器 `healthy`（带超时），再拉 health 比对 `buildSha / embeddedGitCommit / artifactMd5`；重建时必须同时注入 `BUILD_SHA`、`ARTIFACT_MD5`、`SOURCE_SHA`（缺 `artifactMd5（A）` 会让 health 变 `degraded`）。
2. **镜像 ID 与容器内 jar md5 断言**：`docker compose up -d` 起的可能是 compose 里 `image:` 指着的旧 ACR 镜像（当天一次是 `sha256:4ecf4741…`，容器内 `app.jar` md5 `00480837…` ≠ 新构建 `ceb6093b…`），表现是「部署成功但没生效」。修法：构建脚本硬断言「容器镜像 ID == 本地 `secagent:local`」+「容器内 `/opt/secagent/runtime/app.jar` 的 md5 == 期望值」，不一致 `exit 7`；且 `set -euo pipefail` **不捕获 `$(…)` 失败**，必须写成 `if ! …`。
3. **`secagent-redeploy.timer` 按 ACR digest 回滚**：srv1 每 5 分钟读 ACR `:stable` 的 manifest digest，与运行中的不一致就 pull + 重建 ⇒ 本地 `-SkipBuild` 那条路 **5 分钟内必被换回旧镜像**。修法：只走官方链路 —— `docker build` 带 `org.opencontainers.image.revision` / `artifact-md5` 两个 label → `docker push` 到 ACR `:stable` → `srv1-redeploy.sh --expect-commit <sha>`（脚本自己校验 label 与 jar md5，digest 相同则安静退出）。

#### ⑤ `.gitignore` 的坑：`public/` 会吞掉 `static/api/public/`

`public/` 是无锚点规则，匹配**任意层级**叫 `public` 的目录，于是 `static/api/public/` 整棵被排除；而 git 的取反不能救回「父目录已被排除」的文件，第一批快照只能 `git add -f` 才进得去。修法：在 `public/` 之后补两行 ——

```
!static/api/public/
!static/api/public/**
```

加完实测：往 `static/api/public/` 放新文件，`git status` 直接可见（`git check-ignore -v` 命中第 122 行的取反规则）。

| 权限 | 用途 |

| `indices:monitor/stats` | 读索引级文档数 / 体积 |
