# 第二部分 · Amadeus 实现方案 v2（范围收窄：**只要"她会说话"，不做本地对话**）

## 2.1 范围声明（明确砍掉）

```
✅ 要：角色活在 CRT 里（帧动画）+ 39 剪辑 + 状态机自动游走 + 6 个房间活动位 + 开场 180 帧（眨眼）
      + **她开口说话（TTS 语音）** + 字幕 + 屏内状态行 + 底部输入条问答
❌ 不要：**本地对话大脑（LLM 本地部署）**、**语音输入（ASR/麦克风回声消除/语音起始检测）**
        （原项目里最吃配置的两块正好就是这两块）
❌ 关闭：鼠标跟随、中景眨眼（素材不存在，正式关闭）
```

## 2.2 语音三层（这是"她会说话"的全部）

| 层 | 内容 | 合成位置 | 服务器/本机负担 | 有没有声音 |
|---|---|---|---|---|
| **L1 固定台词** | 问候 / 切页解说 / 状态播报 / 取不到数据时的兜底句（几十句） | **离线批量生成一次**（你想试的 GPT-SoVITS 就在这一层） | 一次性；之后是**静态文件**，走 GitHub Pages（连 srv1 都不经过） | ✅ 永远有（不需要 Key） |
| **L2 自由回答** | 她回答你输入框里的问题（`/api/public/ask` 的返回文本） | 云端 **Fish Audio**，经已有 `/api/public/tts` 代理 | 只转发字节流；有 sha256 磁盘缓存 + 限流闸 | ✅ 有 Key 就有 |
| **L3 无 Key 兜底** | 动态回答只出字幕 | 不合成 | 零 | ⚠️ 只有字幕 + 帧里自带的嘴 |

**你问的那个判断，答案是**：原项目里"本地对话（LLM）"和"语音输入（ASR+回声消除）"才是吃配置的大头；
**只做"她说话"这一件事，本地 TTS 是最轻的一块**（尤其**离线批量**生成时，不追实时，慢一点无所谓）。

## 2.3 本机试跑 GPT-SoVITS 的方案（你要试的那条路）

```
前提与卡点（如实）：
· 本机显卡：RTX 3060 Laptop / **6GB 显存**（[实测]）；GPT-SoVITS 推理大致需要几 GB 显存（范围值，未实测，不背书）
· **上游仓库不含模型权重与参考音频**（README 明说）→ 你必须自备：
  ① GPT-SoVITS 模型权重（自行下载）② 一段**合格的参考音频**（她的音色样本；这是成败关键）
· 也就是说：这条路能不能走通，取决于"你有没有一段干净的参考音频"，而不是机器性能

试跑步骤（先花 10 分钟证伪/证实，再决定批量）：
 1) 装好 GPT-SoVITS 环境（独立目录，别污染站点仓库）
 2) **只合成 1 句**（10 个字左右），记录：显存峰值 / 单句耗时 / 音质主观分
 3) 判据：显存不爆 + 单句 ≤10 秒（离线批量可接受）→ 继续；否则**放弃本机，走云端同音色**
 4) 通过则批量生成 L1 台词表；导出 **Opus**（一句几秒 ≈ 30~80KB）+ **口型包络 JSON**（见 2.4）
 5) 若中途失败：直接改用云端同一个音色生成 L1（音色与 L2 一致，无需自备参考音频）—— 这是我认为更稳的默认
```
**我的建议**：**先用云端同一个音色把 L1 生成出来（当天就能听到效果）**，本机 GPT-SoVITS 作为"想试就试"的支线；
理由：① L1/L2 音色统一 ② 不用自备参考音频 ③ 不占你机器。**但决定权在你**，我不替你砍掉这条支线。

## 2.4 语音播放的必须设计（原方案漏掉、评审指出、我接受）

```
· **autoplay 门控**（每个新访客的必经路径）：浏览器在首次用户手势前会静音拦截音频。
  设计：未交互态 = 动画与字幕照常、**声音静默** + 显式"🔊 点我开声"引导；
  首次 pointerdown/keydown 后解锁 AudioContext，再补放/续播语音。
  验收矩阵新增一项：**"无手势进站"**（动画正常、不报错、不卡住、有开声入口）
· **口型包络**：优先"服务端随合成返回"（`/api/public/tts` 在云端合成后顺手按 **10ms 窗 RMS × 3.75**
  （clamp 0~1、首窗保底 0.12）算好 `envelope.json` 一起返回；L1 的包络在离线生成时一并算出存 JSON）
  → 客户端零算力、无播放时钟漂移；客户端不再需要自己分析音频
· **口型渲染**：说话中用基础帧**自带的**嘴；静音（mouthValue ≤ 0.08）叠**整帧闭嘴图** + **椭圆遮罩只露嘴**
  （34×18 是遮罩尺寸来源，不是补丁尺寸）；补丁建议裁成"嘴部小图 + 锚点归一化坐标"，避免 clip-path 缩放与 DPR 漂移
```

## 2.5 角色运行时（与 v1 相同，源码级照抄）

```
渲染：桌面底图 cover（**零倍率，无相机动画**）→ CRT **14 点多边形** clip-path →
      内层：空房间底图 → <canvas> 角色（基底帧 + 口型层）→ 字幕板 → 场景整图 → 扫描线/暗角 → 氛围光呼吸
落位：scale = min(W*0.64/764, H*0.90/1028)，x = 0.52W，y = bottom − 1.2%H，anchor=(0.5,1)
帧播放：图集 drawImage + 按各剪辑 frameIntervalMs 推进（rAF + 时间累加；不用 setInterval 做帧循环）
状态机：37 节点 / 87 边、root=idle、出边概率归一化掷骰子；12 个 once_then_hold；情绪入口 prob=0 由宿主触发
场景机：6 节点 / 19 边（起始 stand_thinking，自环 0.8、看 CRT 0.4）、每个 pose 45~60s、
        最后一次语音后 60s 进入空闲、她不在 = BG_empty
过渡：节点间**硬切**；只有角色态↔场景态用 **0.35s 线性 alpha**（原版唯一过渡）
模块：asset-loader（懒载顺序/降级/内存回收，只留当前+下一段）+ 共用"加权有向图游走"原语（状态机与场景机只是两份配置）
```

## 2.6 资产口径（**修正版，见第三部分错误 1**）

```
实测：atlas 53 件 142.2MB ｜ clips 79 件 96.4MB ｜ medium 35 件 34.6MB（**只含 26 个剪辑**）
      ｜ boot 40 件 6.5MB ｜ poster 40 件 1.7MB ｜ opening 7 件 9.8MB
状态机里是 **37 个剪辑**（sad/smile 不在图里），而 medium **缺 9 个**（含 root 的 `idle`）
⇒ 计划：
   ① 补齐 medium 到 **全部 37 个图内剪辑** ≈ 44MB（单件中位 1.18MB × 37）
   ② 主页最常用的 6~10 个剪辑另发一档 **hi（高度 400~500）**，避免 2x DPR 下发虚
   ③ 总量 **55~60MB**（含 boot/poster/7 张场景 0.6MB/mouth）
   ④ 闸门静态总量上限：**12MB → 60MB**；**首屏仍严 ≤1.5MB**（只载 boot + poster + 字幕板 + 开场 boot）
   ⑤ 全部懒载；多分片图集（`.atlas.p01/p02`）由 loader 合并处理
```

## 2.7 分期与验收（每期都要证据）

```
P1 场景层：书桌 cover + 14 点多边形 + 空房间 + 6 场景硬切
   验收：0–15 秒每秒一帧印样与参考录屏并排；**并复用"掩屏多尺度 NCC"做自动化比对**（不靠人肉看）
P2 角色层：medium（补齐 37 剪辑）+ 状态机 37/87 + 开场 84 帧
   验收：30 秒自动游走的节点序列 + 39/37 剪辑逐一可播的截图矩阵 + **第 39–42 帧四连帧**证明眨眼
P3 说话层：L1 预生成（本机或云端）+ L2 代理 + autoplay 门控 + 口型两层
   验收：有手势/无手势/静音兜底/reduced-motion/窄屏 五项端到端；口型对照截图（说话中 vs 静音）
P4 上线：push → CI → gh-pages → 线上复验（首屏字节数、开场眨眼、门禁原文）
```

| # | 它写的 | 事实（我的实测/依据） | 后果 |
|---|---|---|---|
| **1** | "medium 档全量 ≈45MB，已覆盖全部 39 剪辑；上限定 48MB"（**两份评审各犯一次**） | `web/medium` = 35 文件 / **仅 26 个不同剪辑**；状态机是 **37 个**；**缺 9 个，含 root 的 `idle`**（还有 idle2 / speaking_loop1 / speaking_med / speaking_trans / thinking_speaking1 / trans_standby / idle_closed_eye / idle_side_soft_wind） | 照它收口 → **角色连待机都播不出来**；48MB 这个数不能采用 |
