## ① 一句话定位 + 三段式简介

### 1.1 一句话定位

```
一个个人技术站点 xiaokeqing.cn：把「真实攻击数据」变成可由数字角色表达的问答与叙事，
贡献点在管线、评测、边界设计与工程化，不在基础模型与美术。
```

### 1.2 三段式（是什么 / 给谁用 / 解决什么问题）

**是什么** —— 一个**个人**技术博客站点（`xiaokeqing.cn`）+ 架在上面的**安全数字人**。
站点是 Hugo 静态站 + 原生 HTML/CSS/JS（**无前端框架**），共五类页面：主页 `/`、监测中心 `/alerts/`、
笔记 `/posts/`、AI 问答 `/ai/`、测试模块页 `/test/`，另有文章页 / 分类页 / 404 走 Hugo 常规模板。
它同时有**两重身份**：A = 两台云服务器上真实在跑的蜜罐与检测栈（srv2 七个容器 + 蜜罐网段 `172.19.0.0/16`，
srv1 自研 SecAgent 检测栈与公开只读 API）；B = 把 A 产生的真实数据 → RAG 问答 / LLM 决策 → 由数字角色表达。

**给谁用** —— **主观众是站主本人**，对外用途 = 个人博客 + 面试 / 简历展示。
**明确非商业**：角色素材授权为"非商业技术学习 / 研究 / 演示"，商用需另议。
因此站点上没有账户体系、没有广告、没有收费，也不存在任何运营指标可讲。

**解决什么问题** —— 把"两台服务器上真实发生的攻击"变成**人能看懂、且能逐条核验**的东西：
真实只读接口 → 聚合与脱敏 → 上屏；再让数字角色用**日语语音 + 逐帧动画 + 口型**把结论"说"出来。
它刻意解决的问题是**可信度**：数字只来自真实只读接口，取不到就写"读不到"，
并把这条口径做成了**可自动判分的评测用例** —— 40 题里 19 条应拒答，`must_not_contain` 里放真实快照数字，
编出来即判幻觉。【出处：评测报告 §3.1 / §3.3】

## ③ 功能全集（按模块）

### 3.1 开场六拍

进入站点后先播一段**六拍开场**，把"电视通电 → 助手出现 → 界面就位"讲成一个镜头语言：

| 拍 | 用户看到什么 | 背后怎么实现 |
|---|---|---|
| ① 壁纸 | 首帧只有桌面壁纸 | **T=0 只画一张 `desk.webp`**（实测 77,608 B），首帧窗口 565 KB → 77 KB |
| ② 预载底噪 | 轻微底噪，像屏幕在预热 | 150 ms 预载期，底噪充当"正在加载"的视觉信号 |
| ③ CRT 黑屏闪烁 | 屏内黑屏闪 2~4 次 | 每次 80~140 ms **随机**，由显式状态机驱动 |
| ④ 大脸闪断 | 她的大脸以 2~3 次闪断出现 | 60~100 ms 硬切 + 1~3 px 位移 |
| ⑤ 稳定 + 导航同帧 | 闪烁结束**同一帧**画面稳定（过冲白光），导航淡入 | "导航栏何时出现"由**闪烁结束事件**触发（不猜时间）；实测 dock 不透明度 0 → 0.548 → 1 |
| ⑥ 正式动画 | opening 继续 → 一次镜头推拉 → idle 中景 | 开场播完**硬切**到 idle，与上游原版机制一致 |

- 全程有显式状态机 `window.__xkBoot={phase,t0,marks,log}`；实测采样：22 ms phase=0 → 348 ms phase=2 → 948 ms phase=5。
- 任意点击 / 按键 / 滚动立即结束开场；`prefers-reduced-motion` 下不播开场，直接显示当前姿态静帧。 【出处：UI批实施件 §3①、状态-Q §3、通宵总结 一/二、总账 §1 D5】

### 3.3 角色渲染与交互

**（1）概率状态机 · 38 节点 / 92 边**

- 把上游行为图**机械提取**成 `static/kurisu/statemachine.json`，页面内联播放器 `fetch` 它并接管"播哪一段动作"。
- 实测读数：`node_count=38`、`edge_count=92`、`len(nodes)=38`、`len(edges)=92`、
  **宿主触发入口 9 个**、`prob=0` 边 **9 条**、`has_mouth_profile=true` **16** 个、`mouthPatch` 非空 **38/38**、
  纯概率可达 **10/38**。九个人口实测值：`angry_trans, closed_eye_trans, sad_trans, shy_trans,
  speaking_short, speaking_trans, surprise_trans, thinking_trans, trans_smile`。
- 口径说明：早先多份文档写 **88 边**，是上游旧口径的过期转引；**实际产物是 92 边**。
  `loop_mode` 顶层字段为 `{loop:27, once_then_hold:13}`（合计 40），逐节点统计为 `loop:25 / once:13`（合计 38），
  差的两枚正是图外剪辑 `sad` / `smile`。【出处：项目介绍-给他人改写 §4.1、总文档 §5.2/§7.2、R1 §X3、N2】

**（2）透明 VP9+alpha 视频替掉精灵图集**

- 40 段角色动作由"PNG 图集逐帧贴图"换成"**透明 WebM（VP9 + alpha）逐帧 seek**"：
  `<video>` 离屏（**不进 DOM**）、`muted`、`playsinline`，逐帧 `seek` 后 `drawImage` 到 canvas；
  视频第 i 帧 == 图集第 i 帧（单帧时长取 `frameIntervalMs`，不是容器 `duration`）。
- 体积：40 组 `webm 8,763,277 B + poster 779,892 B = 9,543,169 B`，替代图集 `71,061,412 B`。
  主口径用**公平口径 5.42×**（同集合、同档重算：`9,315,889 ÷ 50,492,702`）；
  **名义 7.45×** 只能作为另一口径括注 —— 分子 40 组含图外的 `sad`/`smile`，
  分母里混了只覆盖 6 个剪辑的 hi 档，集合与质量档都不同。
- 画质自检 **40/40**：alpha MAE 均值 0.1889（最大 0.2511）｜RGB PSNR 均值 37.09 dB（最低 35.85）｜
  边缘 NCC 均值 0.9965｜帧数 7672/7672｜零区泄漏全 40 组共 14 像素。
- 分辨率 **268×360**（原 medium 134×180 的 2 倍边长 / 4 倍像素），统一 `pad=764:1028:100:0:black` 回画幅。
- 路线证伪：AV1+alpha 在 Chromium 的透明解出率 **0.0%** ⇒ 只能走 VP9；
  双拼 mp4（yuv444/420）alpha MAE 0.69~1.05，比 VP9 路线差 3.7~5.6×。 【出处：项目介绍-给他人改写 §4.2、总账 §2.3、R1 §X2、总文档 §7.3】

**（3）按需解码 / 显存与内存策略 / 低端设备自动降级**

- **降级链** `video → 图集(boot→hi) → poster 静帧`；单剪辑解码失败或 404 ⇒ 该剪辑**永久降级、不每帧重试**。
- **连续 2 个剪辑解不出 alpha ⇒ 整站回 pixel**（等于逐像素回退到接通前的图集轨）。
- **同时存活 `<video>` ≤ 4 枚 + LRU 淘汰**（同一个剪辑只占 1 枚）。
- **首屏零新增字节**：清单与 40 组视频**全部懒加载**，首次手势前只取"当前该上屏的那一枚"。
- **低端与省流判定**：`saveData` ∥ `effectiveType≈2g` ∥ `prefers-reduced-motion` ∥ `deviceMemory<=4`
  ∥（VP9 `canPlayType` 与 `MediaSource.isTypeSupported` 都为假）⇒ **命中任一条即走图集**，
  并把降级原因写进 `window.__xkVid.reason`，现场排障可直接读。
- **总开关** `<html data-xk-kurisu-mode="video|pixel|off">`，可被 `?xk-kurisu-mode=` 与
  `localStorage['xk-kurisu-mode']` 覆盖。 【出处：项目介绍-给他人改写 §4.3、_dev/gen-demo-pages.py L1669-1690】

**（4）眨眼 / 视线跟随 / 静音随机口型**

- **眨眼**：眼皮走"锚点 + 小补丁"同构做法 —— `static/kurisu/eye/idle1.json` + `eyes.closed.webp`（**4,322 B**，
  不新增渲染素材、不污染继承基线）；相位照抄上游 E-mote 六档预设的「標準」档，
  实测 **闭 106 ms / 持 53 ms / 开 106 ms**，间隔 **0.5~3 s 随机**。
- **视线跟随**：以眼睛锚点为基准的独立差分通道（否则会被表情时间轴覆盖回 0），
  实测参数 **±200 增益 / ±100 钳制 / 120 ms 平滑**。
- **静音随机口型**：无语音时给嘴部补丁层喂低幅随机值，让静止画面仍"活着"。
- **工程闭环**：这批改动的补丁 json 文件名曾不符播放器契约，导致**各项指标全绿但屏幕上不可见**；
  改名对齐后，**同帧像素 A/B 强差异 0 → 2575**（这就是"之前没生效"的硬证据）。 【出处：资源盘点总览 §④、动画第二批实施件 L100、通宵 §二4、总账 §2.2】

**（5）点头像切换动作并出声、长按开关面板（8 情绪 + 常用动作）**

- **交互**：**点击头像** ⇒ 切换到一个具体动作**并同步出声**（动作与语音成对触发，不各说各话）；
  **长按头像** ⇒ 开关动作面板；面板内容为 **8 套情绪头像** + 一组**常用动作**入口。
  **8 情绪的素材口径**：上游陪伴包提供 **8 情绪 ×（idle / speaking / static）** 已是 webp + manifest，
  可按名直接拼出；面板按钮由标记驱动，加一项只需改标记、无需改 JS。
- **情绪 → 动作映射**由"情绪名 → 动作键"的适配表完成（例：`sided_surprised → surprise_trans`），
  与状态机的宿主触发入口一一对应 —— 这也是"点一下就演对"的关键：情绪入口 `prob=0`，
  必须由宿主显式触发，不能靠概率游走到达。 【出处：动画与语音实现规格 §（素材表）、审计-新外壳 §53、主页实现方案 §99、总账 §2.2】

**（6）手机与桌面两处入口**

- **桌面**：角色在 CRT 场景内，右侧/底部为信息面板与对话区；**手机**：底部通栏的"手机 + 助手"
  卡片形态（头像 + 一句 + 折叠），资源与桌面**共用同一份**头像图集。
- 移动端三处硬伤的修复读数：横向溢出 **245/230/206 → 0**；
  三视口（375/390/414）× 四页实测 **溢出 0 / `dockInView true` / `navMinTouch 45` / console 0**；
  改动全部包在 `@media (max-width:980px)` / `(max-width:520px)` 内，**桌面端零像素变化**。
  溢出判据用 **`visualViewport.width`**（`innerWidth` 在窄屏会被内容撑宽 ⇒ 判据失效）；
  触控目标统一 `min-height:44px`（实测最小 45px）。 【出处：通宵 §四①、布局检查与优化方案 §3、shell-style.html L295-322】

### 3.4 语音

**（1）本地克隆的固定台词**

- 用 **GPT-SoVITS v3**（开源项目，我们用其模型与推理链路、**不改算法**）+ **LoRA rank32** 在自家
  RTX 3060 Laptop 6GB 上合成日语语音，推理侧 `SDPA` + **CUDA Graph / static-KV**；
  后处理链 = 裁静音(−45dB) → 响度闭环 **−16 LUFS** → 首尾 **40ms fade** → m4a(AAC 48k) + webm(Opus 40k)
  → **口型包络从最终编码文件重算**。
- 实测：**RTF ≈ 0.98**（60/60 成功、总 279.4 s、平均 4.66 s/句、最长 10.39 s）；
  **torch 峰值 2070.5 MiB**（含桌面 4336 MiB，基线 1751 ⇒ 仍余约 1.8 GB）；本地成本 **¥0**。
- 走 `--lang 日文` 路线：**不需要 BERT**（中文路线要 1.2 GB BERT，峰值 2647 MiB；日语峰值 2084 MiB）。 【出处：项目介绍-给他人改写 §4.9、总账 §2.4、总文档 §7.4】

**（2）原声优先**

- 站主提供的原声素材包**全量索引、指纹去重、入库**：
  去重口径 = 时长 + 首尾各 0.5 s 的 8k 单声道波形 sha256（**不按文件名**）。
- 实测：4 档共 **5640 条**、ffprobe 失败 0；**3393 个唯一指纹 / 2247 条重复**；
  原声 **484 条**中 **481 条可播 quote + 3 条响度隔离**（`loudnessOutlier`）。
  包名自述"约 59 分钟"与实测不符：`001` 实测 **4132.4 s = 68.9 分钟**，以实测为准。
- **原声优先于合成**：同一入口先查原声，命中即用原声；刻意**不做降噪 / 高通**，保留口气与底噪。
- 真峰闭环（本项目最有技术含量的一处自我纠错）：对**最终分发文件**实测真峰与响度并回写脚本 ——
  缺陷时原声 18 条 + 合成 8 条的最终 m4a 真峰曾 > −1.5 dBTP（**最差 −0.37 dBTP**）；
  从 raw 母带重建后 **原声 484/484、合成 150/150 全部 ≤ −1.5 dBTP**（真峰 max = −1.50）；
  `--selftest` 响度极差 **0.06 LU**；线上 12 句**一个字节都没改**（只改脚本）。 【出处：台词库扩容与合成交付 §4.1~§4.3/§5.5/§5.6、状态-S、项目介绍-给他人改写 §4.11】

**（3）导航时介绍板块**

- 监听路由变化（`hashchange` 与 SSR 落点），每进入一个板块就播该板块的**介绍语音**，
  并同步显示中文字幕；四板块（主页 / 监测中心 / AI 问答 / 笔记）各自一句。
- 台词键与板块一一对应（`nav_home` / `nav_monitor` / `nav_ai` / `nav_notes`）；
  已作废的两个旧板块键不再引用。 【出处：台词库扩容与合成交付 §5（导航板块语音）、状态-Q §4-④】

**（4）对话同步**

- 语音与字幕**同帧起**：字幕由 `zh` 字段驱动、音频由 `ja` 字段驱动，两头对齐同一条 `lineId`。
- 台词库是双语字段结构：`ja` 送 TTS / `zh` 做字幕，另设 `ttsJa` 假名兜底
  （含人名「牧瀬紅莉栖」的 3 条必须走它，因为日文前端会把人名读错）。

**（5）防复读选句**

- 同一入口连续触发时不让同一句被连着播：语义筛子集 → **排除最近 N = min(4, 组内条数−1）**

  `localStorage` 会状态打架）。
- 实测验收：补丁 `git apply --check` 退出码 0；无头验收 **7/7 PASS**

### 3.5 对话

**（1）主页底部输入栏**

- 主页底部常驻一条输入栏，打字提问后直接进入她的对话流；输入栏与内容页共用同一套外观与提交逻辑。

**（2）打字提问 → 真实检索链路**

- 页面调 `POST /api/public/ask`，后端走真实检索：**BM25 稀疏 + 稠密向量双路召回 → RRF 融合（k=60）→ 轻量重排**；

- 重排器是**纯 CPU 的 IDF 词袋打分器**（无模型推理）—— 因为 srv1 是 2C2G，装不下 Cross-Encoder；
  既有消融显示**排序已不是瓶颈**（28/28 召回、MRR 0.9821，当前默认配置即全表最优）。
- 观测延迟：单次问答 **1.3 ~ 5.8 s**（6 条样本）。 【出处：后端问答能力升级方案 §2.4、后端功能与博客展示规划 §2.4、总文档 §7.5】

## ④ 技术实现

> 统一写法：每块按「**做了什么 → 技术选择 → 为什么 → 量化结果**」四段。量化结果**只用真实读数**。

### 4.1 渲染管线

- **做了什么**：把上游行为图机械提取成运行时清单，页面内联播放器按清单驱动"播哪一段动作"；
  渲染层做"可插拔 + 可降级"的一段模块，视频出不来就由图集继续顶。
- **技术选择**：`<video>` 离屏（不进 DOM）+ 逐帧 `seek` + `drawImage` 到 canvas；
  降级链 `video → 图集(boot→hi) → poster 静帧`；同时存活 `<video>` ≤ 4 + LRU。
- **为什么**：图集是全帧整幅位图，动作越长体积越爆；视频有帧间压缩且浏览器原生解码（不用 WebCodecs）；
  AV1+alpha 被实测否掉；两枚 `<video>` 交替方案被否掉（同剪辑两枚各自 seek 会**帧序打架**），
  改用"poster 顶位 + 解好的帧搬进离屏 canvas"。
- **量化结果**：40 组 **9,543,169 B** 替图集 **71,061,412 B**（公平口径 **5.42×**，名义 7.45×）；
  分辨率反而升到 **268×360**；自检 **40/40**（alpha MAE 0.1889 / PSNR 37.09 dB / NCC 0.9965 / 帧数 7672/7672）。 【出处：项目介绍-给他人改写 §4.1~§4.3、总账 §2.2/§2.3】

### 4.2 状态机（行为与表现的解耦）

- **做了什么**：把"她什么时候动、动哪一段"从页面逻辑里抽出来，变成一份**数据清单**；
  页面只负责"按清单取帧、画帧、报状态"。
- **技术选择**：节点 = 剪辑、边 = 带 `prob` 的加权转移，`prob=0` 的边专用作**宿主显式触发入口**；
  清单生成器 `_dev/build_statemachine_manifest.py` 从上游 `graph_config.json` **机械提取**
  并补上图集页信息与真实字节数；页面侧另有显式开场状态机 `window.__xkBoot={phase,t0,marks,log}`。
- **为什么**：上游图里大量过渡动作没有"概率入口"，只有宿主点一下才该出现（说话、惊讶、思考）；
  同时**只提取、不重画**，保证与上游一致；清单与生成器同时入库，避免"手改产物被下次生成冲掉"。
- **量化结果**：`node_count=38` / `edge_count=92` / 宿主入口 **9** / `prob=0` 边 **9** /
  `has_mouth_profile` **16** / `mouthPatch` 非空 **38/38** / 纯概率可达 **10/38** / 图外剪辑 `["sad","smile"]`；
  "新增动画"用倒放实现（`key_point_to_thinking` = `thinking_to_key_point` 倒放），**逐帧 diff 0 ⇒ 0 新增字节**。
- **工程闭环（一次真事故）**：生成器补丁的守卫**比错了键**（拿"边端点名"去比"节点 id"），
  新增 4 条边被**静默丢弃**、边数退回 88 且不报错；改为比 `clip` 并对非法端点直接 `raise SystemExit`
  （把静默变成硬失败）后，**92 边且幂等**。【出处：项目介绍-给他人改写 §4.1/§7.5、总账 §2.2、状态-Q §3】

### 4.3 语音工程

- **做了什么**：在自家 6GB 笔记本上跑通日语 TTS 批量合成，做成可复现管线；
  并把"响度与真峰"的验收口径从母带搬到**最终分发文件**。
- **技术选择**：GPT-SoVITS **v3**（LoRA rank32）+ `SDPA` + **CUDA Graph / static-KV**；
  情绪路由 `--emotions on`（v3 专有）；后处理链 = 裁静音(−45dB) → 归一到 **−16 LUFS** →
  首尾 **40ms fade** → m4a(AAC 48k) + webm(Opus 40k) → **包络从最终编码文件重算**
  （`mouthValue = clamp(RMS(10ms 窗) × 3.75, 0, 1)`，首窗保底 0.12，停止时发 0）。
  台词双语字段 `ja`（送 TTS）/ `zh`（做字幕），另有 `ttsJa` 假名兜底。
- **为什么**：`--lang 日文` 路线不需要 BERT（中文路线要 1.2 GB BERT，峰值 2647 MiB）；
  CUDA Graph 预捕获固定形状桶（448/512/768/128/256/1024 六桶全成功）换掉每句重算的开销；
  口型必须与**实际播出的音频**对齐，而不是与母带对齐。
- **量化结果**：**RTF ≈ 0.98**（60/60、总 279.4 s、均 4.66 s/句）；**torch 峰值 2070.5 MiB**；
  响度 **−16.35 ~ −15.95 LUFS**（极差 0.40 LU）；包络与线上 12 句**逐点 100% 一致**；
  真峰闭环后 **原声 484/484 + 合成 150/150 全部 ≤ −1.5 dBTP**（max −1.50；`--selftest` 极差 0.06 LU）；
  本地成本 **¥0**、云端兜底 **¥0.0065/句**（命中磁盘缓存 = ¥0）。
**真实事故与根因（两条，都实测到了）**：`alimiter` 压的是**采样峰**，对已贴满 0 dBFS 的素材**是空操作**；
旧口径的 `m4a.lufs` 又是 **fade 之前**测的 ⇒ "母带合规 ≠ 上线文件合规"。失败的两版也如实记：
v1 在 20 条里只修好 15 条、1 条反而更差；v2 仍剩 4 条不合规。
**CER 的四个数字（不许合并成一个）**：60 句库主口径 `cer_norm` **0.0683**（中位 0.0336、26/60 完全一致、
46/60 ≤10%）｜275 句库抽检**有偏置**（正式口径）**0.0970** / 同批无偏置 0.1052｜12 句 A/B 的 v3 **0.0235**
（v2Pro 0.1228）。偏置词表是 103 个**站点真实口径词**，**不含任何参考原文整句**（避免泄题）。 【出处：项目介绍-给他人改写 §4.9~§4.12、总账 §2.4、台词库扩容与合成交付 §5.3/§5.5】

### 4.4 后端与隐私闸门

- **做了什么**：公开面问答走真实检索链路、答案带引用与状态标注；把"调用者本人地址"与

### 4.5 发布工程

- **做了什么**：本机构建 → 打包 → 远端校验 → 原子切换；并保证"重复发布不会动线上"。
- **技术选择**：三道门禁（资产断言 / 首屏字节预算 / SSR 契约）→ `hugo` 构建 → tar → `scp` →
  远端 `verify_tree` + 回环自检 + **原子 rename** + 切软链；**幂等判据 = 整树内容哈希**；
  发布按精确 ref；`KEEP=4`；备三档回滚。
- **为什么**：静态站发布的"假成功"最伤 —— 脚本 exit 0、线上一个字节没变。真事故：一次纯资源发布
  （改播放器 JS + 新增 eye 素材）被判"无变化"，删掉暂存、`exit 0`，**线上一个字节没换**；
  根因是幂等判据只看 `index.html`（首页没变 ⇒ 整批资源被当成没变）。
- **量化结果**：`assert-build` 实测 **17 项 / 0 失败**；首屏门禁 **PASS**（主页 840 KB、四内容页 185 KB、
  `/ai/` 1555 KB，预算 1650 KB）；SSR 契约 **全部 PASS**；发布包 tar 记录 81.86 MB；三档回滚耗时
  **秒级 / ~5 秒 / ~2 分钟**。如实记：**这条坑只修了一半** —— 接收脚本已用整树哈希，
  但发布脚本侧仍算 `index.html` 的 sha256，仍可能给出误导性的字节对比。 【出处：项目介绍-给他人改写 §4.20~§4.22/§7.1、通宵 §二1、状态-Q §3、R1 §N3】
