### S1 · 事实快照机制 `docs/facts/<UTC>.json` —— 终结"实测即过期"

**解决**：X5 / V16 / V17（25 分钟内 3 次发布，所有"当前版本""页面字节"瞬间失效）

**做法**：
1. 新增 `_dev/snapshot-facts.py`（只读），一次跑完并落盘：
   ```
   {
     "snapshotAtUtc": "...", "snapshotAtLocal": "2026-10-16 00:37:23 +0800",
     "git": { "head": "4ae5662", "dirty": false },
     "srv2": { "release": "site-20261016-003417",
               "releasesKept": [ ... ],
               "pages": { "/": {"code":200,"bytes":63811}, ... } },
     "srv1": { "publicGetEndpoints": [ 9 个, 含 code/bytes ],
               "adminProbe": {"/api/admin":401, ...},
               "health": { "alertsMockEnabled": true, "buildSha": "..." } },
     "assets": { "kurisuBytes": 91818871, "kurisuFiles": 274, ... },
     "gates": { "assertBuild": {...}, "firstScreen": {...}, "ssrContract": {...} }
   }
   ```
2. 落 `docs/facts/<UTC>.json` + 覆盖 `docs/facts/latest.json`。
3. **文档纪律升级**：总文档里所有"当前值"一律写成
   `{{facts.latest.srv2.release}}` 形式的**占位 + 命令**，不再写死数字。
4. 发布脚本第 0 步自动刷新快照（这样"线上是什么"永远有据可查）。

**自检**（我这轮真的跑了，脚本自身出过两个错）：
- ~~Bug A：`print()` 里三元表达式括号位置错了~~ → 已修（R1 首跑输出异常，重写了 ⑤ 段）
- ~~Bug B：`keypath.lower()` —— keypath 是 tuple，没有 lower~~ → 已修为 `'/'.join(keypath).lower()`，重跑退出码 = 1 ✓
- **仍存在的局限**：脚本只查"文件是否存在"，**不校验内容哈希**。若某个 patch.webp 是空文件或错图，仍会漏。⇒ 下一步加 `size>0` 与可选 sha256 基线。
- **与红线的关系**：无冲突，纯只读。
- **更优解**：把快照做成**发布产物的一部分**（`/opt/secagent/site/facts.json` 随站点一起发布），
  这样线上站点自带"我是什么版本、什么时间构建的"可验证证据，比放在仓库里更硬。

### S3 · 把"截断值/上限值"显式标注做成**字段级契约**（R-COUNT-2）

**解决**：X12（`honeypot.total=10000` 已上屏）

**做法**：
1. 后端（不在本仓库，需提单）：`honeypot` 响应增加
   `{"total":10000,"totalIsCapped":true,"totalCap":10000,"connections":267}`
2. 前端（本仓库可立刻做）：`api-bind.html` L167/L209 的 `fmt(hp.total)` 改为
   - 优先 `hp.connections`（真值 267），或
   - 显示 `≥10,000（统计上限）` 并加 `title` 说明
3. 门禁：新增一条断言 —— **扫描产物里不得出现"把疑似上限值当前值展示"的模式**（简单版：禁止直接渲染名为 `total` 且等于 10000 的值）。

**自检**：
- 会不会误伤？`windowSize=200` / `todayInWindow=200` / `sampled=800` 也是窗口值。⇒ 契约应统一：
  **所有带窗口/上限语义的字段必须成对出现 `xxxIsCapped` 或 `xxxWindow` 描述**。
- 与 D4 完全一致（D4 本就要求"上限值必须显式标注"）。
- **更优解**：干脆在前端**不显示任何 `total`，只显示带窗口描述的量**（如"最近 200 条窗口内"）。
  这样从机制上杜绝了"拿上限当真值"的可能。

## 3. 【创新组】三条能让这个项目**从"像样"变成"有辨识度"**的设计

> 共同特点：**成本极低（都不需要 GPU/后端改动），但都能把"数据是真的"这个卖点从口号变成可验证的事实**。

### ★ S7 · "数据溯源"角标：让每个上屏数字都可点击回溯

**问题**：现在评审者只能"相信"页面上的数字是真的。

**做法**：页面右下角一个 `真` 字角标，点开后展示本次页面加载的**数据溯源面板**：
```
数据源  : https://demo.xiaokeqing.cn/api/public/overview
取数时间: 2026-10-16 00:37:23（快照 15s）
字段    : alerts.bySource[1].count = 126
掩码    : 来源地址前三段保留、末段 x（后端 masked=false ⇒ 前端兜底）
窗口    : 最近 200 条（已取满，实际更多）   ← 截断显式标注
```
- **实现**：`api-bind.html` 里每个绑定函数加一行 `trace.push({...})`，角标读取 `window.__xkTrace`。
- **数据全来自已有接口**，不新增任何后端依赖，不新增任何假数据。

**自检**：
- 会不会泄漏攻击源 IP？⇒ 溯源面板**只显示掩码后的值与端点名**，不显示原始值（与 §⑥-3 一致）。
- 会不会增加首屏？⇒ 面板 HTML 懒加载（点击时才插入 DOM），首屏 +0。
- **更优解**：把 trace 也导出成 JSON（`?__trace=1`），评审者可整包下载核对。

### ★ S8 · 状态机"可解释回放"：她为什么这么演

**问题**：38 节点状态机是项目里技术含量最高的部分，但**面试时讲不出来**——因为它只存在于 JSON 里。

**做法**：前端记录一次会话的状态迁移序列，输出成时间线：
```
00:00.000  idle                 (root, 概率游走 p=0.70)
00:03.240  idle → speaking_trans  (宿主触发: ask_success)
00:03.240  speaking_trans          (once_then_hold, 120帧 @47.6fps)
00:05.760  speaking_trans → speaking_med  (概率 p=0.55)
00:09.100  speaking_med            (hi 档可用 ✅)
```
- 一键导出 Markdown，直接贴进 README / 面试材料。
- **顺便解决 S5 的数据源问题**：情绪标签是否命中，可在同一条时间线里看到。

**自检**：
- 需确认宿主触发事件清单（9 个入口各自对应什么事件）⇒ 目前文档只给了名字（angry_trans / speaking_short / ...），
  **没给事件映射** ⇒ 这是 T8 接线前必须补齐的第 7 项检查。
- 无首屏影响（仅记录对象数组）。

### ★ S9 · "一行命令复现"评测包：把评测能力变成可交付物

**现状**：`scripts/eval/` 5 脚本 + 40 题库已跑通，但 **MOS/ABX 无真实评委**、**单套 ASR 无法分离系统误差**。

**做法**：
1. `scripts/eval/make_bundle.py`：导出一个自包含 zip
   ```
   eval-bundle-20261016/
     questions.json          （40 题 + 19 条应拒答标注）
     audio.sha256.txt        （60 句合成音频指纹）
     asr_cer_results.json    （三口径 CER）
     scoring_template.md     （人工打分表）
     REPRODUCE.md            （环境 + 命令 + 期望值）
   ```
2. **解决"单套 ASR"问题的最省做法**：不换 ASR，改用**同一套 ASR 跑两遍不同输入**做对照——
   - A：TTS 合成音频 → ASR → CER（含 TTS + ASR 联合误差）
   - B：**原声库 2735 条**（合法持有副本）→ 同一 ASR → CER（**纯 ASR 系统误差**）
   - ⇒ `A − B` 即为**可归因于 TTS 的误差上界**。
   - 这一步**不需要第二个模型、不需要云 GPU、不需要新授权**（原声库已合法持有）。
3. 评委数据：把 `mos_template.md` 变成可分发的**盲听网页**（本地静态页，零后端），降低招募评委的门槛。

**自检**：
- 原声库 2735 条是**不同文本**，与 60 句台词不一一对应 ⇒ 严格说 B 组不是"同文本对照"，
  只能做**语料级**的误差基线，不能做句级差分 ⇒ 结论必须写成"误差上界/语料级基线"，不许写成"精确归因"。
- 法律边界：原声库只用于**离线评测**，**不进公开站点**（与 §②-2 素材口径一致）。

**问题**：详版 §① 花了一整节解释"文档与线上不同步"，本质是**线上没有自我标识**。

**自检**：
- `/api/health` 无鉴权且暴露 `alertsMockEnabled`（详版 §⑤-5.5 已标记 ✗）⇒
  页脚**只取 buildSha**，**不把 health 的其他字段上屏**，避免把 mock 开关也暴露成"站点特性"。
- 与 D4 一致：全部为真实只读值。

## 5. 逐条回答详版 §⑩「请审查什么」的 6 个问题

### 5.1 架构是否合理？该拆还是该合？

**合，不是拆。** 但要把"三代"收敛成"一代"。

- 四层划分本身是对的，边界清晰、归属标注诚实（未见把上游成果写成自有，这一条做得比多数个人项目好）。
- **真正的问题不是层数，是同层内的并存**：③ 交互层里躺着 3 套渲染实现（xk-views / app.js+kurisu-player.js / xk-demo），
  只有第 3 套生效。⇒ **先删，再谈架构优化**。删完才是真的四层。
- ② 推理层同时承载"问答"与"决策"两条链：**建议合，但要在接口层分开**。
  理由：两者共用同一套 RAG 检索与护栏；拆开会导致两套护栏、两处 fail-closed，反而增加不一致风险。
  正确做法是**同一个入口、不同的输出契约**（问答 → 文本+引用；决策 → 严格 JSON + 白名单校验）。
- ①↔② 的"只读聚合（脱敏）"**不够**：实测 `ipDisclosure.masked=false` ⇒ 原始 IP 已到浏览器，
  脱敏靠前端兜底。⇒ 应加一层**边缘脱敏**（见 S3）。

### 5.3 数字是否自洽？（五组逐条核）

| 组 | 结论 |

### 5.5 风险排序是否合理？

**"备案排第一" —— 我认为不对，理由如下：**

备案是**长期不可逆收益**，但**不阻塞当下**：站点现在经 CF 隧道是**可用的**（四页全 200，[R1实测]）。
真正"现在就炸"的是 **X12（正在公开展示假数字）**——这一条直接打击项目唯一的卖点，
而且**修它只要改 2 行前端**，零成本、零风险、立刻生效。

**建议重排**：
```
① X12  截断值 10000 已上屏            （卖点被击穿；2 行修复；今天就能做完）
② X1   38/38 mouthPatch 断链           （T8 接线即 404；越晚修返工越大）
③ X11  alertsMockEnabled=true 未澄清   （同一卖点的另一半；一个问询）
④ X13  removalContact 指向空页面       （合规完整性；与 T27 同批）
⑤ 备案                                （长期收益最大，但不阻塞，慢慢办）
```
**关于 `/api/health` 无鉴权为何没进前四**：因为它是**信息暴露**类风险，
危害取决于"暴露了什么"——而它最有杀伤力的那一项（`alertsMockEnabled=true`）**已经被 X11 单独拎出来了**。
修完 X11 之后，`/api/health` 只剩构建指纹暴露，优先级自然下降。⇒ 原文把它单列是对的，只是**应与 X11 合并看**。

### 5.6 我们没想到的坑（原文 5 个角度 + 我补 3 个）
