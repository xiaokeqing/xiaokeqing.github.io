## 九、★P0 追加（2026-10-16 19:00~19:10 现测，由站主截图触发）

**现象**：`https://xiaokeqing.cn/alerts/` 上「实时攻击流 / 威胁等级 / TOP 攻击来源 / 24 小时时序」全部显示
`[读不到] /api/public/alerts 本次取不到（不可达或被拦）`，页面观感"加载很慢、读不到数据"。
**结论：这是真缺陷，不是环境问题；而且它不是"服务器慢"。**

| 层面 | 实测 | 判定 |
|---|---|---|
| srv1 本机回环（7 端点**并发**） | 全部 **200**，`alerts 19ms / audit 23ms / geo 23ms / honeypot 19ms / overview 12ms` | **后端没问题**（负载 0.12、容器 CPU 0.19%、内存 740MiB/1.5GiB、RestartCount=0） |
| 同一批经 Cloudflare（并发） | `kb 1.36s / geo 1.44s / audit 2.19s / webstats 2.51s / honeypot 5.43s / overview 7.36s / **alerts 8.97s**` | **慢在 CF→源站这条路** |
| CF 缓存策略 | `cf-cache-status: DYNAMIC`（API **完全不进边缘缓存**，每次都回源）；本次出口还命中 **LHR（伦敦）** 边缘 | 未备案 + 免费版 ⇒ 边缘选择极不稳定，国内访客的路径比这更差 |
| 前端超时（线上产物） | 数据绑定层上限 ≈ **20s**；`XK_ASK_TIMEOUT=2e4`；**无重试**（`parts.filter(degraded)` 命中 0）；无"保留上次数据" | 一次冷请求超 20s 或被拦 ⇒ 直接写"读不到"，且**不重试、不留旧值** |
| 前端超时（本地未发布 HEAD） | `api-bind.html:26` **`var TIMEOUT = 12000`**；**新增了一次重试**（`:736-739`）；仍**没有"保留上次数据"** | ⚠️ **按现状发布会让"读不到"更容易发生**（上限从 ~20s 缩到 12s） |
| 限流口径 | 响应头 `x-ratelimit-limit: 20`（公开面每分钟 20） | 429 会被前端归到"被拦"这一类 |

**与文档口径的冲突**：§⑤ 写"alerts/audit/geo/webstats 慢，4~30s ⇒ 前端 **20~25s 超时 + 重试 + 保留上次数据**"。实测只有"重试"在**本地未发布**版里做了，另外两项：上限反向缩到 12s、"保留上次数据"从未实现。**这条口径必须改，否则发布即倒退。**

**修法（按性价比排序，建议与批A合并）**
1. **前端（1h）**：`TIMEOUT` 12s→**25s**（别缩短）；保留重试；**补"保留上次成功数据"**（`sessionStorage`）⇒ 慢网最差是"稍旧的数据"，而不是一片"读不到"；把"取数中/重试中"与"读不到"分开显示。
2. **后端预聚合（2~3h，治本）**：alerts / geo / stats24h 这类"5 分钟窗口"的聚合**定时落盘成静态 JSON**，前端改读静态文件 ⇒ 可被 CF 缓存，把 1.4~9s 压到毫秒级，并彻底消除回源抖动。
3. **CF 侧（0.5h）**：给 `/api/public/*` 配 `Cache-Control: public, max-age=60, stale-while-revalidate=300`（现在是 DYNAMIC 全回源）。
4. **备案**：国内访问稳定性的根因，材料已备好（`docs/运维-T11-备案材料清单-20261015.md`）。

## 十一、P0 诊断结论：「监测中心为什么这么慢」（2026-10-16 19:10~19:20 五层实测）

**一句话**：**后端算得飞快（3~5ms），慢的 100% 在"回源路径 + 全栈不缓存 + 前端把 N 个来回串起来"。**

| 层 | 实测 | 判定 |
|---|---|---|
| ① 后端算力 | srv1 本机 9 个端点**暖态 2.9~5.3ms**；仅首次/快照过期时 0.69~2.96s（`alerts` 冷 2.20s、`honeypot` 冷 2.96s）；容器 CPU 0.17%、内存 738MiB/1.5GiB、load 0.06 | **不是瓶颈** |
| ② 后端→CF 的路径 | 同一端点**本机 3ms → 经 CF 0.94~2.60s**；连打 6 次 `0.96 / 0.96 / 1.27 / 1.47 / 3.27 / 3.68s`（抖动 4 倍）；建连 TCP 209ms + TLS 439ms ≈ **650ms/连接**；命中边缘 **LHR（伦敦）** | **主要瓶颈**：每个请求要付一个 0.65s 建连 + 1~2.5s 回源 |
| ③ CF 缓存 | 后端已给 `cache-control: public, max-age=15` + `etag`，但 `cf-cache-status: **DYNAMIC**` ⇒ **CF 完全不缓存**。原因：CF 默认只缓存带静态扩展名的文件，`/api/public/alerts` 无扩展名 ⇒ 每次都回源 | **可立刻改善**：加 Cache Rule 或改成 `.json` 静态路径 |
| ④ 站点 HTML | `/alerts/` 经 CF：TTFB **1.26~1.59s**、total 1.75~2.38s、42.5KB（Brotli，HTTP/2）；响应头 `cache-control: **no-cache**` | 每次访问都穿隧道回源 |
| ⑤ 前端行为 | 每个端点 fetch 带 `{cache:"no-store", credentials:"omit"}` ⇒ **浏览器也完全不缓存**，后端 15s/ETag 被前端自己废掉；7~9 个端点各 1~2.5s；单请求硬上限 **12s**；**无"保留上次成功数据"** | 一个请求抖动超 12s ⇒ 整块写"读不到"（＝你截图的现象） |
| ⑥ 素材 | `kurisu/` 共 **89MB**：medium 49MB / hi 20MB / video 9.3MB / avatar 1.6MB / voice 820KB；`/alerts/` 静态引用只有 `/js/kurisu-player.js`（146.7KB，样式与脚本都内联） | 弱网下与 API 抢带宽（角色线暂缓项，不影响 B 组） |

**结论 → 对应动作**
1. **③+①**：把慢端点**预聚合落盘成 `.json`**（带扩展名 ⇒ 可被 CF 缓存）或加 CF Cache Rule ⇒ 把 1~2.5s 压到边缘毫秒级。**这是治本，也是 B3。**
2. **⑤**：前端 `no-store` 改条件请求 + **保留上次成功数据** + 上限 12s→25s + 状态区分。**这是 B2。**
3. **④**：站点 HTML 的 `no-cache` 改为短缓存（如 `max-age=60` + 发布时刷 CF 缓存），或至少在站内做预取，减少"每次穿隧道"。
4. **②**：CF 边缘命中伦敦说明边缘选择对国内访客很不友好 —— 缓解靠缓存，根治靠**备案（E6）**。
5. **⑥**：素材瘦身属 D 组（角色线暂缓），不影响本项验收。

### 16.2 该怎么设计（原则：动作必须**承载信息**，且**不抢注意力**）
必须有 **触发源 + 优先级 + 冷却 + 抢占规则**，否则会乱动（人物崩坏）。建议的事件→动作契约：

| 触发 | 动作 | 数据来源（已存在） | 优先级 / 冷却 |
|---|---|---|---|
| 首次进入 | 开场亮相（**已实现**） | boot | 一次性 |
| 空闲 | idle 循环（呼吸/眨眼/注视跟随） | 已有（`blink`/`gaze`/`mouthIdle`） | 最低 |
| **正在取数** | `thinking` | api-bind 的"取数中"态 | 中，≥2s 才进（防闪） |
| **取不到 / 超时** | 困惑（`sad_trans` / `closed_eye_trans`） | `window.__xkStale.used` 非空 | 中，≥15s 冷却 |
| **被限流 429** | 无辜/举手 | `window.__xkStale.rateKeys` 非空 | 高，冷却 = `Retry-After` |
| **新告警出现** | 警觉/指向（配合实时攻击流） | `window.XK_FEED` 新条目 | 高，≥30s 冷却 |
| 用户提问 | 倾听 → 思考 → 回答（开口） | ask 流程（`idcard.html` 已有 speak） | 高 |
| 播语音 | 口型（**已接线**） | `audio.currentTime` | 最高（抢占一切） |
| 切 tab / 页面 | 转身 / 换场景 | hash / 路由 | 中 |
| 鼠标悬停角色 | 注视跟随（已有 `gaze`） | `mousemove` | 低 |
| 长时间无操作 90s | 打盹 / 小动作 | idle timer | 低 |

**为什么做（按价值排序）**：
1. **把技术状态可视化** —— 这是本站特有的价值：她"思考"=正在取数、她"困惑"=取不到、她"警觉"=有新告警 ⇒ 访客不读文字也知道系统状态
2. **人格一致性** —— 角色站里不动的角色就是一张图
3. **第一印象**（面试官场景）
4. **但绝不能抢注意力**：默认低频 + 冷却 + 不与阅读/数据争焦点 —— 这也是 R2 收敛当初删掉装饰动画的原因，**不要退回去**

## 十九、"口型达标"的正式验收判据与证据（2026-10-16 22:10 定稿）

**结论：验收判据拆成三条；① 已达标（可入 CI），② 是设计属性，③ 单列为可选门禁。此前文档里那个借来的「70~100ms / r≈0.51」作废（它出自上游作者录屏，不是我方实测）。**

### 判据①（**已达标，可入 CI**）：包络-音频一致性 ≤ 10ms
- 判据：每条台词的「包络覆盖时长（`envelopeValues × hopMs`）− 音频时长」的绝对值落在**一个包络窗**（≤1×hopMs=10ms）内
- 实测（**第一方，160/160**）：偏移 **0~+10ms，p50 +5ms**（existing p50 +6ms / synth p50 +5ms）；
  bank 自报路径与 sha256 **160/160 与磁盘一致**；明细 `E:\DeepSeek1\work\_ak\voice-recon\T4-lipsync-baseline.json`
- 复现脚本：`_ak/lipsync-baseline.py`（不依赖浏览器，**可直接进 CI**）
- 为什么这条是根：`mouthValue = clamp(envelope.values[floor(audio.currentTime*1000/hopMs)] × 3.75, 0, 1)`
  ⇒ 口型是**音频时钟的函数**（构造性对齐），所以"包络与音频时长一致"就是"口型不会整体飘"的充分条件

### 判据②（**设计属性**，非可调参数）：渲染栅格 ≤ 1 帧 + hopMs
- 判据：口型值在**同一个 rAF tick 内**算并绘制 ⇒ 从"音频时刻"到"屏幕像素"的量化误差上界 = **1 个显示帧 + hopMs(10ms)**
- 数值取决于显示器：60Hz ≈ **26.7ms**、120Hz ≈ **18.3ms**；headless 30Hz 实测 43.4ms **是环境上限，不是产品延迟**
- ⚠️ **本机无法给出"真机 60Hz"数值**：MCP 浏览器的窗口被遮挡 ⇒ Chromium 把 rAF **节流到 1Hz**（实测 1002.8ms/帧，
  即使加了 `--disable-backgrounding-occluded-windows/--disable-renderer-backgrounding/--disable-background-timer-throttling`），
  且 `document.hidden=false`。**这是环境产物，不许当结果写进交付。**
- 若要真机数值：需"可见、未被遮挡的窗口 + 真显示器"，或用带屏的本地探针（现有 `_dev/probe-lipsync.mjs` 是 headless 30Hz）

### 判据③（**可选门禁**）：可闻偏移（扬声器出声 vs 屏幕口型）
- 本机**测不了**：需要回环采集（WASAPI loopback / ffmpeg 同时录屏+录声后互相关），本机**无 ffmpeg**
- 处置：**单列为可选门禁**，不阻塞交付；要做时再引入工具链
