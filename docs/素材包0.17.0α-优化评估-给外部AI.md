## 1. 结论摘要（TL;DR）

```
可用的优化只有三条，且价值排序清楚：

① **新增动画（零字节）**：包里新增 `key_point_to_thinking`（120 帧 @8ms，once_then_hold）
   经逐帧比对 —— **与已有 `thinking_to_key_point` 的倒放逐像素完全一致**（mean_abs_diff = 0，含 alpha）
   ⇒ 只要播放器加"倒放开关"（约 6 行），即可零新增字节获得上游这个新转场 ✓✓

② **40 组视频：真正的优化点**（省 5~7 倍字节，画质更高）
   用同一把尺子（**每百万显示像素·帧的字节数**）：
      视频 38,711 B  ｜ 我们现有 hi 档（PNG 图集）197,399 B  ｜ 我们的 medium 档 279,147 B
   ⇒ 同显示尺寸下 **视频比 medium 省 7.2×、比 hi 省 5.1×**，且分辨率是 1x（`[包内自报]` 可见区 PSNR 39.9 dB）
   ⇒ 换算到我们的账：现在 37 剪辑 PNG 图集 **78MB** → 若换成 medium 分辨率视频，预计 **~7~10MB**
      从而"整体资产大降 + 可把所有剪辑发高质量档 + 首屏更省"
   ⚠️ 拦路石：现在的容器是 **IVF**（任何浏览器都不认 ✗），且 **alpha 是独立第二条 VP9 码流**
      → 必须 **remux 成 WebM（带 alpha）** 才能在 `<video>` 里播（本机当时无 ffmpeg，故未实测，见 §9）

③ **重新校色：不建议采用**（差异 0.23~1.08/255，肉眼不可辨），而且它带来一个**必踩的几何陷阱**（见 §4.2）

⇒ 一句话：**这个包没白下** —— 视频那条路有实质优化空间，新动画可以零成本拿到；
   但"更新美术资产包"这句话里**唯一不值钱的部分恰好是"校色"**。
```

## 4. 三个关键发现

### 4.1 校色幅度极小（`[实测]`）
抽 8 个剪辑解帧、按最优对齐逐像素比较：**RGB 平均绝对差 0.23~1.08 / 255**（同画布 idle 对照 0.232），
单点最大 46~67（混着两边各自有损编码的底噪）。
⇒ 判读：**"轻微偏色修正"级别，肉眼基本不可辨**。

### 4.2 ⚠️ 比校色重要得多：**40 个剪辑里 33 个画布被居中裁窄**（`[实测]`）
```
例：thinking_speaking1 764→564 ｜ speaking_loop1 764→500 ｜ sad/smile/shy 等 764→620
    trans_standby 764→636 ｜ idle_closed_eye 960→904 …
穷举偏移验证：裁切**严格居中**（(旧宽−新宽)/2，12 个剪辑全部命中；错误偏移的残差是 5~100 倍）
```
**为什么这是坑**：我们的播放器按"**高度 + 水平居中**"摆放角色（`kurisu-player.js` 落位逻辑），
若直接用裁窄后的帧，角色会**横向跳约屏高的 9.5%**（500px 宽屏 ≈ 48px）✗✗
⇒ 采用新帧的前提是：**先把画布居中补回旧宽度**（`pad764`），或**改播放器按 `opaque_bbox` 锚定**。

### 4.3 新增动画 = 已有剪辑的倒放（`[实测]`）
```
新增：`key_point_to_thinking`  120 帧 ｜ frameIntervalMs = 8 ｜ loopMode = once_then_hold
      KTX2 564×1028（= 旧 764 画布居中裁窄，每边 100）｜ KTX2 35,178,476 B ｜ 视频 3,720,008 B（2.00s）
抽 4 对 (KPT[i], TTKP[119−i]) 解帧比较：mean_abs_diff = 0.0000，max = 0（**含 alpha**）
```
状态机 diff（上游语义）：新增节点 `key_point_to_thinking`；把 `key_point_speaking → thinking_speaking1(0.5)` 这条边
改为**经过新节点**，并新增 新节点 → `thinking_speaking1(1.0)`；净 **37→38 节点 / 87→88 边**。

### 4.4 视频结构（`[实测]` 由 IVF 头 + 逐帧索引 + VP9 sync 校验得出，未实播）
```
40 组 = 80 个 IVF + 40 个 clip.json ｜ **7,672 帧** ｜ 合计 **205,599,227 B（196.07 MiB）**
编码：全部 fourcc VP90、**VP9 profile 0**、codec string `vp09.00.51.08`、bt709、**60fps**
尺寸：高一律 1028，宽 500~904（即被裁窄后的画布）
索引：80/80 逐帧索引扫描完整（声明帧数 = 实际帧数）｜35 组新编码 + 5 组复用
**能不能浏览器直接播：不能** —— ① 容器 IVF（DKIF）无浏览器支持
                              ② **alpha 是独立的第二条 VP9 码流**（需双流合成或重编成带 alpha 的单流）
```

## 5. 优化分析：视频 vs PNG（外部 AI 请重点审这一节）

### 5.1 同一把尺子的对比（`[实测 + 包内自报]`）
| 载体 | 每百万显示像素·帧 | 倍率 |
|---|---|---|
| **视频（1x，color+alpha）** | **38,711 B** | 1.0× |
| 我们现有 hi 档（PNG 图集，268×360 瓦片） | 197,399 B | 5.1× |
| 我们现有 medium 档（PNG 图集，134×180 瓦片） | 279,147 B | 7.2× |

### 5.2 换算到我们的实际账（`[推断]`，需要实测确认）
```
现在：static/kurisu（37 图内剪辑 medium + 6 段 hi + opening + 头像 + 场景）= 约 78MB
若把这 40 组视频重编成**我们 medium 档等效分辨率**的 WebM（带 alpha）：
   预计 ~7~10MB 量级（按 7.2× 折算）→
   · 角色资产从 78MB 掉到 ~10MB
   · 省下的预算足以**把所有剪辑都发 hi 档**（或保留 hi + 大幅提高画质）
   · 而且视频是连续帧，**动作更顺滑**（不再是"逐帧序列 + 节点硬切"）
```

### 5.3 必须解决的工程问题（给外部 AI 的挑战点）
```
① remux：IVF 双流（主旨流 + alpha 流）→ **WebM with alpha**（VP9 in WebM 支持 alpha；AV1 with alpha 亦可）
   需要 ffmpeg（本机当时没有，已另起一条线装便携版）
② 解码/渲染：`<video>` → `drawImage(video, …)` 画进我们现有的 canvas 层序（CRT 多边形内、字幕板之下）
   · 需保留：**静态回退**（缺视频/解码失败/省流量/`prefers-reduced-motion` 时回退 PNG 图集）
   · 需保留：`frameIntervalMs` 的 `Math.max(16,…)` 夹取口径、`once_then_hold`、
     `visibilitychange` 停 ticker **并清零时间累加器**（否则切回会跳帧）
③ 首屏：视频方案对首屏是**利好**（元数据+首帧很小），但要在门禁里量化验证
④ 预算：资产闸门 `assert-build.sh` 目前上限 **80 MiB**，`static/kurisu` 已用 **80,337 KB（余量 1,583 KB）**
   → 视频方案若成真，应**下调**资产总量而不是上调闸门（这是它与"全量重做校色"方案的相对优势）
⑤ 兜底与判据：**同一显示尺寸**下逐剪辑比对（一个剪辑 PNG vs 同剪辑 WebM），比"总量"和"肉眼"更可靠
```

## 6. 我们现有实现与约束（外部 AI 判断可行性所需）

```
渲染：单 canvas + DOM。层序 = 桌面底图 cover（零倍率）→ 氛围光 → CRT 多边形裁剪 →
      屏内：空房间底图 → <canvas> 角色（基底帧 + 闭嘴层）→ 字幕板 → 场景整图 → 扫描线/暗角
帧播放：`static/js/kurisu-player.js`（约 2188 行）—— rAF + 时间累加；图集 drawImage；
      `frameIntervalMs` 逐剪辑；12 个剪辑 `once_then_hold`；多分页图集（≤4 页）
状态机：`static/kurisu/statemachine.json` = 37 节点 / 87 边 / root=idle，
      **prob=0 的边 = 宿主触发入口**（说话/情绪/空闲/节拍，事件驱动，时间线记入 `__xkSm.hostTimeline`）
      · 概率游走只覆盖 9/37 个剪辑（`[实测]` 我独立模拟 2000 步），其余 28 个必须事件触发 —— 这是原版设计
      素材事实源：`docs/amadeus-research/data/statemachine.json` → 经 `_dev/build_statemachine_manifest.py` 生成产物
口型：16 个剪辑有 profile；闭嘴补丁 **34×18**（= 原版椭圆遮罩尺寸来源）；`mouthPatch` 带
      `overlay_entry` + `closed_frame_idx`（**不走上游 `argmin(openness)` 覆盖逻辑**）
      · 12 个"用自己的闭嘴帧"的剪辑用**小补丁**；4 个"借别的剪辑闭嘴帧"的用**原方案（截块+椭圆遮罩）**
      · 包络契约 `{sampleRate, hopMs:10, values[0..1]}`；mouthValue = clamp(RMS(10ms)×3.75, 0, 1)；阈值 0.08、首窗保底 0.12
声音：L1 固定台词 12 句（Opus/PCM 静态文件）+ 包络 JSON；autoplay 门控（手势前静默 + "🔊 点我开声"）
门禁：`scripts/assert-build.sh`（资产 ≤80 MiB、首屏角色 ≤1.5MB、bg.jpg sha256 不变、零 0 字节资产…）
      + `_dev/gate-firstscreen.mjs`（**真浏览器 CDP**，逐页首屏 ≤1,536KB，超预算 exit 1；有反例验证）
      + `_dev/check-ssr-contract.py`（六页 `data-xk-ssr` + `#xk-views`）
托管：站点与素材在 srv2（腾讯云），Cloudflare 隧道备份；**主域名直连 srv2**（2026-10-14 切换）
      `[实测]` 直连 **271~338 KB/s**（2MB 载荷），Pages 9.6~17 KB/s，经 CF 隧道 0~10.7 KB/s（**缓存命中也只有 10KB/s**）
红线：零第三方依赖（资源加载位站外请求必须 0）｜零造假（数字只来自真实接口，取不到写"读不到"）｜
      CSS 一律加容器前缀（曾因整份搬入 `.view{display:none}` 白屏过一次）｜推前必须看本地产物 + 截图
```

## 8. 需要拍板的点（我们内部的，外部 AI 可给建议）

```
1) 走 B 吗？（视频化）—— 它的收益是"资产降 7 倍 + 画质更高 + 动作更顺"，代价是播放器改造与解码风险
2) 若走 B：先做哪个剪辑？建议先 1 个（idle 或 speaking_med）端到端跑通（remux → <video> → alpha 验证 → 体积对比），
   再决定是否全量
3) 若走 B：medium 与 hi 两档都出，还是只出一档？PNG 图集是否保留为回退（我倾向保留，回退成本低）
4) AV1 with alpha 还是 VP9 with alpha？（浏览器支持面 vs 体积）
5) 闸门口径：资产总量上限是否**下调**（例如降到 40 MiB）作为"视频化成功"的判据？
6) 新包的 16 个新嘴型 profile（37×21 补丁）与 16 张整帧嘴型：**只有在我们采用新帧时才需要**，是否长期搁置？
```

## 9. 诚实边界（未验证 / 推断）

```
· 视频结论（编码、帧数、索引完整）来自 **IVF 头 + 逐帧索引 + VP9 sync code 校验** —— 当时**本机没有 ffmpeg/ffprobe**，
  **remux 与浏览器实播未实测**（现已在另起一条线装便携 ffmpeg 并做验证）
· 画质数字（PSNR 39.9dB 等）是 `[包内自报]`，**未独立复算**
· "78MB → ~10MB"是**按每像素·帧倍率折算的推断**，未实跑；实际还取决于 alpha 通道压缩率与目标分辨率
· 几何裁切结论抽样 12 个剪辑（不是 40 个全量）；但"严格居中"这一点在抽样里 12/12 命中
· 安装用的 uv 是本次新装的 0.13.0（CI 用 0.12.8）；`--no-sync` 在 clone 里留下一个空 `.venv`，未改 `uv.lock`
· 我们 staging 的图集脚本 `_kurisu-full\tools\12_web_atlas.py` 的剪辑清单来自缓存 `recon.json`（旧包条目表），
  **新增剪辑必须先刷 `00_recon.py` 或手塞 entries**（否则新剪辑不会进流水线）
```
