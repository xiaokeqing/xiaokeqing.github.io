        /alerts/  告警流 + 威胁等级 + TOP 来源 + 类型矩阵 + 来源国/ASN + 24h 时序

   ↓ 角色层：数字角色按状态机（38 节点 / 92 边 / 9 宿主入口）决定"演哪一段"

**链二 · 用户提问 → RAG → 回答 + 引用 → 字幕**

```

   ↓ 返回：answer + citations[] + state/stateLabel + quota{remaining}
        · 检索不到 ⇒ fail-closed 拒答（state=input-insufficient / rule-based）
        · 模型不可用 ⇒ state=model-failed，正文写明"没有结论"，前端不补答案

   ↓ 前端：按真实 state / stateLabel 驱动表情与动作（取不到就 normal，绝不猜）
        · 🔊 关（默认）⇒ 只出中文字幕，连 bank.json 都不取（返回 SOUND_OFF）
        · 🔊 开 ⇒ 走统一播放器 KurisuPlayer.speakGroup(...)：
            按 lineId 查 bank-merged.origfirst.json（原声优先 → 合成 → 只出字幕三级降级）
            → 播日语音频 + 口型包络驱动嘴部补丁层 + 同帧起中文字幕
   ↓ 三段留痕：回答 / 引用 / 工具调用（response-audit.json）
```

## ④ 已知弱点与取舍

> 每条四段：**现象 → 影响 → 为什么暂时这样 → 可能的改法**。
> **若只读一节，请读这节** —— 这是本文最该被打的部分。

**W1 · 手机（iOS / 微信）画质与内存**
- **现象**：iPhone Safari 连 `video/webm;codecs=vp9` 都不认 ⇒ 走 auto 降级进 pixel 档 ⇒ 画 `/kurisu/full/*.hi.webp`，单张**解码 35.5 ~ 53.3 MB**（opening 38.8 / idle 35.5 / speaking·thinking 53.3 MB）⇒ iOS 逐标签页内存上限把已解码位图丢掉 ⇒ 上屏**一整块灰**，同一页时好时坏；**微信内置浏览器更紧** ⇒ 更差。另有**"糊"**（不是"灰"）：321~380px 源单元被绘到 ≈800×1000 物理像素（≈2.5× 上采样），是**另一件事**。
- **影响**：曾出现"**脸空白 / 灰块**"的线上观感故障（站主真机截图）。
- **为什么暂时这样**：上游素材包最高的 `hi` 档就是全帧大图集；重做素材体系（矢量 / 更细分档 / 更高分辨率源）超出"只做管线不改美术"的边界。
- **已做的收敛** ✓：手机**强制只用中档**（同瓦片 321×432 / 380×290、24 帧、解码 **10.6~13.3 MB** ⇒ 内存降 3~4 倍、画质不变）；位图被丢弃的检测（`XK_TIER.sample(cv)` 抽检非透明像素计数）；**重试一次 ⇒ 仍失败降档**（hi→medium→poster），**宁可出静态帧、不许静默留灰块**；`probe` 采样改成**每次切剪辑都采一次**。实测：手机 hi 档请求 **0**（改前 android-375 / iPhone-375 各 1 次 1,028,055 B），5 个手机组合全部 `facePresent:true` / `noConsole:true`；桌面 `auto = hi` **逐字等于改前**。
- **仍非最优**：只是"降档 + 兜底"，**真机内存压力路径从未验证**（本机只能模拟视口，模拟不了内存压力）；"糊"**未解决**。

**W2 · 口型同步：判据未达标**
- **现象**：素材侧只有 **音频 10ms RMS 与脸部 ROI 逐帧像素变化的 Pearson r = +0.4698**，lag 扫描最佳 **r = +0.5123 @ lag = +70ms**（更宽 ROI：r = +0.3975 / 最佳 **+0.5430 @ +100ms**）；有效独立样本仅约 40 个、有效更新率约 20 Hz。
- **影响**：**"口型同步已实现"这个结论不成立** ✗ —— 原文自限定"不宣称已同步"。上游嘴部 A/B 像素差 MAE = 64.591 只能证明"**嘴在动**"，**不是"跟音频同步"**；两个数**必须一起引**，否则会被夸大成"官方已同步"。
- **为什么暂时这样**：位图帧素材 + 10ms 窗 RMS 包络驱动的补丁层，在**素材侧**就是这样；站点侧的做法是"从最终编码文件重算包络"（与线上 12 句逐点 100% 一致），但那证明的是"**包络与音频一致**"，不是"画面与音频一致"。
- **可能的改法**：① 定一条可判定的验收判据（例 `lag ≤ 40ms` 且 `r ≥ 某阈值`，且**限定 ROI 与样本量**）；② 更可靠的测法（排除 ROI 里混着的鼠标 / 换姿 / 扫描线，提高有效采样率）；③ 若素材侧做不到，把页面宣称降级为"嘴部随语音开合（未证明严格同步）"。

**W3 · 评测样本不足 ⇒ 指标不可作基线**
- **现象**：问答质量集 **40 条**（含 19 条应拒答），但**只采到 4 条有效**（无效 2 / 待跑 34），因为评测通道**当前仍打 `/api/public/ask`**，受公开池 **30 次/日** 限制；可答类**要点命中率 = None**（本轮 0 条有效可答答卷）；MOS / ABX 流程、脚本、题卷都跑通但**没有真实评委数据**（空模板）。
- **影响**：拒答 4/4、幻觉 0、注入护栏 1/1、引用覆盖 0.7500 —— **看着很好但样本量太小，不可作基线** ✗。复读率审计脚本已明确判定**不可作基线**（无会话标识、0 条多轮题），**谁都不许把它读成"模型复读率 55%"**。
- **为什么暂时这样**：评测通道没切 eval 池（`Bearer <APP_EVAL_TOKEN>` + `/api/chat`，**只改脚本**），且 40 题 ≈ 80 次 > 评测池余 31 ⇒ 需先提 `APP_QUOTA_EVAL_DAILY_LIMIT`。
- **可能的改法**：先切 eval 池（`S ≤0.5 人日`）→ 续跑 34 题（**≈2 天**）；所有指标**与样本量同写**（缺一即视为不合格报告）；`must_not_contain` 命中的用例逐条人工复核。

**W4 · 公开池 30 次/日、每 IP 6 次/分**
- **现象**：公开池 `public-demo` **30 次/日**，同 IP **6 次/分**、公开端点同 IP 并发 1、单依赖在飞 ≤2；**没有每 IP 日额度**。
- **影响**：访客**很容易撞额度** —— 一轮评测就能把当日 30/30 跑完（实测发生过）；单 IP 被限速但**换 IP 就能继续消耗**。
- **为什么暂时这样**：额度池是**成本护栏**；站主用途是"个人博客 + 面试演示"，且明确**暂缓**把额度 30 提到 60（理由：`没有每 IP 日额度会被单 IP 刷爆`）。
- **可能的改法**：① 补**每 IP 日额度**（T25-b，`S`；这是"提额度"的前置）；② 评测切 eval 池，**把评测流量从公开池彻底挪走**；③ 页面上"额度用尽"的文案与倒计时做得更显眼（已有，但可更显眼）。

**W5 · 无多轮记忆、公开面禁工具调用（刻意）**
- **现象**：公开面**不派发工具**（`toolExecutionAllowed=false` 恒真、双向拦截 + 构建期隔离测试），问"最近 24h 打了什么"**必然拒答**；公开面**无多轮记忆**（自用池 3~5 轮窗口是**登录面专属**）。
- **影响**：**体验受限** —— 问不出"基于真实数据的统计类问题"，多轮追问要从头说。
- **为什么暂时这样**：**这是刻意的最小 AI 自主权设计** ✓ —— ① 工具生效后每次提问模型调用 **2 → 3~4 次**，30/日只够 **8~10 问**；② 40 条题里 **0 条多轮题** ⇒ 收益**无法量化**；③ "匿名 + 无限记忆"是成本漏洞；④ 权限边界由**代码**保证而非提示词（穷举权限矩阵 + 枚举白名单 + 输出净化器 ⇒ 提示词注入只能改语气、改不了权限），这是项目在安全侧最硬的贡献之一。
- **可能的改法**：若确实要放开，**先量化收益**（设计多轮题进题库、写出可判分的期望）；工具调用必须先解决"调用次数 × 额度"的成本模型。

**W6 · 单机单点与链路带宽**
- **现象**：**srv2 同时承担「蜜罐 + 检测栈 + 站点托管」**；srv1 是 **2 vCPU / 1870 MB**，跑检测栈 + 公开只读 API（还把 Cross-Encoder 挡在门外）。链路实测：**直连 srv2 271~338 KB/s** ｜ GitHub Pages 9.6~17 ｜ **CF 隧道 0~10.7 KB/s**（**即使 `cf-cache-status: HIT`**）。
- **影响**：① 站点被刷会不会**连带蜜罐**？——**未压测** ✗，是已知的单点耦合；② CF 隧道 0~10.7 KB/s 意味着**站主本机对外可访问性实际很差**；③ srv1 的 2C2G 已把若干优化**从技术上排除**（本地推理、Cross-Encoder 重排）。
- **为什么暂时这样**：成本与简化 —— 两台低配云服务器是一个人的预算上限；站点与蜜罐同机是最省事的部署形态。
- **可能的改法**：① **站点托管与蜜罐分机**；② 补一次**压测**（验收标准里就写着"未压测"✗）；③ 弄清 CF 隧道慢的根因：**有没有排除"源站 nginx / systemd 沙箱限流"**？（系统沙箱是 `CPUQuota=25%` + `MemoryMax=128M`）；④ 备案后走直连 + CDN（见 ⑥ D4）。

**W7 · 未备案（CF 隧道）**
- **现象**：域名**未备案** ⇒ 只能走 CF 隧道。铁证（原始记录）：`curl -H 'Host: xiaokeqing.cn' http://43.143.114.79/` → **302 → `dnspod.qcloud.com/static/webblock.html?d=xiaokeqing.cn`**，443 直接 reset；**拦截按"访客来源"生效**（站主本机被拦，srv1 / srv2 侧不被拦）。
- **影响**：**国内访问与 CDN 受限**；从访客视角实测速度是 CF 隧道的 **0~10.7 KB/s**。
- **为什么暂时这样**：ICP 备案**材料已产出**，但**实际提交需站主本人操作**（站主口径"以后再说"）。
- **可能的改法**：站主提交备案 ⇒ 备案后可走境内直连 + 合规 CDN。⚠️ 本文**无法复现那条 302 铁证**（从 srv2 打只拿到 srv2 自己 nginx 的 `301 → https`），这与"按访客来源生效"一致，但该铁证**需访客视角复测**。

**W8 · 内容后台刚起步**
- **现象**：新文章靠**手写 md + 本地构建 + 发布链**；内容后台（上传 / 在线小改 / 列表 / 删除 / 图片压缩入库）**一行都还没写**，只有设计定稿。
- **影响**：站主**不能在任何设备上随手写文章**，必须回到这台 Windows 机器走完整构建 / 发布流程。
- **为什么暂时这样**：设计刻意**不做进 sec-agent 应用**（那是安全运营后端，加写文件能力会破坏 `PublicApiIsolationTest` 保护的边界精神）⇒ 要**独立进程 + 独立路由 + 与站点构建链对齐**，还依赖 ③b（后端令牌真正上线才能校验令牌）；且本机**无 GitHub 私钥**（`git fetch` = `Permission denied (publickey)`）。
- **可能的改法**：按定稿形态做独立进程；或退一步先做"本地脚本一键新建文章 + 预填模板 + 本地预览"的最小可用形态。

**W9 · 前端曾出现"花而不清"的优化（R2 的教训）**
- **现象**：R2 批次一口气加了骨架屏 / 空态统一 / 焦点描边 / 告警流级别色条与暂停 / spark24 刻度峰值 / SVG 甜甜圈 / 矩阵 hover 浮层 / tab hash 直达 / AI 引用卡展开 / 状态徽标四档 / 示例问题 chips / CRT 事件行 / count-up / 宽屏值班便签 / 笔记分类 chips（15 项）。
- **影响**：**信息密度上升后，可读性与"一眼看懂"反而下降** —— 视觉元素多了，但"这张卡在说什么、数字从哪来"变得不明显；这正是站主口中"**花而不清**"的那类优化。
- **为什么暂时这样**：R2 是一批交付，多块改动合并上线；站主随后明确要**收敛**。
- **正在收敛** ✓：R2 之后三批（批次 C 开场硬切、P0-① 手机内存兜底、批次 D 手机导航移头部）**都只做单点、可单独回滚、都带"改前/改后"证据**；P0-① 的纪律明确写"**桌面 auto = hi，逐字等于改前**""不改配色 / 背景 / 字体"。
- **这次教训（值得给评审方看）**：① 一批里**混装"功能"与"装饰"**会让回归面爆炸；② 视觉增强必须配**可断言的验收项**（R2 有 console=0 / 门禁 PASS，但**没有"信息可读性"的判据**）；③ 收敛方向应是"**减少同时出现的信息块**"，而不是"再加一层样式"。

## ⑦ ⭐ 请优化什么（给评审方的明确清单）

### A 类 · 架构与数据面

**A-1｜推理层同时承载"问答"与"决策"两条链**
- **现状**：同一容器里既有 RAG 问答链，也有 LLM 决策链（T14）；两条链采样参数已拆开，但**部署单元没拆**。
- **问题**：决策链 prompt 是 **Java 字符串常量** ⇒ 改它必须**重建整个镜像**（端到端不可用窗口约 30~90 秒），而问答链改动频率明显更高 ⇒ "改 A 必须重启 B"。
- **期望的优化方向**：给出"该拆还是该合"的判断依据（按**改动频率 / 故障域 / 资源占用**还是按**部署复杂度**？）；若拆，最小拆分面是什么（同进程两个 `@Service`？独立容器？）；若合，怎么把 prompt 从代码常量里挪出来而不牺牲确定性。

**A-2｜交互层同时有"旧 SPA 轨道"与"demo 内联轨道"**
- **现状**：`layouts/partials/xk-views/**`（旧 SPA 轨，6 文件）与 `layouts/partials/xk-demo/**`（demo 内联轨，8 文件）**并存**；`static/js/kurisu-player.js`（2,769 行）属旧轨但"选句补丁已应用"；`xk-kurisu-rail.html` 仍在仓库里，但 **demo 轨未 include**（grep 只命中 `spa-view-*.html`）。
- **问题**：**"改了没生效"** 是这条两轨架构的直接后果（历史事故：改了半天才发现改的是没被 include 的那一轨）。
- **期望的优化方向**：给出**判定哪一轨是活的**的可复现方法（而不是"看文档说"）；给出安全的合并顺序（先删旧轨还是先迁功能？）；如何处理"旧轨里还有唯一实现"（如统一播放器的选句逻辑）。

**A-3｜数据面是 18 个扁平文件，无 schema 与版本；端点白名单三处不一致**
- **现状**：出口是 18 个 JSON / JSONL 文件；前端 CORS 白名单 + 只读白名单是**手写清单**，与真实端点集合**三处不一致**（F 记 **12** 个 / L 的 T29 白名单记 **8** 个（漏 3）/ 双智能体规格记 **11**）。
- **问题**：① 没有 schema 与版本 ⇒ 字段缺失时无法区分"没接入"与"没发生"（项目为此专门立了 `coverage.status=NOT_WIRED` vs `gaps` 这条措辞规则）；② 三处手抄 ⇒ 必然漂移。
- **期望的优化方向**：给出"最小契约化"的做法 —— 是否需要一份机器可读的端点契约（路径 + 字段 + 版本 + 是否截断）？如何让**白名单与端点数从代码自动生成**？在"只读 + 个人站"前提下这个投入值不值。

**A-4｜单点耦合：srv2 同时承担蜜罐 + 检测栈 + 站点托管**
- **现状**：srv2 上 7 个容器（含蜜罐）+ 静态站点托管，同一台 4 vCPU / 3719 MB 的机器。
- **问题**：**站点被刷会不会连带蜜罐？** —— 验收标准里明确写着"**未压测**" ✗；且 srv2 一挂，蜜罐、检测、站点**三样同时没了**。
- **期望的优化方向**：给出压测方案（怎么在不影响线上蜜罐的前提下安全测"站点被刷时蜜罐与检测栈的响应"）；给出分机托管的最小代价与收益；以及"同机但隔离"（cgroup / 独立网卡 / 独立 nginx worker 限额）能否达到同等保障。

**A-5｜公开面额度模型缺"每 IP 日粒度"**
- **现状**：公开池 30 次/日 + 同 IP 6 次/分 + 同 IP 并发 1，**没有每 IP 日额度**。
- **问题**：单 IP 被限速但**换 IP 即可继续消耗**；一轮评测就能把当日 30/30 跑完（实测发生过）。
- **期望的优化方向**：给出一个**适合个人站**的额度模型（在多租户限流算法里选最简的一种）；并回答"**额度该按人、按 IP、还是按来源 ASN**"——注意本项目已有"保留前三段用于分组"的 IP 掩码口径，能否复用。

### B 类 · 前端体验与移动端

**B-1｜手机端画质与内存（"灰块"与"糊"是两件事）**
- **现状**：iPhone Safari 不认 `video/webm;codecs=vp9` ⇒ 进 pixel 档画 `hi` 图集，单张**解码 35.5~53.3 MB** ⇒ iOS 丢位图 ⇒ 整块灰；已做"手机强制 medium（解码 10.6~13.3 MB）+ 抽检 + 重试一次 + 降档到 poster"。另有"糊"：321~380px 源单元被绘到 ≈800×1000 物理像素（≈2.5× 上采样）。
- **问题**：① **真机内存压力路径从未验证**（本机只能模拟视口）；② "糊"完全没解决；③ 现在有 boot/hi/medium/poster **四档 × 自动判定**，组合是乘性的。
- **期望的优化方向**：给出**在真机上可复现**的内存压力验证方法（不是"多开几个标签页"这种经验说法）；给出"糊"的可接受阈值判据（多少倍上采样以内算可接受）；评估"手机专用更低分辨率素材档"的收益，以及它与"不许擅自降质上游素材"这条硬口径的**冲突边界在哪里**。

**B-2｜"花而不清"：信息密度上升但可读性下降**
- **现状**：R2 一次性加了骨架屏、空态统一、焦点描边、告警流级别色条与暂停、spark24 刻度峰值、SVG 甜甜圈、矩阵 hover 浮层、tab hash 直达、AI 引用卡展开、状态徽标四档、示例问题 chips、CRT 事件行、count-up、值班便签、分类 chips（15 项）。
- **问题**：**视觉元素多了，但"这张卡在说什么、数字从哪来"更不明显** —— 站主称之为"花而不清"；且 R2 验收只有 `console=0` / 门禁 PASS，**没有"信息可读性"的判据**。
- **期望的优化方向**：给出一套**可判分**的"信息可读性"检查法（不是主观打分）；指出上述 15 项里哪些是"该留的核心"、哪些是"该撤的装饰"；给出**"一次一批"的粒度规则**（一批最多允许混装几类改动）。

**B-3｜登录入口的三个隐蔽入口是自创的安全机制**
- **现状**：`?admin=1` / `#admin` / **1.5 秒内连点头像 5 次** ⇒ 出现 👤；默认 `hidden`；20 张取证截图访客全 `loginHidden=true`。

**B-4｜可核验面板的徽章与真实接线脱节**
- **现状**：`/test/` 第⑤⑥⑦块仍标 `NOT_WIRED`，但统一播放器接线**已交付**（`playerAt≈1830ms`、`KurisuPlayer.speakGroup` 就位、`__xkId.errors` 全空）。

**B-5｜公开面 600 vs 1200 字符的口径漂移，且截断无提示**
- **现状**：前端输入栏按 **600 字符**截断、`XK_ASK_TIMEOUT=20000`；后端实测响应里是 `maxQuestionChars=1200` / `deadlineMs=25000` `[本文实测]`；文档写 1200/25s（那是 A3 的**目标值**）。

### D 类 · 安全加固面

**D-1｜`/api/health` 无鉴权且暴露构建指纹与 mock 开关**
- **现状**：**200 且无鉴权** `[本文实测]`，返回 `embeddedGitCommit` / `buildSha` / `artifactMd5` / `embeddedGitCommitTime` / `fingerprintIssues` / **`alertsMockEnabled: true`** 等；另有 `logsMockEnabled` / `documentVectors: 318`。

**D-2｜`api-bind.html` 四处仍输出完整攻击者 IP**
- **现状**：`api-bind.html` L167 / L223 / L276 / L335 仍打**完整 IP** `[转引自《功能模块规划》§⑤，本文未逐行复核]`；站主已裁定"**不算违规、非必须改**"（那是攻击者地址，不是访客地址）。

- **期望的优化方向**：给出判断 —— 对攻击者 IP 的掩码到底是**隐私要求**还是**展示习惯**？若属后者，能否直接删掉这条豁免、把口径统一？若保留豁免，怎么在页面上标注"此处为未掩码的攻击源地址"以免误读？

**D-3｜蜜罐 `total=10000` 是统计上限却按真实总数展示**
- **现状**：`api-bind.html` L167 / L209 仍 `fmt(hp.total)` `[转引]`；同响应里 `connections=267`、`logins=267`、`sampled=800` **三者互斥**；HANDOFF §3① 的修法是显示 `≥10000（统计上限）`。
- **问题**：这是**"上限值 / 截断值必须显式标注"**这条红线**当前唯一已识别的未达标项** ✗ —— 一个把截断值当真实数展示的页面，和整个项目"零造假"的立场自相矛盾。
- **期望的优化方向**：改动本身只需 **≤0.5h**，**问题不在改法而在判据** —— 请给出"什么情况下**必须**标 `≥` / `≤` / `上限`"的一般规则（除 `total`，还有哪些字段可能是截断值？`candidates=137`？`truncated=true`？）。

**D-4｜令牌只存 `localStorage`，且自用池是"软上限"**
- **现状**：前端令牌 `localStorage['xk-user-token']`；后端 `UserTokenService` 用 **sha256 恒定时间比较** + 每 IP 登录限速 + 失败计数短时封禁 + **未配置一律 fail-closed**；审计**只记长度、不记明文**（有哨兵令牌全路径测试）；自用池是**软上限**（默认 500，`tryAcquireSelfSoft()` **恒返回 true**，"只提醒不硬停"）。
- **问题**：① `localStorage` 里的长期令牌 = 任何同源脚本都能读；② 软上限意味着**令牌泄漏后的成本上限不存在**（设计上就是"站主自己不会被拦"）；③ `max_tokens=4000` 目前**只是口径声明、未真正生效**（模型出口读全局 `app.llm.max-tokens`）。
- **期望的优化方向**：评估"软上限 + 长期 localStorage 令牌"这个组合的真实风险（威胁模型：同源注入 / 设备丢失 / 浏览器同步）；给出**在不影响站主自用体验**前提下的加固方案；回答"令牌轮换的运维成本"能否降到站主愿意做的程度。

**D-5｜凭据与创作素材的授权边界**
- **现状**：角色素材授权 = "**非商业**技术学习 / 研究 / 演示"，商用需另议；而站点**公开可访问**（域名公开、仓库公开）；台词库里 **30 条 `quote` 引用原作用户台词**（逐条带 `source`，可随时下架）；原声片段**引自站主合法持有的副本**，只上传按站点规格重编码后的片段、**不做二次分发**；页面注明版权归原作者、无广告无收费、权利人要求即下架。
- **问题**：**"非商业学习 / 研究 / 演示" + "公开可访问"这个组合的法律风险该怎么定性？** 答案会直接决定"能不能上量、能不能放广告、能不能被搜到"。
- **期望的优化方向**：给出定性意见与**可执行的最小合规动作清单**（不要"去咨询律师"这种废话）；指出哪些现有做法**已经在降低风险**（逐条标明、可下架、不二次分发、无广告无收费），哪些是**新暴露面**（公开仓库里带素材？搜索结果可索引？）。

### E 类 · 工程效率与可维护性

**E-1｜发布脚本与接收脚本的幂等判据不同源（"假成功"只修了一半）**
- **现状**：接收脚本 `srv2-site-receive.sh` L171 `tree_hash()` / L175 用**整树内容哈希**；但发布脚本 `scripts/publish-site-to-srv2.ps1` L132 **仍只算 `index.html` 的 sha256**、L171-173 仍拿它和远端 `index.html` 比，不一致就 `Die`。
- **问题**：**"假成功"这个真实事故的根因只修了一半** —— 若一次发布"整树变了但 `index.html` 未变"，接收侧会正确切换，而**发布侧仍可能报错 / 给出误导性的字节数对比**。
- **期望的优化方向**：给出**两侧同源**的具体做法（判据函数怎么共享？远端算完回传还是本地算完对比？）；给出一次"纯资源发布"的**端到端复现与验收脚本**；指出还有哪些"两个地方各写一遍同一判据"的地方（提示：项目已因这类问题踩过雷）。

**E-2｜生成器范式：改页面必须改生成器，且有静默失败史**
- **现状**：`layouts/partials/xk-demo/**`（除 `test-lab.html`）是**生成物**，源在 `_dev/gen-demo-pages.py`（**2,908 行**）；生成器还会**重写** `static/kurisu/statemachine.json` 与 `manifest.json`；补丁用**文本锚点切片**（`find` 两端锚点，任一端找不到就 `SystemExit`）。**静默失败史**：补丁守卫"比错键"⇒ 新增 4 条边**被静默丢弃**、退回 88 边且不报错。
- **问题**：① 2,908 行单文件生成器 + 文本锚点补丁，**脆弱性高**（历史事故：补丁锚点没含 `@media (max-width:980px){` 那一行 ⇒ **把媒体查询的左括号吃掉**，首页导航被压成顶部横条，靠取证脚本断言才当场抓住）；② 生成器"同时产出页面与数据" ⇒ 素材批次必须先确认闭环。
- **期望的优化方向**：给出把"文本切片补丁"换成**结构化做法**的可行路径（模板引擎？AST？带 schema 的配置？）及迁移代价；给出"生成器跑完该怎么自检"的清单（幂等、边数、关键标记存在性）；评估把生成器**拆成多个模块**的收益。

**E-3｜验收与取证脚本大量未入库（白名单制）**
- **现状**：取证脚本 `_dev/*.mjs`（`shot-batch-a.mjs`、`firstscreen-order.mjs`、`_probe-idcard.mjs`、`shot-batch-b-askbar.mjs`）**未入库** —— `_dev/*` 是**白名单制**，需要规划侧在 `.gitignore` 里加 `!` 行；`.gitignore` 由规划侧提交、站点线不动该文件。
- **问题**：**"验收证据的执行体不在仓库里"** ⇒ 别人拿到仓库**无法复现验收**；这是"站点线只能改代码、不能改 `.gitignore`"分工的副作用。
- **期望的优化方向**：给出"取证脚本该不该入库"的判断依据（可复现性 vs 白名单复杂度）；给出**最小的白名单策略**（按目录？按扩展名？按前缀？）；指出还有哪些"关键结论只有孤证、无法复现"的地方。

**E-4｜口径半衰期与"落笔即过期"**
- **现状**：审查方实测过"**同一个仓库在 25 分钟内被发布了 3 次**"；`docs/` 里**所有**文档写的线上版本都比实际旧（本文实测 `site-20261016-132449`，多份文档写 `125206` / `210145` / `001942`）；项目为此做了 `_dev/snapshot-facts.py`（产出带 UTC 时间戳的 `docs/facts/<UTC>.json` + `latest.json`）。
- **问题**：① 快照机制**存在但没被广泛使用**（多份文档仍写死"当前 release"）；② 行数 / 文件数 / 体积这类数**会漂移**（同一目录在总账与本文实测已差一截，因为期间加了 video / eye）；③ 文档互引时容易把"某时点的值"当成"恒定事实"。
- **期望的优化方向**：给出**"哪个数必须现测、哪个数可以写死"**的判据；给出让快照机制**自动生效**的做法（发布流水线里自动跑？文档里禁止写死当前值、只允许引用 `latest.json`？）；指出还有哪些"口径半衰期"陷阱（提示：`visualViewport.width` vs `innerWidth`、CDP `JSHeapUsedSize` 只到页面内口径 ~1%、容器 `avg_frame_rate` 不可信、`opaque_bbox` 实测不可用、断言项数 16/17/18 都可能出现）。

**E-5｜运维通道本身会被自己挡掉**
- **现状**：真实事故 —— 后端线在 srv1 上跑了一条"grep 整个容器日志"的 SSH 命令（输出极大），会话中途断开；**之后 srv1:22 对该出口 IP 一律超时**（最可能是 fail2ban）；交叉验证 srv2→srv1:22 可达、站点 HTTP 200 ⇒ **srv1 没宕机，是这个来源被挡**；**srv1:22 当前对本机同样被封** `[转引]`。
- **问题**：**"只读操作"同样会撞上主机侧防护，而且它挡的是运维通道本身** —— 代价比读不到日志大得多；且项目**所有需要 srv1 的动作**（后端重建、令牌写入、飞书通知补发）全部卡在这一条上。
- **期望的优化方向**：给出"远端只读诊断"的**安全操作范式**（怎么在 SSH 上做可能产生巨量输出的操作而不触发防护：先 `wc -l` 收敛？重定向到远端文件再取片段？`nice`/`timeout` 包装？）；给出**解封与防复发**的建议；以及"当运维通道本身是单点时"该有什么降级路径（srv2 跳板？带外管理？）。
