## 0. 设计总纲：一句话

**主页是一张"活着的书桌照片"，其它页面是一套「AMADEUS 终端」——角色以三种形态贯穿全站。**

- 视觉母题取自 Amadeus 原版 UI（站长截图）：深色玻璃面板 + 1px 霓虹细边 + 等宽字体标签 +
  状态灯 + 波形指示条（SPEAKING）。本站「科技模式」深色主题就是这个方向，本规划把它**系统化**为组件语言。
- 角色三态（新增的统一概念，〔现状〕已有雏形，本规划收口）：

| 形态 | 用在哪 | 组成 | 资产 |
|---|---|---|---|
| **HOLO**（迷你面板） | 主页底部输入条 | 头像 48px + 一句状态 + 输入框 + SPEAKING 条 | avatar/*.webp |
| **RAIL**（右栏面板） | AI 问答页 320px 右栏 | 全身 canvas + 字幕 + 状态 + 波形 | full/*.webp 图集 |
| **CHIP**（头像卡片） | ≤980px 所有页面 | 132px 头像静帧 + 一句话 | avatar/*.static.webp |

## 2. 主页界面规格

### 2.1 场景层与 DOM 层分工、层序

原则：**只有角色帧合成需要 canvas，其余全部 DOM**。canvas 是唯一无法用 DOM 高效完成的部分
（逐帧 drawImage + 口型双层），且它必须 `aria-hidden`。

| z-index | 层 | 技术 | 说明 |
|---|---|---|---|
| 0 | 桌面底图 desk.webp | `<img>` 零倍率 cover | 常驻最底层；**永不模糊、永不缩放动画**（与实拍透视冲突，一眼假）〔源码+实测〕 |
| 1 | 氛围光 high/low | 两张 `<img>` `mix-blend-mode:screen` | 呼吸交替，幅度 ≤6% 亮度；reduced-motion 时静止 |
| 2 | CRT 裁剪容器 | `clip-path: polygon(14点)`（manifest.scene.crtPolygon） | 唯一遮罩；不支持 clip-path 的浏览器整层降级（见 §4） |
| 2.1 | └ L1 空房间 backplate | `<img>` BG_empty | 她不在时的房间 |
| 2.2 | └ L2 角色 canvas | **唯一 canvas**，DPR 上限 2 | 基底帧 + 整帧闭嘴补丁（椭圆遮罩只露嘴）双层 drawImage |
| 2.3 | └ L3 字幕板 | `<img>` 原版金属板 | 固定几何，不随内容伸缩 |
| 2.4 | └ L4 场景整图 | `<img>` 6 活动位之一 | **角色已合成进画面**且自带玻璃罩/暗角/扫描线 ⇒ 必须压在角色之上〔源码〕 |
| 3 | 屏内 DOM：状态行 + 字幕条 | DOM 文本 | 定位在 CRT AABB 内（见 2.3） |
| 4 | HOLO 输入条 | DOM | 屏外，底部居中 |
| 5 | 导航浮条 | DOM | 顶部 |
| 6 | 主题/搜索（仅非主页） | DOM | 主页不出现 |

### 2.2 CRT 屏幕定位与缩放策略

- 基准：多边形 14 点来自原版 `crt_config.json`（基准图 1672×941，AABB 550..1136 × 195..638）〔源码〕。
- 桌面底图按 coverTransform：scale = max(vw/1672, vh/941)，居中裁剪。〔实测〕录屏第 2 秒配准 =
  原图 1.00 倍 cover、NCC 0.965，证明该公式复刻了原版取景。
- **硬不变量：CRT 多边形变换后的 AABB 必须完整落在视口内，四周各留 ≥16px。**
  桌面照被裁切是可以接受的（照片 cover 裁切自然），CRT 被裁切不可接受。
- **CRT 最小可读尺寸**：变换后 CRT 高度 <300px（超宽屏或窗口压扁）⇒ 放弃场景，直接进
  CHIP 布局（桌面窄窗与移动端同一套代码路径，少维护一条分支）。
- 角色落位照抄原版公式（〔源码〕renderer.js:797-825）：
  scale = min(W·0.64/764, H·0.90/1028)，x = 0.52W，y = bottom − 1.2%H，anchor(0.5, 1)。
  注意 W/H 取**多边形 AABB**而非视口，canvas 像素 = AABB × DPR(≤2)。

### 2.3 屏内/屏外元素规格

| 元素 | 位置 | 字号 | 对比度（目标 ≥4.5:1） |
|---|---|---|---|
| 屏内状态行（右上） | CRT AABB 内，贴多边形右上内缩 12px | 12px 等宽（--xk-mono） | 实测 12.10:1。做法：文字 #DFF3FF，底下垫 rgba(8,14,20,.55) 实底板，**任何文字不得直接压在场景图上** |
| 屏内字幕条（下） | 字幕板区域内 | 16px/1.5 | 实测 11.02:1，同上垫板 |
| HOLO 输入条 | 底部居中，宽 min(720px, 92vw)，高 48px | 输入 15px | 玻璃底 + 1px 边，占位字 #9FB4C8（对底 ≥4.6:1〔推断，交付时实测〕） |
| 导航浮条 | 顶部左或右（不挡 CRT 侧） | 13px | 沿用现状 token |

### 2.4 开场序列（修订现状）

〔实测〕录屏 0–2.033s 是**静止睁眼**特写；眨眼（k039–k042，全闭 ≈0.13s）在 1.31–1.41s；
"拉远"是场景硬切，无任何相机动画。

| 时刻 | 画面 | 依据 |
|---|---|---|
| 0 – 2.8s | look_at_CRT 特写循环，30fps，播到第 84 帧（眨眼自然落在 1.31–1.41s） | 线上 hi 图集已裁 84 帧 |
| 2.8s | **硬切**到 stand_thinking 中景（原版机制 = 最忠实） | 〔源码〕"no fade-out gap" |
| 2.8 – 3.15s | 可选：0.35s **线性 alpha 交叉**（全站唯一允许的角色↔场景过渡，须标注"属我方扩展"） | 〔源码〕_fadeDur=0.35 |
| 规则 | 0.35s 交叉**只允许用于开场→中景这一次**；节点之间、pose 之间一律硬切 | 〔源码〕 |

**会话级只播一次**（sessionStorage 标记）：重复访问/站内返回主页直接进中景。
〔待站主拍板〕若你认为"每次进站都要仪式感"，改为每天首次。

| 资产 | 预算 | 现状实数 |

## 4. 状态与降级（"用户看到什么"清单）

| 触发 | 用户看到 |
|---|---|
| API 取不到 | 状态行/字幕条对应位显示"读不到"（六态机读状态，已有）；绝不补数 |

## 5. 资产加载策略与总量判断

### 5.1 懒载顺序（运行时瀑布）

```
manifest.json（≤10KB，阻塞）
 → desk.webp + 字幕板（首屏渲染必需）
 → opening.boot（前 84 帧）→ 播开场
 → idle boot + poster（中景立即可用）
 → 【load 事件后】opening.hi 后台替换（提升下次开场/重播质量）
 → 【load 事件后】当前场景 backplate + 状态机 Top-2 概率剪辑的 boot
 → 空闲时段按出边概率预取下一剪辑（只留当前+下一个，内存纪律）
```

预加载只有 5 项：desk / 字幕板 / opening.boot / idle boot / poster。其余全部懒载。

### 5.2 总量口径：12MB → 96MB 的判断（〔待站主拍板〕，给建议）

| 方案 | 体积 | 代价 | 收益 |
|---|---|---|---|
| 维持 12MB | — | 39 剪辑只能进 ~3 个（现状 6% 帧） | 无 |
| **一期：精选 10 剪辑** | ≈18–22MB（〔推断〕按 60–80MB÷39×10） | 状态机低概率路径"见到 boot 低清" | 覆盖状态机 >95% 游走概率（自环 0.8 集中在少数节点〔源码〕scenarios.json）；git 历史可控 |
| 二期：全量 39 剪辑 | ≈60–80MB，上限改 96MB | git 仓库历史膨胀（每次改图集 +MB 级历史）；Pages 构建变慢；个人站低流量下绝大多数字节永远不会被请求 | 完整复刻；为将来"鼠标跟随/新状态机"留全素材 |
| Cloudflare R2 | 同左 | **违反零第三方红线**（新增站外域名），需站主显式点头 | 出网免费、不占仓库 |

**建议：分两期。** 一期只发精选 10 剪辑（按 statemachine.json 出边概率覆盖 >95% 选），
总量上限改 **32MB**；跑一个季度后若有"想看全 39 动作"的真实需求证据，二期全量并把上限改 96MB。
96MB 本身没有技术障碍（Pages 软限 1GB、单文件 <100MB、全懒载），**真正的代价在 git 历史**，
所以它值得"先证据后投入"。R2 除非站主愿意为"零第三方"开口子，否则不选。

### 5.3 素材口径（沿用既有流水线，不改）

39 剪辑 → 高度 320–360 WebP q78 alpha 保留 + boot 前 24 帧 + poster 静帧；
180 帧特写独立图集（开场专用）；口型补丁 = 整帧闭嘴图 + 椭圆遮罩（34×18 是遮罩尺寸来源）。

## 6. 可访问性与 SEO

- **角色 = 纯装饰**：canvas `aria-hidden="true"`；场景层配一句 sr-only 描述
  （如"插画：CRT 显示器中的实验室助手，当前在电脑前工作"）；她说话的内容全部镜像到
  屏内字幕条（真实文本、aria-live="polite"），屏幕阅读器读字幕即获得同等信息。
- **SSR 首屏**：包含 desk.webp、导航、HOLO 输入条、sr-only h1、noscript 纯文本降级块；
  **角色 canvas 不进 SSR**（无 JS 时 §4 旧浏览器降级生效）。SEO 正文靠 monitor/notes/about
  的 SSR 内容，主页只承担"门面 + 入口"。
- **键盘**：输入条、语音按钮、情绪控件全部可聚焦有焦点环；Esc 关搜索；`/` 与 Ctrl+K 唤起搜索（〔现状〕）。
- **对比度**：屏内所有文字"垫板 + 浅字"模式（§2.3），交付时给实测数字，不接受计算值。

## 8. 对现有方案的三处挑战

**挑战 ①：开场每次全量播放，且 hi 图集 1MB 悬在首屏预算边上。**
现状是每次进站播 180 帧开场（6 秒），hi 资产 1004KB。问题：重复访问者被强制看 6 秒；
1MB 资产一旦预载策略写错就顶爆 1.5MB 红线。
替代：开场裁到 84 帧（2.8s，眨眼已覆盖）+ 会话级只播一次 + hi 严格 load 事件后加载。
代价：无功能损失；需要 sessionStorage 一条逻辑（门禁补一项断言防回归）。

**挑战 ②：主页四层悬浮 UI 没有层级系统，输入条与 AI 页功能重复。**
现状：导航浮条 + 底部输入条 + 屏内状态行 + 屏内字幕条，各自为政；主页输入条与 #/ai 页
是同一 ask 端点的两个入口，访客不知道区别。
替代（本规划的核心新增）：主页输入条升级为 **HOLO 迷你面板**——照抄站长截图右下角的
HOLO-LINK：48px 头像（SPEAKING 时切 speaking.webp + 波形条）+ 一句话状态 + 输入框；
她的回答先进屏内字幕条，带"在 AI 页查看完整对话 →"链接。#/ai 页保留完整对话 + RAIL。
代价：一个小组件 + 两处文案；收益是全站角色形态统一为三态（HOLO/RAIL/CHIP），叙事闭环。

**挑战 ③：8 个情绪手动按钮是开发者调试功能混进了产品 UI。**
原版没有此功能；对访客它是"打断第四面墙"的调试面板，还占用右栏 8 次 tab 停点。
替代：情绪**只随对话状态自动切换**；手动按钮折叠进 `<details>「调试」`（默认收起，
键盘仍可达），或直接删除（若你认为无调试需求）。
代价：几乎为零；门禁中若有依赖这些按钮 id 的断言需同步改。
