## 三、安全护栏（逐条落地在代码里）

| # | 护栏 | 实现位置 / 做法 |
|---|---|---|
| 1 | **路径限定提交** | `git add -- <该笔记>`；提交前校验"暂存区恰好 1 个文件且等于该笔记"，不合格就 `git reset` 撤销并中止。**全脚本无 -a / -A / `commit -a`** |
| 2 | **仓库脏时不许乱提** | 先读 `git status --porcelain`，把**与本笔记无关**的改动**逐条写进日志并声明"我没有动它们"**，然后只提交该笔记路径 |
| 3 | **门禁不过就不发** | 构建 → ① `check-ssr-contract.py`（要求 5 页 PASS / 0 项不合格）② `assert-build.sh`（要求"通过 18 项"）③ `check-asset-integrity.py`（要求 `[PASS]`、无 `[FAIL]`）。任一不过 ⇒ 只写日志 + 弹提示，**不推送、不发布** |
| 4 | **失败可见** | 日志固定 `%LOCALAPPDATA%\xk-note\watcher.log`；失败再写 `last-failure.txt`（含阶段/文件/退出码/时间）+ **弹一次气泡**（另起进程，不阻塞循环） |
| 5 | **可关** | `-Stop` 写 `STOP` 文件并结束看守进程；配置 `enabled:false` 下个循环自动退出；桌面「关掉自动发布」快捷方式 |
| 6 | **开机自启必须显式安装** | 看守自身**绝不加启动项**；只有跑 `install-note-watch.ps1` 才在「启动」文件夹建隐藏快捷方式（不改注册表 Run 键） |
| 7 | **草稿闸门** | `draft: true` 的笔记**不发布**（线上根本看不到）⇒ 只记日志 + 提示；`autoUndraft:true` 才会替你改成 false（默认 **false**，不替站主改内容） |
| 8 | **不补发存量** | 看守启动时把现有笔记登记为"已知"，`publishBacklogOnStart` 默认 false ⇒ 不会一开机把历史笔记全发一遍 |

## 四、监视机制（为什么不用 FileSystemWatcher）

- 用 **轮询扫描（每 2 秒）**，判据三重：① `LastWriteTime` 变化过 ② **首次看到变化起静置 ≥ `debounceSeconds`（默认 4s）**（你还在打字时不打断）③ **能独占打开该文件**（编辑器已释放 ⇒ 你确实保存并关掉了）
- **不用** `FileSystemWatcher` + `Register-ObjectEvent -Action`：那种写法在 PS 5.1 里依赖事件队列泵，长时间 `Start-Sleep` 时不可靠，也无法稳定自证。轮询慢 2 秒，但**行为可预测、可测**。

### ★自检抓到的两处真 bug（都已修，值得记档）
1. **`-Start` 会落进看守循环**：清完 STOP 后没退出，且未带 `-DryRun` ⇒ 变成一个**"武装"看守**（任何保存都会自动提交+推送+发布）；外层管道又在等它结束 ⇒ 自检直接挂死。现在 `-Start` 做完开关就 `exit 0`。
2. **候选永远"不熟"**：用 `[datetime]::FromFileTimeUtc($known[$p])` 去解释 `DateTime.Ticks`（两个 "ticks" 纪元不同：FileTime 从 1601、DateTime 从 0001）⇒ 年龄算成**负数** ⇒ 流水线一次都不跑（只记"发现变更"）。现在以"首次看到变化的时刻"计时。

### ★编码坑（第三次踩到）
`edit` 工具写回中文 `.ps1` 会**剥掉 BOM** ⇒ PS 5.1 按 GBK 读 ⇒ ParserError。
⇒ 规则：**任何工具化编辑中文 .ps1 之后，复查首三字节 `EF BB BF`**；本次 3 个新 `.ps1` 已逐一补回并复验解析 0 错误。`.cmd` 保持纯 ASCII、无 BOM。

## 七、C 版方案（只出方案，未实现）：发布时**只传改动**

**现状**：每次发布都 `tar` 整站（本次实测 **144.04 MB**，其中 `kurisu/` 素材约 87MB 几乎从不变）→ scp → 接收侧整树哈希 → 原子切换。一次发布的**上传量 ≈ 整站**。

**推荐做法：差分 tar + 硬链接暂存（保留现有原子性）**

1. **发送侧**：本地构建后，产出三样东西
   - 变更文件 tar（新增/修改，按内容 sha256 判定，不看 mtime）
   - 删除清单（线上有、本次没有的相对路径）
   - **本地整树内容哈希**（沿用现有 `tree_hash` 语义，一字不改）
2. **接收侧**：
   - 用 `cp -al 当前 release/. .staging-<ts>/` 从**上一版硬链接**出暂存树（秒级、几乎不占空间）
   - 应用增量 tar（**必须先 `rm` 再写**，绝不原地截断 —— 否则会破坏与上一版共享的硬链接）
   - 按删除清单删除
   - **校验整树哈希 == 发送侧给的期望值**；不等 ⇒ **中止、不切换**（旧的自动回滚逻辑原样保留）
   - 原子 symlink 切换、自检、KEEP=4 全不动
3. **协议**：`RESULT=ok|no-change|mismatch`，新增 `DELTA_BYTES` / `EXPECTED_TREE_HASH`；DryRun 只算不发。

**改动点**（都在现有两个脚本里，不改部署拓扑）
- `scripts/publish-site-to-srv2.ps1`：新增"算增量 + 删除清单 + 期望哈希"，DryRun 输出对比数字
- `scripts/srv2-site-receive.sh`：新增 `--delta` 模式（硬链接暂存 + 应用 + 删除清单 + 哈希校验），旧的全量模式保留为回退路径

**风险**
| 风险 | 处置 |
|---|---|
| 硬链接共享被就地写坏 | 应用增量时 `rm -f` 再写；并加"校验失败不切换" |
| 删除清单算错 ⇒ 删掉线上文件 | 删除清单**只**来自"上一版有 ∩ 本地没有"；整树哈希校验兜底；先 DryRun 演练 |
| 大小写差异（Windows 不敏感 / Linux 敏感） | 发送侧对路径做**大小写冲突检测**，冲突就退回全量 |
| 中断 | 增量包小、可重传；仍是"暂存 → 校验 → 切换"，中断不会污染线上 |
| 首次发布 / 回退版本差异大 | 增量超过阈值（例如 >40% 整站）**自动退回全量** |

**工时估算**
| 项 | 工时 |
|---|---|
| 发送侧增量计算 + 删除清单 + DryRun 对比输出 | 2~3h |
| 接收侧 `--delta` 硬链接暂存 + 应用 + 校验 + 回退全量 | 2~3h |
| 测试（首次发布 / 小改一篇 / 素材大改 / 删除文件 / 中途中断 / 哈希不符中止） | 2~3h |
| **合计** | **6~9h（约 1~1.5 个工作日）** |

**收益**：日常"发一篇笔记"的发布上传量从 **≈144MB** 降到通常 **< 5MB**；中文链路下（本机实测 ~2KB/s～300KB/s 视是否走代理）这一项能省掉**数分钟到十几分钟**。
**不建议现在做**：C 动的是发布链核心（原子切换/回滚），属"高风险低频率"改动；建议排在 C1-B 稳定使用一段时间之后。

## 八、没做到的 / 照实写

1. **没有做过真实自动发布**（自检全程 `-DryRun`：不提交、不推送、不发布）。"提交 → 推送 → 发布"三步在**真实网络下的成功率**未被本次验证（只用 DryRun 验证到"门禁通过、止步于发布前"）。
2. 没有测"编辑器长时间占着文件"的真实场景（只有 `Test-FileClosed` 的独占打开逻辑；自检里文件是脚本追加写入、立即释放）。
3. 没有测 `push` 失败 / `publish` 失败的真实弹窗（只验证了失败路径的**日志与提示代码路径**会走到）。
4. 安装脚本只做了 `-DryRun`；**没有真的写启动文件夹**（符合"显式安装"要求 —— 需要站主自己点一次）。
5. 看守自检重建了 `public/`（含测试笔记那一版）；测试笔记已删，但 `public/` 里可能仍留着那份产物 —— 下次任何一次真实构建都会覆盖，不影响发布链（发布链在自己的 worktree 里重建）。
