## 一、B（视频化）的一个盲区：Safari 不支持 alpha 视频

文档 §5/§8-4 在"VP9 alpha vs AV1 alpha"之间比较，但这两个选项**在 Safari（尤其 iOS）上都不可靠**：

- VP9 in WebM：Safari 16.4+ 部分支持解码，**alpha 通道支持缺失/不可靠**；
- AV1 alpha：基本只有 Chrome 系。

这意味着"alpha WebM"不是一条全平台路线，而是**增强路线**——Safari 必然落到 PNG 回退。
由此 B 实际是两个子方案，请在 pilot 前选定：

| 子方案 | 做法 | 体积 | 兼容性 | 回退负担 |
|---|---|---|---|---|
| **B1 alpha WebM**（文档默认） | 双流 remux 成带 alpha 的 VP9 WebM，透明角色叠在现有层序里 | ~10MB | Chrome/Edge/Firefox ✅；**Safari ✗→回退** | **必须保留全量 PNG medium（44MB）**，总预算 ≈55~60MB，闸门降不动 |
| **B2 预合成不透明视频**（我在 13:49 评审里提的路线） | KTX2 帧离线合成到 BG_empty 上，出普通 H.264/MP4（房间背景是静态的，编码后码率≈0） | 预估 8~15MB | **全平台含 iOS Safari ✅** | 角色 PNG 图集可全砍，只留 boot/poster 兜底 → 闸门可降到 25~30MiB |

关键权衡：
- **B1** 工程小（remux 而非重渲染）、保持现有层序不变；但 Safari 用户永远看 PNG，且 PNG 回退吃掉大部分省下的预算——§8-5"闸门降到 40MiB"在 B1 下不成立。
- **B2** 要做"KTX2 解帧→合成→编码"管线（比 remux 重），但一次解决兼容性、闸门、内存三件事；
  注意 B2 下**静音闭嘴补丁是叠在视频上的小 PNG，不受影响**，0.35s 交叉淡入用 CSS opacity 也能做。
- **建议**：pilot 各出一条 `idle`（B1 一条 WebM、B2 一条 MP4），同屏对比画质/体积/解码行为，
  用实测而不是推演来定。两条都只花一天以内。

## 二、§8 六问的答案

1. **走 B 吗** → 走。这是 0.17 包唯一的实质红利，且与我 13:49 评审的"预合成视频"判断互相印证
   （当时我估 15~30MB，你们实测折算 7~10MB，比我乐观，更好）。
2. **先做哪个剪辑** → **两个而不是一个**：`idle`（验证 root 高频路径 + 游走）+
   `speaking_med`（验证口型链路：包络→mouthValue→闭嘴补丁叠在视频上）。只测 idle 验不到嘴。
3. **medium/hi 都出吗、PNG 留吗** → 视频源是 1x（高 1028），**比现有 hi 档还高**——采用视频后
   **hi 档废弃**；boot/poster 由视频首帧兼任。PNG medium 是否保留取决于子方案（B1 必须留、B2 可砍）。
4. **AV1 还是 VP9** → 若走 B1 选 **VP9**（支持面明显好）；但这个问题的正确解法是考虑 B2 绕过它。
5. **闸门下调吗** → **与子方案绑定，别单独定**：B1 维持 60MiB（PNG 回退在省不动）；
   B2 成功后降到 **25~30MiB** 并把它作为"B2 成功"的判据。
6. **新嘴型 profile 搁置吗** → 搁置正确。但注意下节第 ② 条的联动条件。

## 三、文档没写但必须进规格的 4 个坑

```
① Safari 见上（第一节），这是最大的遗漏。
② 几何联动：若 B 采用新包的裁窄帧/视频（764→500~636），闭嘴补丁的 anchor_track 是旧几何坐标。
   统一解法：编码管线里 ffmpeg pad 滤镜居中补回 764（B1 补透明、B2 补房间像素）——
   播放器零改动、嘴型坐标零改动、落位公式零改动。**不要**改播放器按 opaque_bbox 锚定，
   那是在运行时为离线能解决的问题付永久税。
③ 8ms 剪辑的时长口径：120 帧 @8ms 名义 0.96s，但上游自己的视频是 2.00s（60fps≈16.7ms/帧），
   与你们播放器 Math.max(16,…) 的夹取一致——无冲突，但**要写进规格**，
   防止验收时有人按 0.96s 预期判"转场变慢了"。
④ 硬切预载：视频硬切有解码延迟（PNG 切帧没有）。graph-walker 已经知道出边概率，
   规则：预载 top-2 候选节点的视频（preload="auto"），硬切时双 <video> 元素换 Visible。
   once_then_hold = pause() 停末帧（视频天然停末帧，不用 poster）。
```

## 四、其它（小）

- 新 zip 无外部 SHA256SUMS——把文档 §2 的 zip sha256 写进资产 lockfile（呼应之前"资产唯一
  路径"那条），旧包保留作回滚源的做法正确。
- `00_recon.py` 缓存不刷新新剪辑不进流水线（§9 末条）——这条建议**提升进正文**，它和
  pad764 一样是"采用新帧的前置条件"，埋在诚实边界里容易被执行方漏掉。
- A1 的"倒放开关"：once_then_hold 的"停末帧"在倒放下 = 停原剪辑首帧，语义自洽，无需特殊处理；
  但建议开关做成剪辑级字段（`"reverse": true`）而不是为新节点单独写分支，以后上游再发
  "倒放型"剪辑（这显然是上游的省空间套路，会有下一个）直接配置生效。

## 四·五、B3：第三条路（本文档新增，推荐优先级高于 B1/B2）

思路转换：不纠结浏览器认不认 alpha 视频，**把 alpha 藏进普通视频**——

```
每帧画布横向加倍：左半 = 角色 RGB，右半 = alpha 灰度（如 764×1028 → 1528×1028 不透明 H.264/MP4）
播放：单 <video> 硬解 → canvas 每帧两次 drawImage（左半取色、右半 destination-in 当蒙版）
```

| | B1 alpha WebM | B2 预合成不透明 | **B3 色/A 双拼** |
|---|---|---|---|
| 兼容性 | Safari ✗ | 全平台 ✅ | **全平台 ✅（含 iOS Safari，硬解）** |
| 保持透明/层序不变 | ✅ | ✗（房间烘死，交叉淡入会露玻璃罩接缝） | ✅ |
| 解码器/同步 | 1 个 | 1 个 | **1 个，天然同步**（双文件方案会漂移） |
| PNG 回退负担 | 必须留全量 44MB | 可全砍 | 可全砍（失败路径与 reduced-motion 共用 poster 静帧） |
| 体积估算 | ~10MB | 8~15MB | ~15~25MB（alpha 灰度可再降半分辨率，再省 20~30%） |
| 闸门可降到 | 降不动 | 25~30MiB | **30MiB** |
| 播放器改动 | 视频+PNG 双逻辑 | 最小 | 中等（蒙版合成，与闭嘴补丁同一套 canvas 机制） |

配套设计：
```
· 帧率用 VFR：MP4 逐帧时长直接写各剪辑 frameIntervalMs（8/17/21ms）——
  节奏保真度超过现有 PNG ticker（rAF 只能对 16.7ms 网格，VFR 是真 8ms），视频化唯一的"比原版更还原"点
· once_then_hold = 播完 pause 停末帧（天然）；倒放类新剪辑（A1）直接反向编码一条，几百 KB
· pilot：idle + speaking_med 各出一条 B3，验收 = iOS Safari 实机 + 低端机蒙版帧率 + 与 PNG 同屏比对
· 成功判据：角色资产 ≤25MB → 闸门降 30MiB；失败退回 B1+PNG 回退（承认 Safari 看静态）
· 生成管线是现有图集脚本的小改（KTX2 解帧 → 双拼 → ffmpeg），不需要新工具链
```
