怎么验证 · grep eve.json 与 alerts.json先确认加载，再数告警

第一步永远是确认规则被加载（否则后面的 0 没有意义）：

# 语法验证（一次性容器，等价且不碰生产；README §3 记的就是这条）
docker run --rm --network none --pull=never -v /tmp/xkrules:/rules:ro \
  --entrypoint suricata jasonish/suricata:latest -T -S /rules/xk-lab.rules
# 结果：Suricata version 8.0.7 / Configuration provided was successfully loaded / exit 0
# 再看规则文件在不在生产目录（不在 ⇒ 后面 grep 出 0 是「没部署」）
ls -l /opt/suricata/rules/ ; ls -l /var/ossec/etc/rules/

第二步才是对账（Suricata 看 signature_id，Wazuh 看 rule.id）：

# Suricata：先数条数，再只看自己这台源，避免被别人的扫描混进来
grep -c '"signature_id":1000103' /opt/suricata/logs/eve.json
grep '"signature_id":1000103' /opt/suricata/logs/eve.json | grep '"src_ip":"10.0.0.20"'
grep '"signature_id":1000104' /opt/suricata/logs/eve.json | tail -n 5

# 1000103 的输入证据在 flow 面：会话速率
grep '"dest_port":2222' /opt/suricata/logs/eve.json | grep '"event_type":"flow"' | tail -n 50

# Wazuh：alerts.json 一行一个 JSON

三个已踩的坑均为实测
失败次数型规则会空转 已部署的 100110（120s 内 5 次登录失败）在 2026-10-17 全天 Cowrie 只有 19 条 login.failed 对 14,061 条 login.success， alerts.json 里 "id":"100110" 计数 0。 机器人拿泄露口令表，一枪就中 —— 新规则才改成按会话速率判（100400）。 自测时只发错误口令，测的其实是这条空转规则。
94.9% 的告警是自家的 293,482 条 alert 里 278,405 条是 10.0.0.10 → 169.254.0.4:80 POST /ca_report.cgi。 自测前先想清楚：你 grep 出来的「命中」可能全是云主机心跳； 1000108 就是为消掉它写的，但它是 opt-in，写错方向会把真实 C2 一起静音。
Wazuh XML 的三种写法 ① JSON 解码事件不能用 <same_source_ip/>（内部 srcip 为空，规则永不触发） → 用 <same_field>src_ip</same_field>； ② <if_matched_group> 不写尾随逗号、<group> 要写； ③ 同一 rule 里 <decoded_as> 与 <regex> 不能共存 （Syntax error on tag 'regex' 会让 analysisd 拒绝启动）。
