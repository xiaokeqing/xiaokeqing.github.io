口径：基址来自 <meta name="wb-api">，路径就是表格每一行自己写的； PASS = HTTP 2xx 且响应能解析成 JSON（.js 别名还要求 code=200）， FAIL = 其它一切情况（超时、跨源失败、非 JSON、接口自报失败——此时 HTTP/字节可能显示「未取到」）。 耗时 = fetch 发起到响应体读完；字节 = 解码后的 UTF-8 字节数（跨源读不到压缩后传输量）。 接口带 max-age=45s，命中浏览器或边缘缓存时耗时会接近 0ms —— 所以「快」不等于「新」，新不新看下面第 3 块。

判定优先用服务端 snapshotAt（带时区、口径最硬），取不到才退回按 generatedAt 用本机时钟算； 两个都在秒级刷新，所以这行会随时间自己变旧 —— 这正是要你看的：页面上的数字不是硬编码，它在变旧。 接口带 stale-while-revalidate=90：边缘节点回源刷新期间会先把最多约两分钟的旧副本发给你， 所以「偏旧」通常不是接口挂了（刷新一次多半回到「新鲜」）；cacheAgeSeconds + Age 就是这份数据的真实年龄。 本机时钟如果比服务端快/慢，会出现负数或整小时级偏差，此时页面写「本机时钟早于服务端…」并不判定，而不是假装新鲜。

同一时刻在你自己的终端敲，数字应该和上面那几张表对得上；对不上，问题就在这里，不是页面修图。 取不到的时候（断网、401、429 限流、源站挂了），本页对应行就显示「未取到」并带上原因： 卡片不填 0，不拿别的时刻的数凑数，也不把旧缓存当新数据 —— 这正是这一页的意义。
