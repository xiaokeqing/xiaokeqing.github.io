## ④ 下载事件 0 条：下次怎么把它留住

这不是第四个样本，是这一页最该被记住的一条**缺口**。三条链路全部「连端口、猜口令、不落文件」，于是我们能写行为、写口令结构、写协议特征，却写不出一个 SHA-256。要补的不是分析能力，是**留存链路**：

1. **Cowrie 允许下载并落盘**：`cowrie.cfg` 里 `[honeypot] download_limit_size` 设到非 0（例如 `104857600`，100MB 上限），下载的二进制才会写进 `/opt/cowrie/dl/` 并在 `cowrie.session.file_download` 事件里带 `shasum`、`outfile`、`url`。默认是 0 = 只记录不落盘，这就是本窗口「0 条」的直接原因。
2. **Suricata 开 `file-store`**：`suricata.yaml` 的 `file-store` 段启用（`enabled: yes`、`dir` 指到独立分区、`stream-depth` 给够），HTTP/SMB 流量里的对象会按 `fileinfo` 落成文件，`eve.json` 的 `http` 事件随之带 `fileinfo.filename` / `sha256` / `size`。这一层管的是「不经过蜜罐、直接打 Web 服务」的下载。
3. **蜜罐目录只读挂载 + 单独可写落盘区**：`/opt/cowrie`、`/opt/dionaea` 用 `-v ...:ro` 挂只读（防攻击者改蜜罐自身），只把 `dl/`、`binaries/` 单独挂成可写卷并加配额 —— 否则真抓到样本时，要么落不下，要么把磁盘灌满。

留到之后怎么做：**不复制、不上传、不提供下载链接**，只记录 hash 与元数据（`file` 类型、大小、来源 URL、时间、UA），再按 `docs/样本分析-TEMPLATE.md` 的红线写报告。哈希算出来之前，这一页的第 ① ② ③ 条就一直标着「未留存」——这不是没写，是确实没有。
